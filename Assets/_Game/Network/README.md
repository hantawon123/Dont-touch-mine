# Network

Photon Fusion과 맞닿는 코드만 둡니다. 러너 생성, 세션 시작과 종료, 방 목록 수신,
스폰과 상태 복제가 여기에 있습니다.

- `Server`가 확정한 규칙 판정을 참가자에게 복제하는 것이 이 계층의 역할입니다.
  반대 방향은 없습니다. `Server`는 Photon을 모릅니다.
- Fusion 타입(`NetworkRunner`, `PlayerRef`, `NetworkObject`)은 이 계층 밖으로
  나가지 않습니다. 바깥에는 `Core`의 중립 타입으로 전달합니다.
- `Client`를 직접 참조하지 않습니다.

## 게임 이벤트 RPC 규약

경기 판정은 호스트의 State Authority만 수행합니다. 클라이언트 RPC는 "행동을
시도했다"는 요청일 뿐이며, 성공 여부와 결과는 `MatchSessionCoordinator`가
서버 시간과 현재 상태를 기준으로 다시 검증합니다.

### 공통 원칙

- 송신 플레이어는 RPC 인자로 받지 않고 `RpcInfo.Source`에서 찾은 뒤
  `PlayerRegistry`의 `playerIndex`로 변환합니다. 다른 플레이어를 사칭할 수
  없어야 합니다.
- 위치, 속도, 대상 ID는 유한값인지 확인하고 현재 페이즈, 기절 여부, 거리,
  소유·보유 상태와 남은 사용 횟수를 State Authority가 검증합니다.
- 페이즈, 종료 시각, 배치 위치, 파괴·기절 상태처럼 중간 입장자도 알아야 하는
  값은 `[Networked]` 상태로 복제합니다. RPC만으로 영구 상태를 저장하지 않습니다.
- RPC는 입력 요청과 즉시 연출 알림에만 사용합니다. 동일 요청이 재전송돼도
  서버 상태 검증으로 두 번 처리되지 않아야 합니다.
- 플레이어 물건의 소유자 정보는 전체 송신하지 않습니다. 각 플레이어에게는
  자신의 배정 물건만 개별 통지하고, 파괴 알림에는 파괴자와 물건 ID만 포함합니다.
- 클라이언트가 보내는 시간은 판정에 사용하지 않습니다. 모든 `now` 값은 Fusion
  네트워크 시간에서 얻습니다.

### 클라이언트 -> State Authority 요청

| 요청 | 인자 | 서버 검증 및 처리 |
| --- | --- | --- |
| 물건 집기 | `objectId` | 현재 행동 가능 여부와 물건 존재·미보유 상태 확인 |
| 물건 놓기 | 위치, 회전 | 서버가 현재 보유 물건을 찾고 배치 가능 위치와 페이즈 확인 |
| 물건 던지기 | 위치, 회전, 초기 속도 | 서버가 현재 보유 물건을 찾고 유한한 물리값과 페이즈 확인 |
| 플레이어 타격 | `targetPlayerIndex` | 공격자·대상 활성 상태, 거리, 페이즈와 기절 상태 확인 |
| 분쇄기 사용 | 없음 | 서버가 현재 보유 물건과 F키 횟수를 확인. 배출 위치는 서버 씬의 `ShredderSpot` 사용 |

경기 시작은 방장인 State Authority가 직접 확정하므로 RPC를 만들지 않습니다.
하이라이트 순서와 결과 진입도 State Authority의 네트워크 시간으로 진행하며,
클라이언트의 재생 완료 통지로 공용 페이즈를 바꾸지 않습니다.

플레이어 이탈은 클라이언트 RPC가 아니라 Fusion의 `OnPlayerLeft`를 기준으로
처리합니다. 마지막 위치에 보유 물건과 미배치 배정 물건을 놓고 퇴장자의 숨기기
턴을 건너뜁니다. 활성 플레이어가 한 명이어도 경기는 계속되며 제한 시간 또는
모든 플레이어 물건 파괴로 정상 종료합니다. 새 경기 시작 최소 인원은 변경하지 않습니다.

### State Authority -> 참가자 복제·알림

| 데이터 | 전달 범위 | 방식 |
| --- | --- | --- |
| 페이즈와 페이즈 종료 시각 | 전체 | `[Networked]` 상태 |
| 참가자 활성 상태와 `playerIndex` | 전체 | `[Networked]` 상태 |
| 자신의 배정 물건 | 해당 플레이어만 | 대상 지정 RPC 또는 Input Authority 전용 상태 |
| 물건 위치·보유·파괴 상태 | 전체 | `[Networked]` 상태 |
| 기절 종료 시각과 남은 분쇄 횟수 | 전체 | `[Networked]` 상태 |
| 파괴 알림 | 전체 | RPC: `destroyerPlayerIndex`, `itemId`, `destroyedAt` |
| 기절 알림 | 전체 | RPC: 공격자, 대상, 드롭 물건, 시작·종료 시각 |
| 던지기 연출 | 전체 | RPC: 던진 플레이어, 물건, 해제 Pose, 초기 속도 |
| 파이널 구간 알림 | 전체 | RPC: 시작·종료 시각 |
| 경기 결과 | 전체 | `[Networked]` 상태: 종료 사유, 종료 시각, 승자 목록 |

RPC 수신 측은 UI와 연출만 갱신합니다. 수신 RPC에서 `Server` 규칙을 다시
실행하거나 로컬 판정으로 네트워크 상태를 덮어쓰지 않습니다.

## 호스트 이전 중 경기 복원

- `StartGame` 성공만으로 승계를 완료하지 않습니다. Fusion의 `IsResume`이 해제되고 Runner와 씬이 준비될 때까지 신규 캐릭터 생성과 런타임 진행을 보류합니다. 스냅샷의 기존 좌석을 먼저 복원한 뒤 누락된 참가자만 생성하고 방장 표시와 스냅샷을 갱신합니다.
- `HostMigrationResume`은 Fusion 코루틴에서 호출되므로 복원 예외를 승계 비동기 흐름으로 전달해 방 종료·정리를 수행합니다. 대기 중 퇴장하거나 Runner가 교체되면 기존 승계 작업은 후속 처리를 중단합니다.
- 인게임 승계는 씬의 경기 규칙·배정·위치 복원까지 확인한 뒤 완료합니다. 준비 중에는 복원 전용 틱만 허용하고, 복원 실패는 Update에서 승계 실패 정리로 전달합니다. 결과 씬에서는 이미 종료된 경기 런타임을 다시 만들지 않습니다.
- 승계 씬은 퇴장 직전 화면이 아니라 저장된 경기 페이즈에 맞춥니다. Waiting은 로비, Hiding/Searching은 경기 씬, 결과가 확정된 Highlight/Result는 결과 씬을 사용합니다. 씬 변경 뒤 기존 공개 상태를 다시 전달하며, Fusion 준비·씬 보정·경기 복원 대기는 각각 실제 시간 60초를 넘기면 승계 실패로 정리합니다.
- 승계로 재생성한 KCC 캐릭터는 저장된 서기·앉기·엎드리기 자세와 이동 설정을 유지하고 해당 자세의 충돌체 높이를 다시 적용합니다. 신규 캐릭터만 기본 서기 자세로 초기화하며, 복원된 캐릭터도 위치 배치가 끝나기 전에는 KCC를 활성화하지 않습니다.
- 서버에서 확정한 페이즈를 받으면 앱의 방 내부 상태도 한 번에 동기화합니다. 스냅샷 롤백으로 Highlight/Result에서 InGame으로 돌아갈 수 있지만, 일반 사용자 화면 전환 규칙과 Home/RoomBrowser의 진입 제약은 유지합니다. 결과 진입에는 기존처럼 Result 페이즈와 결과 데이터가 모두 필요합니다.
- 배정 정보는 최초 전송 뒤에도 현재 경기의 수신자별로 보관합니다. 참가자 씬은 준비된 뒤 실제 수신할 때까지 1초 간격으로 자신의 배정 정보만 재요청합니다. 서버는 요청 패킷의 송신자와 확정 명단을 대조하고 이미 공개한 배정만 재전송하며, Runner 교체·재경기 초기화 때 보관 내용을 비웁니다.
- 결과 화면의 씬 이동과 자동 로비 복귀도 `IsRuntimeReady`를 확인합니다. 승계 중에는 복귀 카운트다운을 멈추고, 준비가 끝나면 남은 표시 시간부터 이어갑니다. 아직 준비되지 않은 새 호스트를 씬 로딩 실패로 처리하지 않습니다.
- 새 호스트에게 결과 씬이 이미 로드됐다면 재로드하지 않고 복귀 타이머만 진행합니다. 스냅샷이 진행 중인 경기로 롤백되면 이전 결과의 이동·복귀 상태를 비워 다음 종료 결과를 정상 처리합니다.
- `MatchSession` 프리팹의 `MatchMigrationCheckpoint`는 각 권한 틱 끝에 배정·스폰·배치·전투 상태와 서버 시각을 기록합니다. 일반 참가자에게는 이 컴포넌트를 복제하지 않아 물건 소유자 정보를 공개하지 않습니다. 새 호스트만 Fusion의 권한 스냅샷에서 읽습니다.
- 공개된 `MatchSessionState`의 물건·참가자·결과와 함께 순수 `MatchSessionCoordinator`를 복원합니다. 남은 시간은 체크포인트 시각과 새 서버 시각의 차이만큼 보정합니다. 복원 경로에서는 신규 경기 시작이나 물건 재배정을 하지 않습니다.
- 마지막으로 Photon Cloud에 저장된 스냅샷 이후의 진행은 유실될 수 있습니다. 자동 저장 간격은 현재 10초이며, 전송 실패 시 마지막 성공 시점은 더 오래될 수 있습니다.
- 원본 하이라이트 프레임·이벤트 기록은 기존 호스트 메모리에만 있으므로 이전이 발생한 경기에서는 하이라이트를 생략하고 확정 결과로 이동합니다. 이미 확정된 승자·종료 사유는 재계산하지 않습니다.
- 네트워크 프리팹 구성이 변경되므로 반드시 모든 참가자가 같은 커밋/빌드를 사용해야 합니다. 비공개 체크포인트의 실제 Fusion 복원과 멀티플레이 승계는 실기 검증 대상입니다.

## 방 객체 메모리와 초기화 실패

방 상태와 호스트 복원 체크포인트가 같은 `NetworkObject`에 들어가므로 Fusion 힙의
`PageShift`는 16(64 KiB)을 사용합니다. `PageCount`는 256으로 유지합니다. 페이지 크기는
전체 Fusion 힙의 사전 할당 메모리에도 영향을 주므로 실제 플레이 메모리를 확인해야 합니다.
방 객체 생성 전 상태 크기를 검사하고, 초기화에 실패하면 해당 러너 정리를 기다린 뒤
실패를 반환합니다. 이 동안 새 연결을 차단하며, 프리팹 크기 검사는 EditMode 테스트로도 확인합니다.

## 왜 `Server`와 분리했나

`Server`는 경기 규칙을 순수 C#으로 판정하고 EditMode 테스트로 검증합니다.
Fusion을 같은 어셈블리에 두면 그 테스트에 Photon이 딸려 들어옵니다.
전송 계층만 떼어내면 양쪽 모두 원래 목적대로 남습니다.

## NetworkBehaviour를 새 어셈블리에 만들 때

Fusion은 `NetworkBehaviour`가 든 어셈블리를 IL 후처리(weaving)해야 동작합니다.
대상 목록은 `Assets/Photon/Fusion/Resources/NetworkProjectConfig.fusion`의
`AssembliesToWeave`이고, 기본값에는 `Assembly-CSharp` 계열만 들어 있습니다.

`Game.Network`는 등록해 뒀습니다. 앞으로 다른 어셈블리에 `NetworkBehaviour`를
만들면 그 이름도 여기에 넣어야 합니다. 빠뜨리면 컴파일은 통과하고 실행 시점에만
이렇게 실패합니다.

```text
[Fusion] Type ... has not been weaved. Has the assembly ... been added to
```

## 두 인스턴스로 테스트하기

빌드를 만들지 않고 에디터 안에서 호스트와 클라이언트를 동시에 띄웁니다.
Multiplayer Play Mode 2.0 기준입니다.

### 1. 태그 만들기 (프로젝트당 한 번)

`Edit > Project Settings > Multiplayer > PlayMode > Player Tags`에서 `+`를 눌러
`Host`와 `Client`를 만들고 **Save**를 누릅니다. `ProjectSettings/VirtualProjectsConfig.json`에
기록되므로 팀원은 이 단계를 건너뜁니다.

### 2. 시나리오 만들기 (프로젝트당 한 번)

1. `Window > Play Mode > Scenarios`를 엽니다.
2. **Configure play mode scenarios**를 고릅니다.
3. `+`로 시나리오를 만듭니다.
4. 오른쪽에서 **Editor** 체크가 켜져 있는지 확인하고,
   **Additional Editor Instances**의 `+`로 인스턴스를 하나 추가합니다.

### 3. 태그 배정

같은 창에서 각 인스턴스의 **Tags** 드롭다운을 펼쳐 고릅니다.

| 인스턴스 | 태그 |
| --- | --- |
| Editor | `Host` |
| Additional Editor | `Client` |

한 인스턴스에는 태그를 하나만 붙일 수 있습니다.

### 4. Play

호스트가 방을 열고 클라이언트가 그 방으로 들어갑니다. 추가 인스턴스 창은
`Ctrl+F9`~`Ctrl+F12`로 전환합니다.

### 태그가 하는 일

태그는 `GameSessionLifetimeScope`의 모드만 덮어씁니다. 방 이름·맵·인원·비밀번호는
인스펙터 값을 양쪽이 그대로 공유하므로 한 곳만 고치면 됩니다.

태그를 붙이지 않으면 인스펙터의 `Mode`가 그대로 쓰이고, 빌드에는 가상 플레이어가
없으므로 태그 분기 자체가 동작하지 않습니다.

> Unity 문서는 역할 배정에 태그 대신 Dedicated Server 패키지를 권합니다. 그쪽은
> 전용 서버 빌드를 전제하는데 우리는 플레이어 호스트 방식이라, 전용 서버로 옮기기
> 전까지는 태그가 맞습니다.
