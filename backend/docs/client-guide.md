# 클라이언트 연동 안내

Unity 클라이언트가 이 백엔드를 붙일 때 알아야 하는 규약입니다.

**엔드포인트 목록은 여기 없습니다.** 그건 [`openapi.json`](openapi.json)에 있고 코드에서
자동 생성됩니다. 이 문서에는 명세가 표현할 수 없는 것만 적습니다 — 왜 그렇게 되어 있는지,
어떤 순서로 불러야 하는지, 값의 형식이 무엇인지.

명세를 눌러보면서 확인하려면 백엔드를 로컬에 띄우고 `http://localhost:8080/swagger-ui.html`
로 갑니다. **운영 서버는 Swagger 를 열지 않습니다.** 지금 API 에 인증이 없어서, 운영에서
서빙하는 Swagger UI 는 아무나 열어서 운영 DB 에 쓸 수 있는 버튼이 됩니다.

기대 응답까지 적어둔 요청 모음은 [`../http/accounts.http`](../http/accounts.http) 에
있습니다(VS Code REST Client). 전수가 아니라 눌러볼 만한 것만 있습니다.

## 2. 식별과 인증은 다릅니다

거의 모든 요청에 헤더 둘을 함께 넣습니다. 둘 다 계정 발급 응답에 있습니다.

```
X-User-Id: <userId>
X-Account-Token: <photonToken>
```

**`X-User-Id` 는 식별이고 `X-Account-Token` 이 증명입니다.** `userId` 는 공개 값이라 같은
방에 있던 사람은 서로의 것을 압니다. 그것만 믿으면 남의 이름으로 신고나 친구 끊기를 보낼 수
있어서, 서버가 그 `userId` 에 찍어 준 서명(`photonToken`, 3절 끝)을 같이 요구합니다. 서버는
요청마다 서명을 다시 계산해 비교하고, 없거나 다르면 `401 UNAUTHORIZED` 입니다.

**`X-User-Id` 를 보내는 모든 요청에 붙이세요.** 한 곳에서 헤더를 만들고 있다면 거기 한 줄이
전부입니다. 계정 발급(`POST /api/v1/accounts`)만 예외인데, 토큰을 아직 받기 전이기
때문입니다. 플레이 로그 전송은 원래 `X-User-Id` 를 보내지 않으므로 그대로입니다.

서버에 서명 비밀이 설정되지 않았으면(로컬 개발) 계정 응답에 `photonToken` 이 없고 검사도
하지 않습니다. 그때는 헤더를 비워 두거나 빼면 됩니다.

클라이언트는 `userId` 를 비밀로 다룰 필요가 없지만, **화면에 남의 `userId` 를 노출하지는
마세요.** 토큰은 로그와 화면에 남기지 않습니다.

되돌릴 수 없는 연산은 자격증명을 하나 더 요구합니다. 현재는 계정 삭제 하나이고
`X-Device-Id` 를 받습니다.

## 3. `deviceId` 는 자격증명입니다

계정은 기기 식별자로 발급받습니다. 그 값이 곧 그 계정의 비밀번호에 해당합니다.

지켜야 할 것:

- **응답에 절대 나오지 않습니다.** 어떤 API 응답에서도 `deviceId` 를 읽을 수 없습니다.
  테스트가 그걸 검증합니다. 클라이언트가 직접 저장해 두어야 합니다.
- **로그에 남기지 마세요.** 서버도 남기지 않습니다.
- **쿼리 파라미터로 보내지 마세요.** nginx 접근 로그에 남습니다. 헤더나 본문으로 보냅니다.
- 기기에 안전하게 보관합니다. 이 값을 잃으면 **그 계정으로 돌아갈 방법이 없습니다.**

### 발급은 멱등합니다

같은 `deviceId` 로 다시 부르면 새 계정이 생기지 않고 기존 계정이 돌아옵니다.
`201` 이면 새로 만든 것, `200` 이면 원래 있던 것입니다. 그래서 앱을 켤 때마다 그냥 불러도
됩니다 — 응답을 못 받아 재시도하는 경우에도 계정이 하나로 유지됩니다.

### 임시 닉네임

발급 시 서버가 닉네임을 지어 줍니다. 응답의 `nicknameSet` 이 `false` 면 아직 임시입니다.
**첫 실행에서 닉네임 입력 화면을 띄울지 판단하는 값입니다.** 이름 자체를 비교하지 마세요.

닉네임은 **대소문자를 구분합니다.** `player` 와 `Player` 는 서로 다른 이름이라 둘 다
존재할 수 있습니다. 중복 확인을 클라이언트에서 대소문자 무시로 하면 서버 결과와 어긋납니다.

### 검색은 정확히 일치입니다

```
GET /api/v1/users?nickname=나그네9821
```

**앞글자로는 찾히지 않습니다.** `나그` 로는 아무도 안 나옵니다. 닉네임을 통째로
알고 있어야 찾을 수 있습니다.

**대소문자를 구분합니다.** `player` 로 검색하면 `Player` 는 나오지 않습니다.
둘은 서로 다른 닉네임이고 동시에 존재할 수 있습니다.

그래서 **결과는 많아야 한 명**입니다. `limit` 파라미터는 남아 있지만 결과에 영향을
주지 않습니다.

찾지 못하는 경우가 흔하므로 **"검색 결과가 없습니다" 표시를 반드시 두세요.** 빈
배열이 정상 응답입니다.

자기 자신은 언제나 결과에서 빠집니다.

### 검색에서 빠지기

```
PUT /api/v1/accounts/me/searchable
{ "searchable": false }
```

바뀐 계정을 그대로 돌려줍니다. 따로 조회할 필요 없이 그 응답으로 체크박스를 다시
그리면 됩니다. 현재 값은 `GET /api/v1/accounts/me` 의 `searchable` 에도 있습니다.

**멱등합니다.** 이미 꺼둔 것을 또 꺼도 성공입니다. 체크박스를 두 번 눌러 원래대로
돌아온 경우가 오류일 이유가 없습니다.

**값을 빠뜨리면 `400` 입니다.** `{}` 를 보내면 "끄겠다"로 읽지 않습니다.

#### 무엇이 막히고 무엇이 안 막히는가

**닉네임 검색에서만 빠집니다.** 서버가 결과에 담지 않으므로 응답 자체에 없습니다.

| | 켠 상태 | 끈 상태 |
| --- | --- | --- |
| 닉네임 검색 | 나옴 | **안 나옴** |
| 친구 목록 | 나옴 | 나옴 |
| 받은 요청 · 받은 초대 | 나옴 | 나옴 |
| `userId` 로 온 친구 요청 | 받음 | 받음 |

이미 아는 사람과의 화면은 그대로 둡니다. 친구 목록에서까지 이름이 사라지면 친구가
없어진 것처럼 보입니다.

그래도 뜻이 성립하는 이유는 `userId` 가 UUID 라서입니다. 검색으로 찾지 못하면 그 값을
알 길이 사실상 없습니다 — 이미 친구이거나, 요청을 주고받았거나, 같은 방에 있었던
경우뿐입니다.

**같은 방에 있었던 사람은 예외입니다.** 방에 들어갈 때 클라이언트가 Fusion 연결 토큰에
`userId` 를 함께 실어 보내고, 호스트가 그 값을 각 `PlayerAvatar` 의 `UserId` 로 복제합니다.
그래서 같이 게임한 사람은 서로의 `userId` 를 알고, 검색을 꺼도 친구 요청을 보낼 수
있습니다. 의도한 동작입니다.

### 외형

옷장에서 고른 파츠 넷을 계정에 저장합니다.

```
PUT /api/v1/accounts/me/appearance
{ "bodyColor": "body_black", "hood": "hood_bear_purple", "shoes": "shoes_pink", "face": "face_smile" }
```

바뀐 계정을 그대로 돌려줍니다. 응답의 `appearance` 로 캐릭터를 다시 그리면 됩니다.

**넷 다 필수입니다.** 하나라도 빠지면 `400` 입니다. 화면은 늘 넷을 다 알고 있으므로 부분
갱신은 없습니다.

**멱등합니다.** 처음 저장과 덮어쓰기가 같은 요청이고, 같은 값을 다시 보내도 성공입니다.

#### 서버는 파츠 목록을 모릅니다

값은 클라이언트가 정한 파츠 id 이고 서버는 **형식만** 봅니다. 공백 없는 ASCII 출력 문자로
1~32자입니다. `#A1B2C3` 같은 색상값도 통과합니다. 한글과 공백은 막힙니다.

그래서 **처음 보는 id 도 그대로 저장되고 그대로 돌아옵니다.** 카탈로그에서 파츠를 빼거나
이름을 바꾼 뒤에도 이전에 저장한 값은 남습니다. 응답에서 모르는 id 를 읽으면 그 파츠만
기본값으로 대체하세요. 그렇지 않으면 카탈로그를 고칠 때마다 옛 사용자의 캐릭터가 깨집니다.

32자는 저장 길이일 뿐입니다. 파츠 id 문자열은 서버와 이 클라이언트 사이에서만 오갑니다.
외형은 지금 **내 클라이언트에서만** 적용하고, 로비와 경기에서 다른 사람에게 복제하지는 아직
않습니다. 서버에 남는 것이 인덱스가 아니라 id 문자열이라 카탈로그 순서를 바꿔도 저장된
외형은 깨지지 않습니다.

#### 조회는 따로 없습니다

`POST /api/v1/accounts` 와 `GET /api/v1/accounts/me` 응답에 실려 옵니다. 앱을 켜서 계정을
발급받는 그 응답으로 외형까지 알 수 있고, 호출이 하나 늘지 않습니다.

```json
{ "userId": "...", "nickname": "...", "appearanceSet": true,
  "appearance": { "bodyColor": "body_black", "hood": "hood_bear_purple", "shoes": "shoes_pink", "face": "face_smile" } }
```

**저장한 적이 없으면 `appearanceSet` 이 `false` 이고 `appearance` 는 `null` 입니다.** 그때는
클라이언트의 기본 파츠를 씁니다.

**`appearance == null` 로 판별하지 마세요.** `JsonUtility` 는 JSON 의 `null` 객체를 null 로
읽지 않고 필드가 비어 있는 객체를 만듭니다. `appearanceSet` 이 그 함정을 피하려고 있는
값입니다. `nicknameSet` 과 같은 역할입니다.

남의 외형을 서버에서 조회하는 길은 없습니다. 서버는 내 것만 기억하고, 로비와 경기에서
다른 사람의 외형을 보여 주는 복제는 아직 클라이언트에 없습니다.

#### 초기화

```
DELETE /api/v1/accounts/me/appearance
```

저장한 외형을 지우고 "아직 고르지 않은" 상태로 돌아갑니다. 응답은 위와 같은 계정이고
`appearanceSet` 이 `false` 입니다. 저장한 적이 없어도 `200` 입니다.

기본 파츠를 PUT 하는 것과 다릅니다. 그렇게 하면 기본 파츠가 나중에 바뀌어도 초기화한 사람은
옛 값에 남습니다. 지우면 그때의 기본값이 쓰입니다.

### Photon 접속에 쓰는 토큰

계정 응답에 `photonToken` 이 함께 옵니다. **Photon 에 접속할 때 `userId` 와 짝으로 보내야
합니다.** 이것이 없으면 정지된 사람이 남의 `userId` 를 넣어 게임에 들어옵니다.

```csharp
var auth = new AuthenticationValues { AuthType = CustomAuthenticationType.Custom };
auth.AddAuthParameter("userId", account.UserId);
auth.AddAuthParameter("token", account.PhotonToken);
auth.UserId = account.UserId;
```

**로비 접속과 방 접속 두 곳 모두에 실어야 합니다.** 한 곳만 하면 다른 쪽이 그대로 열립니다.

`photonToken` 은 계정을 돌려주는 모든 응답에 들어갑니다(발급·조회). 앱을 껐다 켜면 계정을
다시 읽으므로 따로 보관하지 않아도 됩니다. 서버에 비밀이 설정되지 않았으면 이 필드가
없고, 그때는 Photon 인증도 꺼진 상태라 보낼 것이 없습니다.

만료가 없습니다. 서버가 서명 비밀을 바꾸면 모두의 토큰이 한 번에 무효가 되고, 그때는
계정을 다시 읽어 새 토큰을 받습니다.

## 4. 시각 형식

시각은 모두 **`yyyyMMddHHmmss` 형식의 14자 문자열이고 UTC** 입니다. `20260903142530` 처럼
옵니다. ISO 8601 이 아니고, 타임존 정보가 문자열에 없습니다.

```csharp
// UTC 로 명시해서 파싱해야 합니다. 안 하면 기기 로컬 시간으로 읽혀 9시간 어긋납니다.
DateTime.ParseExact(createdAt, "yyyyMMddHHmmss", CultureInfo.InvariantCulture,
                    DateTimeStyles.AssumeUniversal | DateTimeStyles.AdjustToUniversal);
```

화면에 보일 때는 `.ToLocalTime()` 을 거칩니다.

## 5. 오류 응답

실패는 항상 같은 형태입니다.

```json
{ "code": "ACCOUNT_NOT_FOUND", "message": "계정을 찾을 수 없습니다." }
```

**`code` 로 분기하세요.** `message` 는 사람이 읽는 용도이고 문구가 바뀔 수 있습니다.

| `code` | HTTP | 언제 | 클라이언트가 할 일 |
| --- | --- | --- | --- |
| `MISSING_HEADER` | 400 | 필수 헤더가 없음 | 버그입니다. 헤더를 확인하세요 |
| `INVALID_REQUEST` | 400 | 값이 형식에 안 맞음 | 입력값을 고쳐 다시 보냅니다 |
| `SELF_FRIEND_REQUEST` | 400 | 자기에게 친구 요청 | UI 에서 미리 막습니다 |
| `UNAUTHORIZED` | 401 | `X-User-Id` 는 있는데 `X-Account-Token` 이 없거나 그 계정의 것이 아님 | 헤더를 확인하세요. 서버 비밀이 바뀐 뒤라면 계정을 다시 읽어 새 토큰을 받습니다 |
| `ACCOUNT_NOT_FOUND` | 404 | 부르는 사람의 계정이 없음 | **계정을 다시 발급받아야 합니다** |
| `TARGET_NOT_FOUND` | 404 | 상대를 찾을 수 없음 | "그 사용자가 없습니다" |
| `SUSPENDED` | 403 | 정지된 계정 | **더 진행할 수 없습니다.** 안내를 띄우고 멈춥니다. 계정 발급을 다시 불러도 같은 응답입니다 |
| `FRIEND_REQUEST_NOT_FOUND` | 404 | 그 요청이 없음 | 목록을 다시 불러옵니다 |
| `NOT_FRIENDS` | 404 | 친구가 아님 | 목록을 다시 불러옵니다 |
| `NICKNAME_TAKEN` | 409 | 닉네임이 이미 쓰임 | 다른 이름을 받습니다 |
| `ALREADY_FRIENDS` | 409 | 이미 친구 | 목록을 다시 불러옵니다 |
| `REQUEST_ALREADY_SENT` | 409 | 이미 보낸 요청 | 목록을 다시 불러옵니다 |
| `TARGET_IN_GAME` | 409 | 초대할 친구가 로비나 경기 중 | "게임 중인 친구입니다". 홈으로 나오면 다시 부를 수 있습니다 |
| `CONFLICT` | 409 | 동시 요청이 겹침 | 다시 시도하면 대개 됩니다 |
| `RATE_LIMITED` | 429 | 한 IP 가 플레이 로그를 분당 허용량 넘게 보냄 | 그 배치를 스풀에 두고 다음 flush 에 다시 보냅니다 |
| `NICKNAME_GENERATION_FAILED` | 500 | 서버가 임시 닉네임을 못 만듦 | 서버 문제입니다. 재시도 |

`ACCOUNT_NOT_FOUND` 와 `TARGET_NOT_FOUND` 를 나눈 이유가 대응이 다르기 때문입니다.
전자는 내 계정이 사라진 것이라 발급부터 다시 해야 하고, 후자는 화면에 메시지만 띄우면
됩니다.

`SUSPENDED` 는 그 둘과 또 다릅니다. **재시도로 풀리지 않습니다.** 운영자가 계정을 정지한
상태이고, 계정 발급(`POST /api/v1/accounts`)과 `X-User-Id` 가 붙은 모든 요청이 같은
응답을 줍니다. 그래서 `ACCOUNT_NOT_FOUND` 처럼 발급을 다시 부르면 같은 자리를 맴돕니다.
안내를 띄우고 멈추는 것이 유일한 대응입니다.

사유는 응답에 담기지 않습니다. 정지 사유는 신고 내용에서 나오므로 그대로 돌려주면 누가
무엇을 신고했는지가 드러납니다.

`UNAUTHORIZED` 는 정지 검사보다 앞에서 납니다. 토큰이 없는 요청은 그 계정이 정지됐는지
아닌지를 알 수 없습니다. 남의 `userId` 를 넣어 정지 여부를 알아내는 길을 막으려는 것입니다.

## 6. 접속 상태

친구 목록의 `presence` 는 `OFFLINE` / `ONLINE` / `IN_LOBBY` / `IN_GAME` 넷 중 하나입니다.

| 값 | 뜻 |
| --- | --- |
| `OFFLINE` | 게임을 켜지 않았거나 알림 채널 연결이 끊겼습니다 |
| `ONLINE` | 게임은 켰지만 Photon 룸 밖입니다. 홈이나 게임 찾기 화면 |
| `IN_LOBBY` | 룸에 들어가 사람을 기다리는 중 |
| `IN_GAME` | 경기 중 |

`IN_LOBBY` 와 `IN_GAME` 을 나눈 것은 **화면 표시를 위한 것입니다.** 초대는 둘 다
막힙니다(7절) — 로비에 있는 사람도 토스트를 보지 못하는 것은 같습니다.

게임 안의 실시간(위치·동작)은 Photon Fusion 이 담당하고, 접속 상태는 이 서버가 들고
있습니다. 근거는 **알림 WebSocket 연결이 살아 있는지**입니다(11절) — 붙어 있으면 온라인,
마지막 연결이 끊기면 오프라인입니다.

> **바뀐 점.** 예전에는 30초마다 `PUT /api/v1/presence` 를 보내야 했습니다. **그 주기
> 호출은 이제 필요 없습니다.** 접속자 천 명이면 초당 33번 들어오던 요청과 트랜잭션이
> 없어지고, 서버가 30초마다 붙어 있는 연결 전체를 `UPDATE` 한 문장으로 갱신합니다. 보내야
> 하는 것은 방을 오갈 때의 한 프레임뿐입니다.

### 규칙

- **주기적으로 보낼 것은 없습니다.** 알림 채널에 붙어 있는 동안 서버가 알아서 온라인으로
  유지합니다.
- 알림 채널에 붙으면(`HELLO_ACK`) `ONLINE` 이 됩니다. 이미 룸 안이던 사람은 그대로
  둡니다 — 경기 중 재접속이 사람을 방에서 끌어내면 안 되니까요.
- 마지막 연결이 끊기면 **즉시** `OFFLINE` 입니다. 90초를 기다리지 않습니다.
- 방을 오갈 때만 알림 채널로 `PRESENCE` 프레임을 보냅니다.
  ```json
  { "type": "PRESENCE", "sessionId": "룸-식별자", "sessionKind": "LOBBY" }
  ```
- `sessionId` 를 안 보내면 `ONLINE` 입니다. 보내면 룸 안이고, 로비인지 경기인지는
  `sessionKind` 가 정합니다 — `LOBBY` 면 `IN_LOBBY`, `MATCH` 면 `IN_GAME`.
- **`sessionKind` 를 생략하면 `MATCH` 로 봅니다.** 이 필드가 생기기 전의 클라이언트가
  지금과 똑같이 동작하도록 한 것입니다. 로비를 로비로 보이게 하려면 반드시 보내세요.
- `sessionId` 가 없으면 `sessionKind` 는 무시합니다. 룸 밖이면 상태는 `ONLINE` 하나입니다.
- 상태를 직접 지정하는 값은 없습니다. 잘못된 조합을 아예 표현할 수 없게 한 것입니다.
- `PUT /api/v1/presence` 와 `DELETE /api/v1/presence` 는 **그대로 남아 있습니다.** 알림
  채널이 끊긴 사이에 방을 옮겼거나 프레임을 아직 쓰지 않는 클라이언트를 위한 것입니다.
  같은 값을 같은 규칙으로 받습니다.

### Fusion 이벤트와 짝짓기

| Fusion 이벤트 | 보낼 프레임 |
| --- | --- |
| 알림 채널 연결 (`HELLO_ACK`) | 없음. 붙은 것만으로 `ONLINE` |
| `OnPlayerJoined` (내가 방에 들어감) | 그 방의 `sessionId` + `sessionKind: "LOBBY"` → `IN_LOBBY` |
| 경기 시작 (로비 씬 → 경기 씬) | **같은** `sessionId` + `sessionKind: "MATCH"` → `IN_GAME` |
| 경기 종료로 로비로 돌아옴 | 같은 `sessionId` + `sessionKind: "LOBBY"` → `IN_LOBBY` |
| 방을 나감 / `OnDisconnectedFromServer` | `sessionId` 없이 → `ONLINE` |
| 앱 종료 (`OnApplicationQuit`) | 없음. 연결이 끊기면 `OFFLINE` |

**`HELLO_ACK` 직후에 룸 안이면 그때 한 번 보내세요.** 재연결이 경기 중에 일어날 수
있고, 서버는 이전 연결에서 무엇을 보고했는지와 지금 어디 있는지를 대조하지 않습니다.

`sessionId` 는 방을 식별하는 문자열이면 됩니다(Fusion 의 세션 이름 등). 64자 이내입니다.

**잘못된 프레임은 조용히 버립니다.** 모르는 `sessionKind`, 너무 긴 `sessionId`, `HELLO`
전에 보낸 `PRESENCE` 는 무시되고 연결은 유지됩니다. 푸시 채널에는 오류를 돌려줄 자리가
없고, 끊어버리면 오타 하나로 실시간 알림 전체를 잃기 때문입니다. **응답이 없으니 성공을
확인할 방법도 없습니다** — 확실히 해야 하면 `PUT` 을 쓰세요. 그쪽은 같은 입력을
`INVALID_REQUEST` 로 되돌립니다.

**경기 시작은 `sessionId` 가 바뀌지 않습니다.** 로비와 경기는 같은 Photon 룸이고 그 룸이
씬을 갈아타는 것뿐이라, 서버가 알아챌 방법은 `sessionKind` 하나입니다. 이 전환 시점에
보내지 않으면 경기 중인 내내 `IN_LOBBY` 로 보입니다.

방을 옮기면 `sessionId` 가 달라집니다. 그냥 새 값으로 보내면 됩니다.

### 크래시하면

프로세스가 죽으면 TCP 도 끊기므로 서버가 알아채고 바로 오프라인으로 내립니다. 네트워크가
조용히 죽는 경우(노트북을 덮거나 Wi-Fi 가 바뀜)는 서버가 30초마다 보내는 ping 이
걷어냅니다. 다만 끊긴 것으로 치는 시점은 전송이 실제로 실패할 때 — TCP 재전송이
포기하거나 5초 전송 제한이나 64KB 버퍼 제한에 걸릴 때 — 라서 30초 안을 보장하지는
않습니다.

**90초**가 걸리는 경우는 둘입니다. 서버 자체가 죽었다 살아난 경우 — 살아 있는 연결이
하나도 없는데 DB 에는 온라인인 행이 남아 있습니다 — 와, 연결이 끊긴 순간의 `OFFLINE`
기록이 DB 오류로 실패한 경우입니다. 둘 다 마지막 하트비트가 90초를 넘기면 스윕이
정리합니다.

## 7. 방 초대

로비에서 친구를 방으로 부르는 흐름입니다. 서버가 하는 일은 **방 코드를 친구에게
건네주는 것뿐**입니다. 그 코드가 가리키는 방이 아직 있는지, 자리가 남았는지, 잠겨
있는지는 전부 Photon 쪽이고 서버는 모릅니다.

### 친구에게만 보낼 수 있습니다

친구가 아니면 `NOT_FRIENDS` 입니다. 화면이 친구 목록에서 부르기도 하지만, 모르는
사람에게 방 코드가 흘러가는 길을 아예 두지 않으려는 것입니다. 요청만 보내둔 상대는
아직 친구가 아닙니다.

**친구를 끊으면 그 사람과 주고받은 초대가 함께 사라집니다.** 남겨두면 끊은 것이 끊은
것이 아닙니다 — 방금 끊은 사람이 이미 받아둔 코드로 그대로 들어옵니다. 양방향으로
지우므로 끊은 뒤에는 받은 초대 목록도 다시 읽으세요. 화면에 남아 있던 초대를 지우는
`DELETE` 는 서버에 이미 없어도 `204` 이고, 그 사람을 다시 부르면 `NOT_FRIENDS` 입니다.

### 방 코드 형식

6자이고, 알파벳은 `0-9A-Z` 에서 **I, O, U, L 을 뺀 32자**입니다. 1과 I, 0과 O 는 눈으로
구분하기 어렵고 코드는 사람이 읽어 옮기는 값이라 아예 넣지 않았습니다. 형식이 맞지
않으면 `INVALID_REQUEST` 입니다.

클라이언트의 `RoomCodeFormat` 과 같은 규칙입니다. 한쪽만 바꾸면 클라이언트가 만든
코드를 서버가 거절하기 시작합니다.

### 초대는 3분 뒤 사라집니다

서버는 Photon 의 방 목록을 몰라서 방이 없어진 것을 알 수 없습니다. 대신 초대 자체에
수명을 둡니다. 로비에서 사람을 기다리는 동안은 유효하고, 경기가 끝난 뒤 남은 초대로
없는 방에 들어가려는 일은 줄어듭니다. **없어지지는 않습니다** — 초대를 눌렀는데 방이
이미 닫혔으면 입장이 `NotFound` 로 실패합니다. 그 실패를 처리해야 합니다.

만료된 초대는 조회에서 이미 빠져 있습니다. 클라이언트가 시각을 보고 거를 필요는
없습니다.

### 받는 방법

초대가 저장되면 상대의 알림 채널로 `ROOM_INVITE_RECEIVED` 가 즉시 나갑니다(11절). 화면은
그 프레임의 `roomCode` 로 토스트를 띄우면 되고, 목록이 필요하면 `GET /api/v1/invites` 를
읽습니다. 목록은 최신 초대가 위입니다. 폴링은 필요 없습니다.

알림 채널이 끊겨 있던 사이에 온 초대는 채널이 다시 붙을 때(`HELLO_ACK`) 목록을 한 번
읽어 메꿉니다. 3분이 지난 것은 이미 빠져 있습니다.

### 게임 중인 친구는 부를 수 없습니다

상대의 접속 상태가 `IN_LOBBY` 나 `IN_GAME` 이면 `409 TARGET_IN_GAME` 입니다. 로비와 경기
중은 서버가 구분하지 않고 둘 다 막습니다. 초대 토스트는 홈과 게임 찾기 화면에서만 뜨기
때문에 지금 보내도 상대가 볼 수 없고, 3분 뒤 조용히 사라질 뿐입니다. 친구 목록의
`presence` 로 미리 버튼을 비활성화하고, 그래도 이 응답이 오면 "게임 중인 친구입니다" 로
안내하세요.

판정은 친구 목록과 같습니다. 알림 채널이 끊긴 상대는 `OFFLINE` 으로 보고 초대를 받아
줍니다.

### 같은 사람을 다시 부르면

새 초대가 생기지 않고 만료 시계만 처음부터 다시 갑니다. 두 번 눌렀다고 상대 목록에
두 개가 뜨지 않습니다. 다만 **다른 방으로 부르면 별개 초대**입니다.

### 없앨 때

`DELETE /api/v1/invites/{userId}` 하나로 거절과 입장 후 정리를 모두 처리합니다.
경로는 초대 식별자가 아니라 **부른 사람의 `userId`** 입니다. 같은 사람이 여러 방으로
불렀다면 함께 사라집니다.

없는 초대를 지워도 `204` 입니다. 만료돼 사라진 초대를 거절하는 경우가 흔하고, 그것은
오류가 아니라 이미 원하는 상태입니다.

## 8. 신고

`POST /api/v1/reports` 로 보냅니다.

```json
{ "userId": "...", "reason": "ABUSE", "memo": "채팅으로 욕설을 했습니다" }
```

### 신고해도 아무 일도 일어나지 않습니다

**이것이 가장 중요한 점입니다.** 차단이 있던 자리지만 성질이 반대입니다.

신고당한 사람은 알 수 없고, 검색에서 사라지지도, 친구 요청이 막히지도 않습니다.
기록으로 남고 사람이 나중에 봅니다. 화면은 "신고했습니다" 만 보여주세요 — 그 이상을
약속하면 거짓말이 됩니다.

### `reason` 은 아래 다섯 중 하나입니다

| 값 | 뜻 |
| --- | --- |
| `ABUSE` | 욕설, 비하, 괴롭힘 |
| `CHEATING` | 부정행위 |
| `SPAM` | 도배, 광고 |
| `INAPPROPRIATE_NAME` | 부적절한 닉네임 |
| `OTHER` | 그 밖 |

목록에 없는 값은 `400 INVALID_REQUEST` 입니다. 값이 늘어날 수는 있으니 클라이언트에서
목록을 하드코딩할 때는 그 점을 감안하세요.

### `memo` 는 선택이고 500자까지입니다

비워도 되고, 생략해도 `""` 로 보내도 같습니다. 넘으면 `400 INVALID_REQUEST` 입니다.
원래 200자였는데 운영자가 메모를 보기 시작하면서 피드백 메시지와 같은 500자로 늘렸습니다.
입력칸의 글자수 제한도 500 으로 맞추세요.

`OTHER` 를 고른 경우에는 메모가 사실상 필수입니다. 서버가 강제하지는 않지만 메모 없는
`OTHER` 는 운영자가 판단할 근거가 없습니다. 화면에서 유도해 주세요.

### 같은 사람을 여러 번 신고할 수 있습니다

막지 않습니다. 그래서 **"이미 신고했습니다" 를 보여줄 수 없습니다** — 서버가 그 상태를
알려주지 않습니다. 자기가 낸 신고를 조회하는 API 도, 취소하는 API 도 없습니다.

### 신고한 뒤 탈퇴해도 그 신고는 남습니다

내가 낸 신고는 내가 탈퇴해도 지워지지 않고, 신고자 정보만 비워집니다. 신고 화면에
"탈퇴하면 취소된다" 같은 설명을 넣지 마세요.

### 친구가 아니어도 신고할 수 있습니다

같은 방에서 만난 사람을 신고하는 것이 주된 쓰임이라 친구 관계를 요구하지 않습니다.
`userId` 만 알면 됩니다.

자기 자신과 없는 사용자는 둘 다 `404 TARGET_NOT_FOUND` 입니다.

## 9. 플레이 로그 전송

`POST /api/v1/events` 에 이벤트 배열을 보냅니다. **무엇을 언제 보내는지는 여기 없습니다.**
그건 [`analytics-events.md`](analytics-events.md) 가 정하고, 이 절은 HTTP 규약만 적습니다.

```json
[{ "occurredAt": 1788750000000, "clientSessionId": "…uuid…", "clientSeq": 0,
   "roomCode": "ABC234", "matchId": null, "matchTimeMs": null, "userPublicId": "…uuid…",
   "eventName": "scene_enter", "phase": null, "mapId": null,
   "posX": null, "posY": null, "posZ": null,
   "fromHost": false, "schemaVer": 1, "params": { "scene": "Lobby" } }]
```

- **`X-User-Id` 헤더를 붙이지 않습니다.** 주체는 이벤트마다 `userPublicId` 로 들어가고, 호스트가
  다른 플레이어를 대신해 보내므로 요청 하나가 한 사람의 것이 아닙니다.
- **`202` 는 "받았다"이지 "저장했다"가 아닙니다.** 응답 본문이 없고, 저장은 서버가 뒤에서 합니다.
- 한 요청에 **200건**까지입니다. 클라이언트는 50건마다 flush 하므로 평소에는 닿지 않습니다.
- `occurredAt` 은 **UTC epoch 밀리초**입니다. 다른 API 의 14자 문자열과 다릅니다.
- `params` 는 JSON 객체여야 하고 2KB 이내입니다. 배열이나 문자열을 넣으면 `400` 입니다.

### 400 은 재전송하지 않습니다

배치 안의 이벤트 하나가 규칙을 어기면 **배치 전체가 `400`** 입니다. 일부만 받으면 무엇이
들어갔는지 알 수 없어 재전송을 판단할 수 없기 때문입니다. `message` 가 `events[3]: …` 처럼
몇 번째가 왜 틀렸는지 말합니다. 400 을 받은 배치는 스풀에서 지우세요. 다시 보내도 같은 답입니다.

거부되는 경우:

- `eventName` 이 명세 목록에 없음
- `occurredAt` 이 **지금-7일 ~ 지금+5분** 밖. 기기 시계가 크게 틀린 경우이고, 그 배치는 잃습니다
- 필수 필드(`occurredAt`, `clientSessionId`, `clientSeq`, `eventName`, `fromHost`, `schemaVer`) 누락
- 배열이 비었거나 200건 초과

### 429 는 재전송합니다

한 IP 에서 분당 600요청을 넘기면 `RATE_LIMITED` 입니다. 클라이언트 하나는 10초마다 한 번
보내므로 혼자서는 닿지 않고, 같은 교실의 수십 명이 공용 IP 하나로 보여도 닿지 않게 잡은
값입니다. 스풀 재전송이 몰릴 때 닿을 수 있는데, 그 배치는 스풀에 그대로 두고 다음 flush 에
다시 보내면 됩니다.

### 같은 이벤트를 두 번 보내도 됩니다

`202` 를 받지 못한 배치를 스풀에서 다시 보내면 서버가 `(clientSessionId, clientSeq, occurredAt)`
으로 중복을 알아보고 조용히 버립니다. **그래서 `clientSeq` 는 재전송해도 같은 값이어야 합니다.**
스풀에 쓸 때 이미 붙어 있어야 합니다.

## 10. 계정 삭제

`DELETE /api/v1/accounts/me` 는 **되돌릴 수 없습니다.** 계정과 함께 친구 관계와 접속
기록이 모두 사라집니다. 복구 수단이 없으니 확인 화면을 반드시 두세요.

`X-User-Id` 와 `X-Device-Id` 를 함께 보냅니다. 자격증명이 맞지 않으면 `404
ACCOUNT_NOT_FOUND` 입니다 — 남의 계정이 존재하는지 알 수 없게 하려고 실패를 구분하지
않습니다.

삭제한 뒤 같은 기기로 다시 발급받으면 **새 계정**이 생깁니다. 닉네임도 다시 쓸 수 있게
풀립니다.

**그 사람에 대한 신고**는 함께 사라집니다. 볼 대상이 없기 때문입니다.

**그 사람이 낸 신고**는 남고 신고자만 비워집니다. 신고는 신고당한 사람에 대한 기록이지
신고자에 대한 기록이 아니라서, 목격자가 떠났다고 제3자에 대한 진술을 없애지 않습니다.

## 11. 실시간 알림

친구 요청과 방 초대는 저장되는 순간 상대에게 **WebSocket 으로 밀어줍니다.** 폴링은 필요
없습니다. 주소는 `wss://j15d205.p.ssafy.io/ws/notifications` 이고, 로컬은
`ws://localhost:8080/ws/notifications` 입니다. HTTP 의 `https` 를 `wss` 로 바꾸면 됩니다.

### 붙는 순서

1. 연결을 연다.
2. 첫 프레임으로 자기를 밝힌다. 헤더가 아니라 프레임인 이유는 브라우저 WebSocket 이 헤더를
   붙일 수 없기 때문입니다. `token` 은 REST 의 `X-Account-Token` 과 같은 값입니다.
   ```json
   { "type": "HELLO", "userId": "...", "token": "..." }
   ```
3. 서버가 `{ "type": "HELLO_ACK" }` 를 돌려준다. **이때가 "연결됨"입니다.** 이 시점에 친구
   목록, 받은 요청, 받은 초대를 한 번 전체 조회해서 끊겨 있던 사이 놓친 것을 메꿉니다.
   연결이 열린 시점을 쓰면 서버가 아직 나를 모르는 사이에 온 알림을 놓칩니다.
4. **룸 안이면 그때 `PRESENCE` 프레임을 한 번 보낸다**(6절). 붙은 것만으로는 `ONLINE` 이라
   서, 경기 중에 재연결한 경우 이 프레임이 없으면 친구들에게 부를 수 있는 사람으로 보입니다.

연결 뒤 5초 안에 HELLO 가 없으면 서버가 끊습니다(close 1008, 사유 `HELLO_TIMEOUT`). `token`
이 없거나 그 `userId` 의 것이 아니면 같은 코드로 끊고(`UNAUTHORIZED`), 모르는 `userId` 도
그렇습니다(`UNKNOWN_USER`). 두 번째 HELLO 는 무시합니다.

### 클라이언트가 보내는 프레임

`HELLO` 와 `PRESENCE` 둘입니다. `PRESENCE` 는 방을 오갈 때 보내고, 값과 규칙은 6절에
있습니다. **둘 다 응답이 없습니다**(`HELLO` 만 `HELLO_ACK` 를 받습니다) — 모르는 `type`,
모르는 값, 순서가 틀린 프레임은 조용히 버려지고 연결은 유지됩니다.

### 서버가 보내는 프레임

전부 같은 모양입니다.

```json
{ "type": "ROOM_INVITE_RECEIVED", "sentAt": "20260908123000",
  "from": { "userId": "...", "nickname": "..." }, "roomCode": "7K2M9P" }
```

| `type` | 언제 | 받으면 할 일 |
| --- | --- | --- |
| `FRIEND_REQUEST_RECEIVED` | 누가 나에게 친구 요청을 보냄 | 홈이면 토스트. 받은 요청 목록을 다시 읽습니다 |
| `FRIEND_REQUEST_ACCEPTED` | 내가 보낸 요청을 상대가 수락 | 친구 목록과 보낸 요청 목록을 다시 읽습니다 |
| `FRIEND_REQUEST_REMOVED` | 상대가 거절했거나 취소함. 어느 쪽인지는 알려주지 않습니다 | 받은·보낸 요청 목록을 다시 읽습니다 |
| `FRIEND_REMOVED` | 상대가 친구를 끊음. 둘 사이의 방 초대도 함께 지워집니다 | 친구 목록과 받은 초대 목록을 다시 읽습니다 |
| `ROOM_INVITE_RECEIVED` | 친구가 나를 방으로 부름. 같은 방으로 다시 부른 갱신도 포함 | 홈이면 토스트. `roomCode` 로 입장합니다 |

`roomCode` 는 방 초대에만 있고 나머지는 `null` 입니다. `sentAt` 은 다른 API 와 같은
`yyyyMMddHHmmss` UTC 입니다. **모르는 `type` 은 무시하세요.** 서버가 종류를 더해도 옛
클라이언트가 깨지지 않아야 합니다.

**알림은 신호이고 목록의 진실은 REST 입니다.** 프레임 하나를 놓쳐도 다음 프레임이나
재연결 때 목록을 읽으면 같은 곳에 도착합니다. 그래서 서버는 붙어 있지 않은 사람에게 갈
알림을 보관하지 않고 버립니다.

### 끊김과 재연결

- 서버가 30초마다 ping 을 보냅니다. 브라우저와 .NET 은 pong 을 자동으로 돌려주므로 할 일이
  없습니다.
- 끊기면 1초부터 시작해 두 배씩 늘리며 최대 30초 간격으로 다시 붙으세요. 지터를 섞어야
  서버가 재시작할 때 전부가 같은 순간에 몰리지 않습니다.
- 다시 붙으면 HELLO 부터 다시 합니다. `HELLO_ACK` 를 받으면 위의 전체 조회를 또 하고,
  룸 안이면 `PRESENCE` 도 다시 보냅니다.
- **끊겨 있는 동안 친구들에게 오프라인으로 보입니다.** 이 채널이 접속 상태의 근거이기
  때문입니다(6절). 그래서 재연결을 오래 미루지 마세요.

### 어디서 띄우나

토스트는 **홈과 게임 찾기 화면에서만** 띄웁니다. 로비와 경기 중에는 채널은 그대로 두되
목록만 갱신하고 토스트는 내지 않습니다. 게임 중인 사람은 초대를 받을 수 없으므로(7절)
로비에서 초대 프레임이 오는 일은 없고, 친구 요청은 홈으로 돌아왔을 때 배지로 봅니다.

## 12. 피드백

`POST /api/v1/feedback` 으로 보냅니다. 설정 화면의 "피드백 보내기" 가 부르는 자리입니다.

```json
{ "message": "숨는 시간이 너무 짧아요", "buildVer": "1.4.2", "platform": "WebGL" }
```

`X-User-Id` 헤더가 필요합니다. 없으면 `400 MISSING_HEADER`, 가리키는 계정이 없으면
`404 ACCOUNT_NOT_FOUND` 입니다. 익명으로는 받지 않습니다 — 같은 사람이 열 번 보낸 것과
열 명이 보낸 것을 구분할 수 없으면, 읽는 사람에게 가장 중요한 정보가 사라집니다.

### 답장은 없습니다

`201` 은 **적어 뒀다**는 뜻이고 읽고 답하겠다는 뜻이 아닙니다. 답을 보낼 경로(메일·알림)가
없으므로 화면에서 "답변을 드립니다" 같은 문구를 쓰지 마세요. 자기가 보낸 피드백을 조회하는
API 도, 취소하는 API 도 없습니다.

### `message` 는 500자까지입니다

**화면 상한과 서버 상한이 같습니다.** 화면에서 500자를 꽉 채워 쓴 글이 서버에서 거절되는
일은 없습니다. 501자부터 `400 INVALID_REQUEST` 이고, 공백만 있는 것도 같은 400 입니다.
앞뒤 공백과 꼬리 줄바꿈은 서버가 떼고 저장하므로 화면이 미리 다듬지 않아도 됩니다.

이모지가 섞여도 500자는 글자 수입니다. 바이트가 아닙니다.

### `buildVer` 와 `platform` 은 선택이지만 넣어 주세요

둘 다 없어도 받습니다(생략해도 `""` 로 보내도 같습니다). 다만 이 값이 없으면 "튕깁니다"
라는 피드백을 받아도 **재현할 빌드를 알 수 없습니다.** `buildVer` 는 32자, `platform` 은
16자까지이고 값의 목록을 서버가 정해두지 않았습니다. 플랫폼 이름이 늘어나도 400 이 되지
않게 하려는 것입니다.

### 보낸 뒤 탈퇴하면 내용은 남습니다

작성자 정보만 비워지고 본문은 남습니다. 신고와 같습니다. "탈퇴하면 없어진다" 같은 설명을
넣지 마세요.

### 실패했을 때 입력을 지우지 마세요

전송이 실패했는데 입력창을 비우면 플레이어가 애써 쓴 글이 사라집니다. 4xx 든 5xx 든
내용을 그대로 두고 다시 보낼 수 있게 하세요. 지금 화면이 전송 준비 전에도 그렇게 하고
있습니다.
