# 클라이언트 연동 안내

Unity 클라이언트가 이 백엔드를 붙일 때 알아야 하는 규약입니다.

**엔드포인트 목록은 여기 없습니다.** 그건 [`openapi.json`](openapi.json)에 있고 코드에서
자동 생성됩니다. 이 문서에는 명세가 표현할 수 없는 것만 적습니다 — 왜 그렇게 되어 있는지,
어떤 순서로 불러야 하는지, 값의 형식이 무엇인지.

명세를 눌러보면서 확인하려면 백엔드를 로컬에 띄우고 `http://localhost:8080/swagger-ui.html`
로 갑니다. **운영 서버는 Swagger 를 열지 않습니다.** 지금 API 에 인증이 없어서, 운영에서
서빙하는 Swagger UI 는 아무나 열어서 운영 DB 에 쓸 수 있는 버튼이 됩니다.

기대 응답까지 적어둔 요청 모음은 [`../http/accounts.http`](../http/accounts.http) 에
있습니다(VS Code REST Client). 전수가 아니라 눌러볼 만한 것만 있습니다.

## 1. 주소

| 대상 | 주소 |
| --- | --- |
| 로컬 | `http://localhost:8080` |
| 운영 | `https://j15d205.p.ssafy.io` |

살아 있는지 확인: `GET /actuator/health` → `{"status":"UP"}`

## 2. 식별과 인증은 다릅니다

거의 모든 요청에 `X-User-Id` 헤더를 넣습니다. 계정 발급 응답에서 받은 `userId` 입니다.

**이건 인증이 아니라 식별입니다.** 남의 `userId` 를 아는 사람은 그 사람인 척 요청할 수
있습니다. 지금은 그게 허용된 상태이고, 로그인을 붙이는 시점에 바뀝니다. 클라이언트는
`userId` 를 비밀로 다룰 필요가 없지만, **화면에 남의 `userId` 를 노출하지는 마세요.**

되돌릴 수 없는 연산만 실제 자격증명을 함께 요구합니다. 현재는 계정 삭제 하나이고
`X-Device-Id` 를 받습니다.

---

## 3. `deviceId` 는 자격증명입니다

계정은 기기 식별자로 발급받습니다. 그 값이 곧 그 계정의 비밀번호에 해당합니다.

지켜야 할 것:

- **응답에 절대 나오지 않습니다.** 어떤 API 응답에서도 `deviceId` 를 읽을 수 없습니다.
  테스트가 그걸 검증합니다. 클라이언트가 직접 저장해 두어야 합니다.
- **로그에 남기지 마세요.** 서버도 남기지 않습니다.
- **쿼리 파라미터로 보내지 마세요.** nginx 접근 로그에 남습니다. 헤더나 본문으로 보냅니다.
- 기기에 안전하게 보관합니다. 이 값을 잃으면 **그 계정으로 돌아갈 방법이 없습니다.**

### 발급은 멱등합니다

같은 `deviceId` 로 다시 부르면 새 계정이 생기지 않고 기존 계정이 돌아옵니다.
`201` 이면 새로 만든 것, `200` 이면 원래 있던 것입니다. 그래서 앱을 켤 때마다 그냥 불러도
됩니다 — 응답을 못 받아 재시도하는 경우에도 계정이 하나로 유지됩니다.

### 임시 닉네임

발급 시 서버가 닉네임을 지어 줍니다. 응답의 `nicknameSet` 이 `false` 면 아직 임시입니다.
**첫 실행에서 닉네임 입력 화면을 띄울지 판단하는 값입니다.** 이름 자체를 비교하지 마세요.

닉네임은 **대소문자를 구분합니다.** `player` 와 `Player` 는 서로 다른 이름이라 둘 다
존재할 수 있습니다. 중복 확인을 클라이언트에서 대소문자 무시로 하면 서버 결과와 어긋납니다.

## 4. 시각 형식

시각은 모두 **`yyyyMMddHHmmss` 형식의 14자 문자열이고 UTC** 입니다. `20260903142530` 처럼
옵니다. ISO 8601 이 아니고, 타임존 정보가 문자열에 없습니다.

```csharp
// UTC 로 명시해서 파싱해야 합니다. 안 하면 기기 로컬 시간으로 읽혀 9시간 어긋납니다.
DateTime.ParseExact(createdAt, "yyyyMMddHHmmss", CultureInfo.InvariantCulture,
                    DateTimeStyles.AssumeUniversal | DateTimeStyles.AdjustToUniversal);
```

화면에 보일 때는 `.ToLocalTime()` 을 거칩니다.

## 5. 오류 응답

실패는 항상 같은 형태입니다.

```json
{ "code": "ACCOUNT_NOT_FOUND", "message": "계정을 찾을 수 없습니다." }
```

**`code` 로 분기하세요.** `message` 는 사람이 읽는 용도이고 문구가 바뀔 수 있습니다.

| `code` | HTTP | 언제 | 클라이언트가 할 일 |
| --- | --- | --- | --- |
| `MISSING_HEADER` | 400 | 필수 헤더가 없음 | 버그입니다. 헤더를 확인하세요 |
| `INVALID_REQUEST` | 400 | 값이 형식에 안 맞음 | 입력값을 고쳐 다시 보냅니다 |
| `SELF_FRIEND_REQUEST` | 400 | 자기에게 친구 요청 | UI 에서 미리 막습니다 |
| `ACCOUNT_NOT_FOUND` | 404 | 부르는 사람의 계정이 없음 | **계정을 다시 발급받아야 합니다** |
| `TARGET_NOT_FOUND` | 404 | 상대를 찾을 수 없음 | "그 사용자가 없습니다" |
| `FRIEND_REQUEST_NOT_FOUND` | 404 | 그 요청이 없음 | 목록을 다시 불러옵니다 |
| `NOT_FRIENDS` | 404 | 친구가 아님 | 목록을 다시 불러옵니다 |
| `NICKNAME_TAKEN` | 409 | 닉네임이 이미 쓰임 | 다른 이름을 받습니다 |
| `ALREADY_FRIENDS` | 409 | 이미 친구 | 목록을 다시 불러옵니다 |
| `REQUEST_ALREADY_SENT` | 409 | 이미 보낸 요청 | 목록을 다시 불러옵니다 |
| `CONFLICT` | 409 | 동시 요청이 겹침 | 다시 시도하면 대개 됩니다 |
| `NICKNAME_GENERATION_FAILED` | 500 | 서버가 임시 닉네임을 못 만듦 | 서버 문제입니다. 재시도 |

`ACCOUNT_NOT_FOUND` 와 `TARGET_NOT_FOUND` 를 나눈 이유가 대응이 다르기 때문입니다.
전자는 내 계정이 사라진 것이라 발급부터 다시 해야 하고, 후자는 화면에 메시지만 띄우면
됩니다.

## 6. 접속 상태

친구 목록의 `presence` 는 `OFFLINE` / `ONLINE` / `IN_GAME` 셋 중 하나입니다.

서버는 **실시간 통신을 하지 않습니다.** Photon Fusion 이 실시간을 담당하고, 서버는
클라이언트가 보내는 하트비트로만 상태를 압니다. 그래서 하트비트를 안 보내면 친구 목록에서
계속 오프라인으로 보입니다.

### 규칙

- 하트비트는 **30초마다** 보냅니다.
- 서버는 마지막 하트비트가 **90초** 넘으면 오프라인으로 봅니다. 30초 주기면 두 번
  놓쳐도 버팁니다.
- `sessionId` 를 함께 보내면 `IN_GAME`, 안 보내면 `ONLINE` 입니다. 상태를 직접 지정하는
  값은 없습니다 — 방에 있으면 게임 중입니다.
- 게임을 끄기 전에 **`DELETE /api/v1/presence`** 를 부릅니다. 그러면 즉시 오프라인이 되고,
  친구들이 90초 동안 유령을 보지 않습니다.

### Fusion 이벤트와 짝짓기

주기 하트비트만으로는 상태 전환이 최대 30초 늦습니다. Fusion 이벤트에서 한 번 더 보내면
즉시 반영됩니다.

| Fusion 이벤트 | 보낼 것 |
| --- | --- |
| `OnConnectedToServer` | `sessionId` 없이 → `ONLINE` |
| `OnPlayerJoined` (내가 방에 들어감) | 그 방의 `sessionId` → `IN_GAME` |
| 방을 나감 / `OnDisconnectedFromServer` | `sessionId` 없이 → `ONLINE` |
| 앱 종료 (`OnApplicationQuit`) | `DELETE /api/v1/presence` |

`sessionId` 는 방을 식별하는 문자열이면 됩니다(Fusion 의 세션 이름 등). 64자 이내이고,
넘으면 `INVALID_REQUEST` 입니다.

방을 옮기면 같은 `IN_GAME` 이지만 `sessionId` 가 달라집니다. 그냥 새 값으로 보내면 됩니다.

### 크래시하면

강제 종료되면 `DELETE` 를 못 보냅니다. 그때는 90초 뒤에 자동으로 오프라인이 됩니다.
친구 목록을 조회하는 시점에도 판정하므로, 스윕을 기다리지 않고 바로 오프라인으로 보입니다.

## 7. 방 초대

로비에서 친구를 방으로 부르는 흐름입니다. 서버가 하는 일은 **방 코드를 친구에게
건네주는 것뿐**입니다. 그 코드가 가리키는 방이 아직 있는지, 자리가 남았는지, 잠겨
있는지는 전부 Photon 쪽이고 서버는 모릅니다.

### 친구에게만 보낼 수 있습니다

친구가 아니면 `NOT_FRIENDS` 입니다. 화면이 친구 목록에서 부르기도 하지만, 모르는
사람에게 방 코드가 흘러가는 길을 아예 두지 않으려는 것입니다. 요청만 보내둔 상대는
아직 친구가 아닙니다.

**친구를 끊으면 그 사람과 주고받은 초대가 함께 사라집니다.** 남겨두면 끊은 것이 끊은
것이 아닙니다 — 방금 끊은 사람이 이미 받아둔 코드로 그대로 들어옵니다. 끊은 뒤에
초대 목록을 다시 부를 필요는 없지만, 화면에 남아 있던 초대가 서버에는 이미 없으므로
누르면 `NOT_FOUND` 가 옵니다.

### 방 코드 형식

6자이고, 알파벳은 `0-9A-Z` 에서 **I, O, U, L 을 뺀 32자**입니다. 1과 I, 0과 O 는 눈으로
구분하기 어렵고 코드는 사람이 읽어 옮기는 값이라 아예 넣지 않았습니다. 형식이 맞지
않으면 `INVALID_REQUEST` 입니다.

클라이언트의 `RoomCodeFormat` 과 같은 규칙입니다. 한쪽만 바꾸면 클라이언트가 만든
코드를 서버가 거절하기 시작합니다.

### 초대는 3분 뒤 사라집니다

서버는 Photon 의 방 목록을 몰라서 방이 없어진 것을 알 수 없습니다. 대신 초대 자체에
수명을 둡니다. 로비에서 사람을 기다리는 동안은 유효하고, 경기가 끝난 뒤 남은 초대로
없는 방에 들어가려는 일은 줄어듭니다. **없어지지는 않습니다** — 초대를 눌렀는데 방이
이미 닫혔으면 입장이 `NotFound` 로 실패합니다. 그 실패를 처리해야 합니다.

만료된 초대는 조회에서 이미 빠져 있습니다. 클라이언트가 시각을 보고 거를 필요는
없습니다.

### 받는 방법

서버는 실시간 통신을 하지 않으므로 **초대를 밀어주지 못합니다.** 로비에 있는 동안
`GET /api/v1/invites` 를 주기적으로 부르세요. 접속 상태 하트비트와 같은 주기(30초)면
충분합니다. 목록은 최신 초대가 위입니다.

### 같은 사람을 다시 부르면

새 초대가 생기지 않고 만료 시계만 처음부터 다시 갑니다. 두 번 눌렀다고 상대 목록에
두 개가 뜨지 않습니다. 다만 **다른 방으로 부르면 별개 초대**입니다.

### 없앨 때

`DELETE /api/v1/invites/{userId}` 하나로 거절과 입장 후 정리를 모두 처리합니다.
경로는 초대 식별자가 아니라 **부른 사람의 `userId`** 입니다. 같은 사람이 여러 방으로
불렀다면 함께 사라집니다.

없는 초대를 지워도 `204` 입니다. 만료돼 사라진 초대를 거절하는 경우가 흔하고, 그것은
오류가 아니라 이미 원하는 상태입니다.

## 8. 신고

`POST /api/v1/reports` 로 보냅니다.

```json
{ "userId": "...", "reason": "ABUSE", "memo": "채팅으로 욕설을 했습니다" }
```

### 신고해도 아무 일도 일어나지 않습니다

**이것이 가장 중요한 점입니다.** 차단이 있던 자리지만 성질이 반대입니다.

신고당한 사람은 알 수 없고, 검색에서 사라지지도, 친구 요청이 막히지도 않습니다.
기록으로 남고 사람이 나중에 봅니다. 화면은 "신고했습니다" 만 보여주세요 — 그 이상을
약속하면 거짓말이 됩니다.

### `reason` 은 아래 다섯 중 하나입니다

| 값 | 뜻 |
| --- | --- |
| `ABUSE` | 욕설, 비하, 괴롭힘 |
| `CHEATING` | 부정행위 |
| `SPAM` | 도배, 광고 |
| `INAPPROPRIATE_NAME` | 부적절한 닉네임 |
| `OTHER` | 그 밖 |

목록에 없는 값은 `400 INVALID_REQUEST` 입니다. 값이 늘어날 수는 있으니 클라이언트에서
목록을 하드코딩할 때는 그 점을 감안하세요.

### `memo` 는 선택이고 200자까지입니다

비워도 되고, 생략해도 `""` 로 보내도 같습니다. 넘으면 `400 INVALID_REQUEST` 입니다.

`OTHER` 를 고른 경우에는 메모가 사실상 필수입니다. 서버가 강제하지는 않지만 메모 없는
`OTHER` 는 운영자가 판단할 근거가 없습니다. 화면에서 유도해 주세요.

### 같은 사람을 여러 번 신고할 수 있습니다

막지 않습니다. 그래서 **"이미 신고했습니다" 를 보여줄 수 없습니다** — 서버가 그 상태를
알려주지 않습니다. 자기가 낸 신고를 조회하는 API 도, 취소하는 API 도 없습니다.

### 신고한 뒤 탈퇴해도 그 신고는 남습니다

내가 낸 신고는 내가 탈퇴해도 지워지지 않고, 신고자 정보만 비워집니다. 신고 화면에
"탈퇴하면 취소된다" 같은 설명을 넣지 마세요.

### 친구가 아니어도 신고할 수 있습니다

같은 방에서 만난 사람을 신고하는 것이 주된 쓰임이라 친구 관계를 요구하지 않습니다.
`userId` 만 알면 됩니다.

자기 자신과 없는 사용자는 둘 다 `404 TARGET_NOT_FOUND` 입니다.

## 9. 계정 삭제

`DELETE /api/v1/accounts/me` 는 **되돌릴 수 없습니다.** 계정과 함께 친구 관계와 접속
기록이 모두 사라집니다. 복구 수단이 없으니 확인 화면을 반드시 두세요.

`X-User-Id` 와 `X-Device-Id` 를 함께 보냅니다. 자격증명이 맞지 않으면 `404
ACCOUNT_NOT_FOUND` 입니다 — 남의 계정이 존재하는지 알 수 없게 하려고 실패를 구분하지
않습니다.

삭제한 뒤 같은 기기로 다시 발급받으면 **새 계정**이 생깁니다. 닉네임도 다시 쓸 수 있게
풀립니다.

**그 사람에 대한 신고**는 함께 사라집니다. 볼 대상이 없기 때문입니다.

**그 사람이 낸 신고**는 남고 신고자만 비워집니다. 신고는 신고당한 사람에 대한 기록이지
신고자에 대한 기록이 아니라서, 목격자가 떠났다고 제3자에 대한 진술을 없애지 않습니다.
