# 채팅 정화와 기록

로비와 인게임 채팅에서 금칙어를 가려 내보내고, 신고가 들어왔을 때 확인할 수 있게 원문을 짧게
보관합니다(S15P21D205-1026).

**분석 수집과 다른 것입니다.** 분석(`d205_analytics`)은 익명 집계용이라 장애 격리로 컨테이너와 DB를
분리했고 채팅을 담지 않습니다. 채팅은 신고·정지와 조인해야 뜻이 생기는 운영 데이터라 계정 서비스
DB에 담습니다. 두 개를 뭉뚱그리면 "분석에 채팅이 있다"는 오해가 생깁니다.

## 흐름

```
방 서버 기동 → GET /internal/chat/blocklist → 목록을 메모리에

메시지마다 → 게임 서버가 중계하면서
             ├─ 들고 있는 목록으로 판정 → 가린 문장을 전원에게 브로드캐스트
             └─ 원문을 2.5초 묶음으로 POST /internal/chat  (응답을 기다리지 않음)

신고가 오면 → 신고 상세의 경기 키 → 그 방 그 시간대 대화
```

**판정을 게임 서버가 로컬로 합니다.** 메시지마다 백엔드에 묻는 방식도 검토했는데, 채팅 전달이
백엔드 생사에 묶이고 응답 순서가 뒤바뀌면 대화 줄이 뒤집힙니다. 목록을 기동 때 한 번 받아 두면
지연이 없고 백엔드가 죽어도 채팅은 평소대로 돕니다. 그동안 필터와 기록만 빠집니다.

**목록 갱신은 따로 할 일이 없습니다.** 방 서버는 방이 빈 뒤 120초에 스스로 종료하고 release host가
새로 띄웁니다. 백엔드에서 `chat-blocklist.txt`만 바꿔 재기동하면 그다음에 열리는 방부터 새 목록입니다.

## 경로를 잠그는 이유

`/internal/**`은 **nginx에 없습니다.** 계정 서비스가 `127.0.0.1:8080`에만 바인딩돼 있어 같은 EC2의
게임 서버만 닿고, 그 위에 공유 키(`CHAT_INTERNAL_KEY`)가 있습니다. 키가 없거나 틀리면 **404**입니다 —
401이나 403은 "여기 무언가 있다"를 알려주는 셈입니다. 공개 명세(`docs/openapi.json`)에서도 뺐습니다.
404로 숨겨 놓고 명세에 주소를 실으면 숨긴 의미가 없습니다.

잠그지 않으면 두 가지가 깨집니다. 목록을 아무나 받아 가면 그것이 곧 우회 목록이 되고, 채팅을
아무나 올릴 수 있으면 남의 이름으로 가짜 대화를 심어 누명을 씌울 수 있습니다. **위조 가능한 기록은
없는 것보다 나쁩니다.**

키는 `INTERNAL_KEY`와 나눕니다. 그쪽은 계정 서비스가 분석 서비스를 부를 때 내미는 값이라, 같은
값을 게임 서버에 주면 분석 쪽 내부 경로(탈퇴 익명화)까지 열 수 있게 됩니다. 그리고 게임 서버에는
명령줄이 아니라 `D205_CHAT_KEY` 환경변수로 넘깁니다. 명령줄 인자는 같은 장비의 누구나 `ps`로 읽습니다.

## 무엇을 담는가

`chat_logs` 한 표입니다(V21).

| 칸 | 뜻 |
| --- | --- |
| `room_code` | 어느 방. 신고의 `context_key`에서 `#` 앞과 같은 값 |
| `scope` | `LOBBY` 또는 `MATCH` |
| `sender_seq` | 말한 사람. 탈퇴하면 FK가 NULL로 만듭니다 |
| `sender_ref` | 그 방에서만 뜻이 있는 발화자 표식 |
| `message` | **가리기 전의 원문** |
| `masked` | 금칙어에 걸렸는가. 저장할 때 백엔드가 다시 판정 |
| `sent_at` | 게임 서버가 찍은 시각 |

**원문을 담습니다.** 가린 것만 남기면 조사가 되지 않습니다. 그래서 오래 두지 않습니다.

**닉네임은 담지 않습니다.** 바뀌는 값이라 조회할 때 붙입니다.

**`masked`는 게임 서버가 보낸 값을 믿지 않습니다.** 게임 서버가 들고 있는 목록은 낡을 수 있으므로
저장 시점에 백엔드가 자기 목록으로 다시 판정합니다.

`sender_ref`가 필요한 경우는 좁습니다. 계정은 기기 기반으로 자동 발급되고 계정 없이는 Photon이
접속을 막으므로 보통은 `sender_seq`가 있습니다. 비는 경우는 백엔드가 죽어 있을 때 저장된
크리덴셜로 들어온 클라이언트(S15P21D205-925)와 탈퇴한 사람뿐입니다. 그때 대화록이 "알 수 없음"
여러 줄로 뭉개지면 읽을 수 없으므로, 누구인지는 몰라도 발화자는 구분되게 합니다.

## 얼마나 두는가

**기본 3일**입니다. 신고는 대개 경기 직후에 들어오므로 그 안에 확인이 끝납니다. 청소는 한 시간마다
돌고, 멈추면 개인정보가 무한정 쌓입니다.

**아직 판단하지 않은 신고가 가리키는 구간은 남깁니다.** 근거를 지우면 신고만 남고 판단은 못 합니다.
지킬 구간은 신고의 `context_key`에서 방 코드를 떼어 신고 시각 앞뒤로 잡으며, 폭은 관리 화면이 열 수
있는 가장 넓은 값과 같습니다. 좁게 잡으면 운영자가 넓혀 읽던 줄이 다음 청소에 사라집니다.

검토가 끝난 신고는 지키지 않습니다. 정지까지 간 건의 근거는 정지 사유에 옮겨 적는 것으로 남깁니다.

`context_key`가 없는 옛 신고는 어느 방인지 알 수 없어 지킬 수 없습니다. 지금 클라이언트는 항상
보냅니다.

## 신고와 어떻게 잇는가

**`context_key`를 조인 키로 쓰지 않습니다.** `7K2M9P#2`의 `#2`는 각 피어가 자기가 본 경기 수를 센
값이라, 늦게 들어온 사람은 같은 경기에 다른 번호를 붙입니다. 전역 식별자가 아닙니다. `#` 앞의 방
코드와 시각 구간으로 찾습니다.

정확한 조인이 필요해지면 서버가 경기 시작 때 경기 id를 전원에게 내려주고 신고에 함께 싣는 방식으로
올립니다. 클라이언트·게임 서버·백엔드 세 곳이 바뀝니다.

## 운영 주의

**채팅 본문을 로그에 남기지 마세요.** 3일 삭제가 의미를 가지려면 채팅이 저장되는 곳이 이 표
하나여야 합니다. 애플리케이션 로그나 요청 로그로 흘리면 그쪽은 지워지지 않습니다. 디버깅이
필요하면 건수나 방 코드만 남깁니다.

**대화 조회는 운영자 인증이 걸린 경로입니다.** 채팅 원문은 개인정보이고 그 화면은 사람 이름과 함께
펼쳐 보여줍니다.

## 설정

| 이름 | 곳 | 기본 |
| --- | --- | --- |
| `CHAT_INTERNAL_KEY` | 계정 서비스 `.env` | 없음. 비면 `/internal`이 전부 404 |
| `chat_internal_key` | release host 설정 | 없음. 비면 게임 서버에 키를 넘기지 않음 |
| `internal_api_origin` | release host 설정 | `http://127.0.0.1:8080` |
| `chat.retention-days` | 계정 서비스 | 3 |
| `chat.protect-window-minutes` | 계정 서비스 | 180 |
| `chat.sweep-interval-ms` | 계정 서비스 | 3600000 (한 시간) |

앞의 둘은 **같은 값**이어야 합니다. 다르면 게임 서버가 404를 받고 필터 없이 뜹니다. 그때 게임 서버
로그에 경고가 남습니다.

## 아직 없는 것

**이용자 고지가 저장소에 없습니다.** 게임 화면에도 문서에도 "무엇을 언제까지 왜 보관하는지" 적은
곳이 없습니다. 채팅 원문을 담기 시작했으므로 어디에 적을지 정하고 적어야 합니다 — 최소한 원문을
담는다는 것, 3일이라는 기간, 신고가 접수되면 처리가 끝날 때까지 남는다는 것, 탈퇴하면 발신자
연결이 끊어진다는 것입니다.
