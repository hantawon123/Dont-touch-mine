# 플레이 로그 수집 부하 테스트 (863)

"수집을 별도 서비스로 나누지 않아도 되는가"를 말이 아니라 숫자로 답합니다. 이벤트 배치를 초당
N건 쏘면서 **같은 앱의 게임 API 응답 시간**을 함께 재고, N 을 올려 어디서 무너지는지 찾았습니다.

**결론부터.** 기준선(초당 300 이벤트, 실제 예상 부하의 4배 이상)의 40배인 초당 12,000 이벤트까지 올려도 게임 API p99 는 15ms 안팎으로
변하지 않았습니다. 수집이 밀리면 큐가 넘쳐 이벤트를 버릴 뿐 게임은 모릅니다. 상한 큐 설계가
약속대로 동작합니다. 첫 측정에서 드러난 한계는 자원이 아니라 플러셔가 한 주기에 배치 하나만 넣는
구조였고, 그것을 고친 뒤 다시 잰 것이 2차입니다.

---

## 조건

| 항목 | 값 |
| --- | --- |
| 날짜 | 2026-09-07 |
| 어디서 | 개발 PC (22 코어). 운영 EC2 가 아닙니다. Jenkins 와 경합하고 운영 테이블에 가짜 행이 쌓이기 때문입니다 |
| 서버 | `./gradlew bootRun`, local 프로필. `ANALYTICS_RATE_LIMIT_PER_MINUTE=100000000` 으로 레이트 리밋만 끔 |
| DB | `compose.local.yml` 의 MySQL 8.4 컨테이너, 새 볼륨 |
| 클라이언트 | `loadtest/events_load.py` (Python 표준 라이브러리). 요청 1건 = 이벤트 50건. 이벤트의 85%가 호스트 발행이고 그중 17/22 가 `position_sample` 이라 전체의 약 66%가 `position_sample` |
| 게임 API 프로브 | `GET /api/v1/accounts/me` 초당 5회, 부하와 무관하게 계속 |
| 단계 | 60초씩. 0(기준선) → 6 → 30 → 60 → 120 → 240 req/s |

**테스트의 1× 기준선은 6 req/s, 초당 300 이벤트** 입니다. 동시 60명이 10초마다 한 번 보내면 6 req/s 이고,
테스트는 요청마다 flush 상한인 50건을 가득 채워 보냅니다. 실제 예상 부하는 그보다 작습니다. 경기당
약 2,600행을 경기 길이 6~8분(기본 설정으로 숨기기 180초 + 찾기 300초, 물건이 먼저 다 발견되면 더 짧음)·
6명으로 나누면 한 사람이 초당 약 1 이벤트를 만들고, 동시 60명이면 초당 55~72 이벤트, 즉 요청당 10건
안팎입니다. 그래서 **1× 기준선은 실제 예상의 약 4~5배**로 보수적입니다. 아래 표의 "기준선 대비"는 이
300 이벤트/초에 대한 배수이고, 실제 예상 부하 대비로 읽으려면 4배 이상을 더 곱합니다.

레이트 리밋을 끈 이유: 한 PC 에서 쏘므로 IP 하나입니다. 운영값(분당 600)이면 10 req/s 부터 429 라
그 위를 잴 수 없습니다. 이 테스트가 보려는 것은 큐·플러셔·DB 이고, 레이트 리밋은 별도 테스트
(`GameEventQueueTest`)가 봅니다.

## 1차: 플러셔가 한 주기에 배치 하나

| req/s | events/s | 기준선 대비 | 202 | 실패 | 수집 p99 | 게임 p50 | 게임 p99 | 게임 max |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | – | – | 0 | – | 12.9ms | 24.2ms | 108.8ms |
| 6 | 300 | 1× | 360 | 0 | 100.2ms | 9.8ms | 21.1ms | 39.2ms |
| 30 | 1,500 | 5× | 1,800 | 0 | 7.7ms | 9.7ms | 14.6ms | 34.3ms |
| 60 | 3,000 | 10× | 3,600 | 0 | 9.6ms | 10.5ms | 19.1ms | 30.0ms |
| 120 | 6,000 | 20× | 7,200 | 0 | 8.7ms | 9.2ms | 14.0ms | 29.2ms |
| 240 | 12,000 | 40× | 14,400 | 0 | 10.3ms | 9.2ms | 15.2ms | 30.2ms |

- 6 req/s 의 수집 p99 100ms 는 첫 요청들의 JIT 워밍업입니다. 그 뒤로는 10ms 안팎입니다.
- **게임 API 는 기준선과 구분되지 않습니다.** 40배 부하에서 p99 15.2ms, 기준선 24.2ms. 오히려 낮은
  것은 JVM 이 따뜻해져서입니다.
- 429 도 5xx 도 전송 오류도 없었습니다. 수집 API 는 모든 단계에서 전부 202 를 냈습니다.

서버 쪽은 달랐습니다. 앱 로그의 1분 요약:

```
23:33:23  큐 초과로 버림  24,200건  insert 실패 0건  (누적 저장 484,200건, 큐 잔량 100,000건)
23:34:23  큐 초과로 버림 418,200건  insert 실패 0건  (누적 저장 709,200건, 큐 잔량 100,000건)
```

120 req/s(초당 6,000 이벤트)부터 큐가 차서 버리기 시작했고, 240 req/s 에서는 분당 42만 건을
버렸습니다. 그런데 MySQL CPU 최고치는 **13%** 였습니다. DB 가 한계가 아니었습니다.

원인은 플러셔 구조입니다. 1초마다 한 번, 최대 5,000행 배치 하나를 넣으므로 처리량 상한이 정확히
**초당 5,000행**입니다. 6,000/s 가 들어오면 초당 1,000행씩 큐에 쌓이고, 10만 개 큐는 100초 뒤에
넘칩니다. 12,000/s 면 7,000/s × 60 = 42만 건, 로그 숫자와 맞습니다.

버려진 이벤트는 로그에 남고 게임 API 는 아무 영향이 없었으니 **"넘치면 버리고 게임은 산다"는 약속은
지켜졌습니다.** 다만 상한이 기준선의 16배(초당 5,000)라는 것은 "수십 배"라는 판단 기준에 못
미치고, 무엇보다 자원이 남아 있는데 소프트웨어가 막는 것이라 고쳤습니다.

## 고친 것

`GameEventFlusher.flush()` 가 한 주기에 배치 하나만 넣던 것을, 큐가 빌 때까지 최대
`analytics.flush-max-batches-per-tick`(기본 20) 번 연달아 넣도록 바꿨습니다. 이론 상한은 초당 10만
행이 되고, 그러면 DB 가 먼저 한계를 냅니다. 큐가 비면 바로 멈추므로 평소에는 한 번만 돕니다.

## 2차: 고친 플러셔

같은 조건, 단계만 위로. 0(기준선) → 120 → 240 → 480 → 960 req/s. 워커 48개.

| req/s | events/s | 기준선 대비 | 202 | 실패 | 수집 p99 | 게임 p50 | 게임 p99 | 게임 max |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | – | – | 0 | – | 13.5ms | 25.7ms | 160.7ms |
| 120 | 6,000 | 20× | 7,200 | 0 | 13.5ms | 9.6ms | 16.2ms | 39.7ms |
| 240 | 12,000 | 40× | 14,400 | 0 | 9.9ms | 8.8ms | 15.2ms | 25.9ms |
| 480 | 24,000 | 80× | 28,800 | 0 | 11.9ms | 8.3ms | 19.6ms | 27.4ms |
| 960 | 48,000 | 160× | 57,600 | 0 | 12.7ms | 8.0ms | 18.7ms | 21.9ms |

앱 로그의 1분 요약(드롭이 있는 분만 찍힙니다):

```
23:42:19  큐 초과로 버림   457,600건  insert 실패 0건  (누적 저장 1,780,000건)
23:43:23  큐 초과로 버림 1,860,100건  insert 실패 0건  (누적 저장 2,680,000건)
```

- **120·240 req/s 에서 드롭 0.** 1차에서 42만 건을 버리던 지점입니다. 플러셔 구조가 원인이었다는
  것이 확인됐습니다.
- **480 req/s(초당 24,000 이벤트)** 는 단계 시작 후 40초까지 드롭 없이 갔고, 끝머리에서 넘치기
  시작했습니다. 처리량이 그 근처라는 뜻입니다.
- **960 req/s(초당 48,000)** 에서는 1분에 186만 건을 버리며 약 90만 건을 저장했습니다. 지속 저장
  처리량은 **초당 1.5만~2.4만 행** 사이이고, 이때 MySQL CPU 는 44%(코어 하나의 절반 남짓)였습니다.
  이제 한계는 앱이 아니라 insert 처리량입니다.
- **게임 API 는 기준선의 160배 부하에서 p99 18.7ms.** 무부하(25.7ms)보다 낮습니다. 격리가 됩니다.
- 5분 동안 289만 행이 들어갔고 insert 실패는 0건입니다.

정리하면 한계는 기준선(초당 300 이벤트)의 **50~80배**, 실제 예상 부하(초당 55~72 이벤트)로는 200배
이상이고, 그 위에서도 잃는 것은 이벤트일 뿐
게임은 멀쩡합니다.

## 판단

- **B안(같은 앱, 스키마·풀만 분리) 유지.** 게임 API 격리는 기준선의 160배 부하에서도 확인됐고, 처리량 한계는
  기준선의 50~80배(실제 예상 대비 200배 이상)입니다. 지라 863 의 기준("수십 배 이상이면 유지")을 넘습니다.
- 수집을 별도 서비스로 나눠도 이 격리 이득은 늘지 않습니다. MySQL 을 공유하므로 DB 쪽 위험은
  같고, 지금 보인 것은 DB 가 아니라 앱 안의 플러셔 상한이었습니다.
- 다시 재야 할 때: 클라이언트 발행이 붙어 실제 이벤트 크기·비율이 정해졌을 때 한 번, 운영과 같은
  4 vCPU 환경에서 한 번. 이 PC 는 22코어라 절대치는 운영보다 좋게 나옵니다. 비율(기준선 대비 몇 배)로
  읽으세요.

## 다시 돌리기

개발용 MySQL(`d205-mysql-local`)이 떠 있으면 먼저 내립니다. `compose.local.yml` 이 `container_name`
과 호스트 포트 3307 을 고정하고 있어서 `-p d205load` 는 볼륨 이름만 갈라 줄 뿐, 개발용 컨테이너가 살아
있으면 아래 `up` 이 이름·포트 충돌로 실패합니다.

```
docker compose -f compose.local.yml down            # 개발용 MySQL 이 떠 있을 때만
docker compose -p d205load -f compose.local.yml up -d mysql
ANALYTICS_RATE_LIMIT_PER_MINUTE=100000000 ./gradlew bootRun
python loadtest/events_load.py --stages 0,6,30,60,120,240 --stage-seconds 60                # 1차
python loadtest/events_load.py --stages 0,120,240,480,960 --stage-seconds 60 --workers 48    # 2차
```

드롭·실패는 앱 로그의 `플레이 로그 지난 1분` WARN 을 보고, MySQL CPU 는 `docker stats` 로 봅니다.
끝나면 `docker compose -p d205load -f compose.local.yml down -v` 로 치웁니다. `-p d205load` 로 만든
볼륨만 지워지므로 개발용 DB(`d205` 프로젝트)의 데이터는 남고, 컨테이너는 다시 `up` 해서 올립니다.
