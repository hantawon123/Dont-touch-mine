# 실제 경기 자동 성능 측정

원본이 아닌 **독립된 Unity 프로젝트 복사본 두 개**에서 사용한다. Assets/Library/ProjectSettings를 원본과 링크하거나 공유하지 않는다. Unity 버전, 소스 커밋, 품질 설정을 맞춘다.

1. 두 복사본의 `Assets/Editor`에 `ClientPerformanceAuto.cs`를 복사하고 각 프로젝트 루트에 빈 `.performance-lab` 파일을 만든다. 원본에는 설치하지 않는다.
2. 동일한 `PERF_REVISION`, 6자리 `PERF_TEST_CODE`(기본 PER994), 새 절대 경로 `PERF_OUTPUT`을 두 프로세스의 환경 변수로 전달한다. 기존 결과 디렉터리를 재사용하지 않는다.
3. 서버는 Unity의 `-batchmode -nographics -projectPath <서버 복사본> -executeMethod ClientPerformanceAuto.Server -logFile <서버 로그>`로 시작한다.
4. 클라이언트는 `-projectPath <클라이언트 복사본> -executeMethod ClientPerformanceAuto.Client -logFile <클라이언트 로그>`로 시작한다. 실제 렌더링이 필요하므로 클라이언트에 batchmode/nographics를 넣지 않는다.

실행기는 기존 개발 서버 경로로 방을 만들고 마트에 입장한다. 서버가 출발 위치를 한 번 준비한 후 클라이언트는 일반 Fusion/KCC 입력으로 작은 동선을 반복한다. 10초 준비 후 30초 구간 3회를 기록하고 마지막 30초는 CPU Profiler를 켜 별도로 기록한다. 마지막 구간을 일반 FPS 평균에 합치지 않는다. 테스트 장면 진입/기존 게임의 인증 경로를 사용하므로 네트워크 연결이 필요하다.

`environment.json`, `trial-0.csv`부터 `trial-3.csv`, `cpu.raw`, `game.png`, 완료 시 `client-done.txt`가 나온다. `SummarizePerformance.ps1 -Directory <결과 경로>`로 평균 FPS와 p95/p99를 읽는다. 완료 파일이 없거나 로그에 오류가 있으면 통과로 판정하지 않는다. 두 에디터는 정상 완료 후 종료된다. 시작 중 스크립트 재컴파일로 Play가 종료되면 준비 후 재시도한다.

실행기는 검증 복사본의 제품명/버전, Play 상태와 Game 창을 변경한다. 테스트 종료 후 복사본의 설정을 원본에 복사하지 않는다. 소스 변경 전후 비교에는 같은 해상도·주사율·전원·품질·서버 부하를 사용하고, 측정 중 에디터 조작과 빌드를 피한다. CSV는 프레임 간격이며 GPU 처리 시간이나 화면 출력률 자체가 아니다.

이 자동 이동은 반복 가능한 탐색 기준선이다. 6인 전투, 모든 맵 구역, 물건 상호작용, 하이라이트 스킵, 재경기의 검증을 대신하지 않는다. 해당 시나리오는 별도 검사로 확장하며 단일 PC 결과를 실제 6인 성능으로 보고하지 않는다.

## 2026-09-16 WebGL 고정 시점 배칭 비교

별도 최적화 WebGL 빌드(OptimizeSpeed / RuntimeSpeed, 빌드 1069초)와 로컬 개발 서버 1인을 사용했다. Intel Arc 내장 GPU의 ANGLE D3D11 인앱 브라우저이며 RTX 4070 네이티브/일반 Chrome의 성능 보증이 아니다. 마트 진입 후 카메라 (-19.5, 2.00, -14.40), FOV 60, Unity 보고 해상도 960×600, 렌더 스케일 0.5, 내부 프레임 제한 144로 고정했다. 각 구간은 설정 변경 후 5초 대기하고 30초 측정했다.

| 순서 / 조건 | 평균 FPS | p95 ms | 평균 CPU 메인 ms | 평균 CPU 렌더 ms | 배치 수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기본 1 | 47.37 | 27 | 16.25 | 9.20 | 1025 |
| SRP Batcher 끄기 + GPU 인스턴싱 1 | 44.12 | 29 | 17.80 | 10.68 | 919 |
| 동일 인스턴싱 2 | 43.01 | 29 | 18.37 | 10.96 | 919 |
| 기본 복귀 2 | 47.87 | 27 | 16.06 | 9.06 | 1025 |
| SSAO 끄기 | 51.11 | 25 | 14.75 | 7.76 | 564 |
| 기본 복귀 3 | 45.63 | 29 | 17.07 | 9.61 | 1025 |

전체 씬에서 메시 렌더러 13,520개, 정적 배칭 참여 렌더러 7,348개, 고유 공유 머티리얼 66개, 고유 메시 참조 423개를 확인했다. 이는 카메라에 실제 보이는 개수가 아니다. CPU 메인/렌더 시간은 겹치므로 합산하지 않는다. GPU 시간은 0으로 반환돼 판정에 사용할 수 없었다. 모든 구간의 평균 presentWait는 약 4.8ms였다.

배치 수 감소만으로 성능 향상을 판단하면 안 된다. 이번 인스턴싱은 일관되게 느려 원본에 반영하지 않았다. SSAO 제거는 주변 기본 측정보다 개선되지만 120FPS에 크게 못 미치고 시각 효과를 제거하므로 그대로 반영하지 않았다. 저장된 게임 스크린샷에서 기본/SSAO 제거 양쪽 모두 같은 구도의 주요 구조물이 유지됨을 확인했다. 모든 사건·물건의 가시성을 검증한 것은 아니다.

표시 관련 제한도 있다. 브라우저 DOM 캔버스 버퍼는 1920×1080, CSS 크기와 Unity 보고 크기는 960×600이었고, 웹 표시에서 여백이 생겼다. Unity가 저장한 이미지는 정상 구도의 960×600이었다. 동일 실행 내부의 상대 비교로만 사용하고, 정상 전체화면 1080p FPS로 보고하지 않는다. 일반 Chrome의 약 70FPS 현상 및 120FPS 달성은 미검증이다.

완료 마커와 6개 CSV/스크린샷은 작업 공간 `.build/performance-995-web-batch`에 보관했다. 원본 프로젝트에 시험 실행기를 설치하지 않았다. 임시 서버와 페이지를 종료하고 검증 복사본의 인증·버전·빌드 설정을 복원했다. 다음 검증은 실제 사용 GPU와 캔버스 크기를 먼저 통일하고 CPU PlayerLoop/렌더 제출의 세부 비용을 측정해야 한다.

프레임 설정은 별도 커밋 ecf39977에서 30·40·60·120 선택지를 유지하고, 120 선택만 내부 144FPS 제한으로 대응하도록 변경했다. 설정 테스트 31개가 통과했다. 이 내부 여유는 성능 개선이나 120FPS 보증을 의미하지 않는다.


## 2026-09-16 동일 Intel GPU 비교 및 렌더 스레드 대조

GPU 차이의 영향을 분리하기 위해 기존 Mono 네이티브 시험 플레이어를 별도 디렉터리에 재사용하고, 동일 Unity 버전에서 새로 컴파일한 시험용 Assembly-CSharp.dll만 교체했다. 신규 전체 네이티브 빌드는 셰이더 컴파일 단계에서 중단했으며, 완성된 신규 배포 빌드라고 보고하지 않는다. 게임 에셋과 게임 로직 DLL은 기존 시험 플레이어를 사용한다. `-force-d3d11 -force-device-index 1`의 실행 로그에서 Intel Arc (0x7d55)를 확인했다. 두 복사본의 WebGL_RPAsset 및 WebGL_Renderer 파일 SHA256도 동일했다.

양쪽 모두 같은 마트 시점(-19.5, 2.00, -14.40), FOV 60, Unity 보고 960×600, WebGL 품질 프로필, 렌더 스케일 0.5, 제한 144, VSync 0, 같은 PC의 별도 서버/1인 조건으로 측정했다. 네이티브는 세 구간 각 30초를 측정했다. 렌더 스레드 대조 실행에는 `-force-gfx-direct`를 추가하고 로그의 `kGfxThreadingModeDirect`를 확인했다.

WebGL은 검증용 프레임워크에서 캔버스 크기 지정만 960×600으로 고정하는 `sizeqa=1`을 추가하고 DPR 1로 실행했다. DOM 버퍼와 CSS 모두 960×600인 것과 여백 없이 전체 구도가 보이는 것을 확인했다. 프레임 예약/게임 로직은 이 보정에서 변경하지 않았다. 이 생성물 패치는 제품 최적화 코드가 아니다.

| 실행 | 평균 FPS 범위 | 평균 CPU 메인 ms 범위 | 평균 CPU 렌더 ms 범위 |
| --- | ---: | ---: | ---: |
| 네이티브 Intel, 기존 렌더 스레드 | 142.78~143.23 | 3.28~3.41 | 1.25~1.29 |
| 네이티브 Intel, 직접/단일 스레드 렌더 | 138.78~142.36 | 4.98~5.26 | 3.14~3.31 |
| WebGL Intel, 크기 보정 후 기본 구간 3회 | 40.71~42.07 | 18.88~19.69 | 10.91~11.30 |

WebGL 크기 보정 후 인스턴싱 2회는 34.97~35.97FPS, SSAO 끄기는 45.25FPS였다. 이전 시험과 동일하게 인스턴싱의 악화와 SSAO 제거의 제한된 개선이 반복됐다. 두 설정 모두 제품에는 반영하지 않았다. 평균 presentWait는 네이티브 기본 3.59~3.70ms, 직접 렌더 1.80~2.04ms, WebGL 기본 4.86~4.90ms다. CPU 메인/렌더는 겹치므로 합산하지 않는다.

판정: 이 시점의 큰 격차는 GPU 모델과 캔버스 크기 차이를 줄여도 남는다. 네이티브의 렌더 스레드를 끄는 것만으로 WebGL의 낮은 FPS가 재현되지 않았다. 따라서 GPU 선택이나 별도 렌더 스레드 부재만을 주원인으로 단정하지 않는다. WASM/브라우저 그래픽 호출/플랫폼 구현의 추가 비용을 세부 계측해야 한다. 높은 CPU 렌더 시간은 조사할 위치를 알려주지만 개별 함수의 원인 증거는 아니다.

남은 비교 한계: 네이티브 Mono와 WebGL IL2CPP/WASM, 직접 D3D11과 ANGLE/OpenGLES3, 업스케일링 자동 선택과 WebGL Linear가 서로 다르다. 메인 스레드의 GPU 대기와 플랫폼별 타이밍 의미도 완전히 같다고 가정하지 않는다. 동일 프레임의 결정적 리플레이가 아니라 같은 시점의 별도 1인 경기다. 일반 Chrome의 약 70FPS 현상은 직접 재현하지 않았다. 네이티브 p95가 8.33ms를 넘는 구간도 있으므로 평균 143FPS를 안정적인 최저 120FPS 보증으로 해석하지 않는다.

완료 마커/환경/CSV/이미지:
- `.build/performance-995-native-intel`
- `.build/performance-995-native-intel-direct`
- `.build/performance-995-web-fixed-canvas`

모든 측정은 빌드 작업이 종료된 뒤 순차 실행했다. 시험용 서버/클라이언트와 미리보기를 종료하고 검증 복사본을 복원했다. 사용자의 원본 에셋·품질 설정은 변경하지 않았다.

시험 인자 의미는 [Unity Player 명령줄 문서](https://docs.unity3d.com/kr/6000.0/Manual/PlayerCommandLineArguments.html)를 따른다. WebGL의 C/C++ 스레드 지원과 C# 스레드는 서로 다른 제약이 있으므로 단순히 스레드 옵션 하나로 해결된다고 결론내리지 않는다([Unity Web 기술 제약](https://docs.unity3d.com/ja/6000.0/Manual/webgl-technical-overview.html)).
