# AI 봇 플레이어 — Jira 스토리·태스크 초안 (2026-09-14)

사람이 부족한 방을 봇으로 채워 6인 경기를 돌릴 수 있게 하는 AI 봇 개발의 스토리·태스크 분해.
마트 맵 에픽(901: 902~915)과 같은 형식(설명 / 작업 체크리스트 / 완료 조건 / 선행 / 규모)을 따르되,
이번에는 에픽 아래 **스토리 5개**를 두고 각 스토리 아래 태스크를 붙였다.
이슈 번호는 아직 미발급. 발급 후 아래 "번호 매핑" 표와 각 제목의 괄호를 채운다. 커밋은 `S15P21D205-### [CL] 태그: 제목`.

전제
- 규칙: 6인, 숨기기 1인당 30초 차례(다른 사람은 대기 스폰), 찾기 6분(기본 5분), FINAL 30초, 물건 1개씩, 파쇄기 인당 5회, 3타 기절 2초.
- 네트워크: Photon Fusion 호스트 권위(`GameMode.Host`, 권한 판정은 모두 `runner.IsServer`). 경기 판정은 `MatchSessionCoordinator`(playerIndex 기준)가 한다. 클라이언트 행동은 `PlayerInteractor → IPlayerInteractionCommands(NetworkInteractionSceneBridge) → MatchSessionState`의 RPC(`RPC_RequestHold/Release/Drop/Throw/Hit/Shredder/CompleteHidingTurn/ConfirmPhaseIntroReady`) → `MatchStarter.Try*(PlayerRef source, …)`가 `PlayerRef → playerIndex`로 바꿔 코디네이터에 넘기고 결과를 `Publish*`로 복제한다. 이동은 `PlayerMovement(IPlayerInputIntentSource) → PlayerInputIntent → NetworkPlayerInput{Move, LookYawDegrees, Buttons(Jump/Sprint/Crouch/Prone/Attack)}`을 `NetworkRunnerService.OnInput`이 로컬 플레이어 것만 채우고, `NetworkPlayerMotor.FixedUpdateNetwork`가 `GetInput`으로 읽어 KCC에 적용한다. 플레이어 프리팹은 `Assets/_Game/Content/Prefabs/NetworkedPlayer.prefab`(`NetworkPrefabs.asset`의 `Player`).
- 봇은 **호스트에서만** 판단·입력을 만든다. 클라이언트는 사람 플레이어와 똑같이 복제 결과만 본다. 호스트가 나가면 방이 닫히므로 봇 승계는 없다.
- 방 최소 시작 인원은 1(`RoomSettings.MinMatchPlayerCount`)이라 혼자 시작은 이미 가능하다. 봇의 목적은 "빈자리 채우기"(연습·테스트·인원 부족)다.
- 방 Custom Properties는 Fusion 10개 제한 중 8~9개를 쓰고 있어 봇 설정은 새 속성이 아니라 `rules` JSON(버전 있음)에 넣는다.
- 내비게이션: `com.unity.ai.navigation 2.0.14`가 manifest에 있지만 어느 씬에도 NavMesh가 없다. 마트 씬은 렌더러 약 2.4만 개, 상품 Carryable 7천여 개라 **정적 구조물만** 베이크한다.
- 어셈블리 규칙(README): Client↔Server 직접 참조 금지, Fusion 타입은 Network 밖으로 안 나감. 봇 **판단 로직은 Server(순수 C#)**, 포트(인터페이스)는 Core, NavMesh·레이캐스트·Fusion 연결은 Network/Bootstrap.
- 진행 방향: **규칙 봇(S1~S5)을 먼저 완성해 기준선으로 삼고 → 그 위에 강화학습 환경(S6) → 학습 모델 통합·평가·반복(S7)**. 학습은 매크로 행동(무엇을 할지) 계층만 맡고 실행(길찾기·집기·공격)은 규칙 루틴을 재사용한다. 추론은 `com.unity.ai.inference`(Sentis), 학습은 ML-Agents.
- 비범위: 봇 음성·채팅, 호스트 승계 시 봇 복원, 로비에서 봇이 걸어 다니는 연출(로비 NavMesh 없음 → 스폰 자리에 서 있기), 조이스틱 수준(저수준 이동) 강화학습.

## Story S1. [봇 참가] 호스트가 방에 봇을 추가·제거하고, 봇이 참가자로 경기에 들어온다

> **사용자 스토리**: 방장으로서, 사람이 모이지 않아도 봇을 추가해 6인 경기를 시작하고 싶다. 참가자로서, 봇이 누구인지 명단에서 바로 구분하고 싶다.
>
> **인수 조건**
> - 방 만들기·로비 설정에서 봇 수(또는 자동 채우기)를 정하면 로비 명단에 봇이 사람과 같은 형식(닉네임 + 봇 태그)으로 나타난다.
> - 게임 시작 시 봇이 스폰 지점에 캐릭터로 서 있고, 물건이 배정되며, 페이즈 진행(숨기기 차례 포함)이 봇 때문에 멈추지 않는다.
> - 봇에게는 친구 추가·신고·보이스 버튼이 없고, 호스트에게는 봇 제거 버튼이 있다.
> - 백엔드 플레이 로그는 봇을 계정으로 기록하지 않는다.

## Story S7. [학습 모델 통합·평가] 학습한 정책을 게임에 넣고 규칙 봇·사람과 비교해 반복 개선한다

> **사용자 스토리**: 방장으로서 "어려움" 봇이 학습된 봇이길 바라며, 학습 봇이 규칙 봇보다 실제로 더 잘 찾고 더 잘 지키는지 숫자로 확인하고 싶다. 팀으로서 학습 봇이 이상 행동을 하면 즉시 규칙 봇으로 되돌릴 수 있어야 한다.
>
> **인수 조건**
> - ONNX 모델이 Sentis 추론으로 호스트에서 돌고, 봇 난이도 중 하나가 학습 정책을 사용한다.
> - 학습 봇 vs 규칙 봇 승률·행동 지표가 자동 평가로 나오고, 사람 플레이테스트 리포트가 있다.
> - 모델 로드 실패·추론 시간 초과 시 규칙 봇으로 자동 폴백된다.

1. **S1 기반**: T1 → T2 → T3 (봇이 경기 씬에 서 있고 디버그 명령으로 행동) — 1주차

3. **S3 숨기기**: T10 → T11 — 2주차
4. **S4 탐색·난투**: T12 → T13 → T14 → T15 — 3주차

첫 데모 목표(2주차 말): 방장 혼자 방 만들기 → 봇 5명 채우기 → 숨기기 차례가 봇으로 진행 → 찾기 페이즈에서 봇이 순찰·수거까지.
두 번째 목표(S5 끝): 규칙 봇 어려움이 사람 초보를 이기는 수준 + 성능 기준 충족. 이 시점의 규칙 봇이 강화학습의 기준선·학습 상대가 된다.
세 번째 목표(S7): 학습 봇이 규칙 봇 대비 승률 60% 이상, 사람 플레이테스트에서 이상 행동 없음.
