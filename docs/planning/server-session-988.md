# 경기 권한과 세션 전환 — S15P21D205-988

987의 실제 WebGL 최소 접속 검증 다음 단계다. 같은 feature 브랜치에 연속 커밋하며 MR은 사용자 보고 후 결정한다. 구현과 로컬 네이티브 6인 흐름 검증을 마쳤으며, 서로 다른 PC의 WebGL 확인은 아래 수동 절차로 진행한다.

## 실행과 방 생성

별도 Unity 프로세스를 `-batchmode -nographics -gameServer -roomCode 988ABC -region kr`로 실행한다. 서버 구매·임대 없이 로컬에서 실행할 수 있다. Photon이 이 Unity 프로세스를 실행해 주는 것은 아니다.

서버는 기존 계정 API와 Photon Custom Auth를 사용한다. 서버 기기 ID는 플레이어와 다른 PlayerPrefs 키로 보관하며 로그에 쓰지 않는다. 서버에는 플레이어 입력, Voice 연결, 프런트엔드 화면 조립을 하지 않는다. 경기 씬의 물리와 상호작용 구성은 유지한다.

서버 프로세스 하나가 빈 세션 하나를 Photon 로비에 `available=true`로 광고한다. 이 세션은 사용자가 보는 방 목록에서 제외된다. 일반 방 만들기는 빈 서버를 찾아 **Client로 접속**하고, 첫 접속자의 설정 요청을 서버가 검증한 후 정상 방으로 전환한다. 설정 확정 전에는 다른 접속을 받지 않는다. 비밀번호 원문은 세션 속성에 게시하지 않는다. 공개 닉네임은 기존 스트리머 표시 정책을 거친 값으로 보낸다.

서버가 없으면 방 생성은 연결 실패를 안내하며 플레이어 Host로 대체 실행하지 않는다. 서버 자동 공급과 운영 환경 배포는 989/990의 후속 범위다. 초기 구현은 미리 실행한 프로세스의 가용량 안에서 동작한다. 빈 상태 또는 설정 미확정 상태가 120초를 넘으면 프로세스가 정리된다.

방 목록도 Fusion의 `ClientServer` 로비를 조회한다. Photon의 서버 접속 한 자리는 화면 인원에서 제외한다. 홈 예열과 방 만들기가 같은 인증을 기다렸더라도 목록 연결은 하나만 생성하고, 인증 대기 중 취소되면 새 연결을 만들지 않는다.

## 권한과 수명

- 기존 `PlayerAvatar.IsHost`는 UI 호환을 위해 이름을 유지하되 **로비 방장**을 뜻한다. 서버 권한은 `IsServer`/StateAuthority로만 판정한다.
- 시작·설정·강퇴 요청은 RPC의 실제 송신자와 서버가 소유한 방장 상태를 대조한다. 클라이언트가 보낸 계정 ID나 대상 ID로 요청자 권한을 결정하지 않는다.
- 경기 확정, 물리 결과, 비공개 아이템 배정, 기록은 기존 서버 규칙을 사용한다. 서버에서 로컬 하이라이트 재생 이벤트를 발생시키지 않는다.
- 방장 퇴장 시 기존 방 종료 정책을 유지해 서버 세션을 닫는다. 일반 참가자의 경기 중 퇴장은 기존 경기 규칙으로 처리한다. 재경기는 같은 서버에서 진행한다.
- 네이티브 서버와 WebGL은 `server-v1-{Application.version}`으로 동일한 호환 버킷을 사용한다. 기존 Host 빌드와 섞이지 않으므로 같은 변경의 빌드끼리 실행해야 한다.

## 검증

관련 EditMode 테스트와 전체 게임을 사용한 독립 실행 파일 실험을 진행한다. [검증 도구](../../Tools/network/server-flow/README.md)는 제품의 방 생성·입장 명령과 실제 씬을 사용한다. 권한 상태나 경기 결과를 직접 변경하지 않는다.

2026-09-14 결과:

- 관련 EditMode 180개 통과. 권한·세션 계약, 목록 인원수, 연결 재사용, 인증 대기 경합·취소를 포함한다.
- 전체 게임 Win64 빌드 성공. 버전 `988-local-v1`, 서버 1개와 서로 다른 실험 계정의 클라이언트 6개를 같은 PC에서 실행했다.
- 모든 참가자가 Client로 접속했고 일반 참가자 5명의 시작 RPC에 서버가 `NotHost`를 반환했다.
- 서버가 없는 별도 실행에서 방 생성이 `ConnectionFailed`로 거절되고 Host 러너가 생성되지 않았음을 확인했다. [실패 경로 증거](../../Tools/network/server-flow/no-server-evidence-2026-09-14.txt)의 드라이버 `FAIL`은 의도한 접속 실패 결과다.
- 6인 경기의 숨기기·탐색과 비공개 배정 수신, 탐색 중 1명 퇴장 뒤 5인 진행, 결과 수신·결과 씬 로드, 5인 재경기와 새 배정, 재경기 탐색 중 방장 정상 퇴장에 따른 전체 방 종료를 확인했다.
- [허용 필드만 추출한 실행 증거](../../Tools/network/server-flow/evidence-2026-09-14.txt)를 검증기가 통과했다. 해당 실행의 서버·클라이언트 로그에 검사 대상 런타임 예외가 없었다. 종료 후 남은 실험 클라이언트 창은 정리했다.
- 실제 WebGL 빌드 성공. 브라우저의 정상 방 만들기에서 `Client / IsServer=False`, 서버 방 확보, 로비의 `1/6` 표시를 확인했다. 설정의 나가기 버튼으로 홈에 복귀했고 서버 로그의 `Session closed`와 프로세스 종료를 확인했다. [WebGL 증거와 한계](../../Tools/network/server-flow/webgl-evidence-2026-09-14.txt)를 함께 기록했다.

남은 별도 관찰: 기존 백엔드의 presence·friends 요청에서 네이티브와 WebGL 모두 HTTP 401이 발생했다. 계정 발급·Photon 인증·방 생성과 경기 흐름은 진행되었지만 친구·접속 상태 연동까지 정상이라고 판정하지 않는다. WebGL 확인 도중 내장 브라우저에서 Chromium `UnknownError` 알림도 한 번 발생했다. 이후 UI 퇴장과 홈 복귀는 완료했으나 원인은 확정하지 않았으므로 일반 브라우저의 6인 수동 확인에서 재발 여부를 기록한다.

실행 중 드러난 원인도 흐름 단위로 보완했다. 서버 전용 DI에서 선택적 인증 저장소를 명시적으로 제외했고, 화면이 없는 서버도 Home에서 Lobby로 진입시켜 경기 후반의 앱 상태 전환이 이어지게 했다. 로비 조회 위치와 인증 후 중복 연결 경합을 수정했으며, 성공한 방 생성의 타임아웃 타이머가 폐기된 취소 소스를 다시 호출하지 않도록 함께 해제한다. 보완 후 위 6인 전체 흐름을 다시 실행했다.

최종 네이티브 실행 어셈블리 SHA-256:

```text
Game.Network.dll   084D00A52709710068967FD6488AA083AF9EBB6C543E0A75942712C62D6A7371
Game.Bootstrap.dll 665A91DF1D7A8C726C9B3B154BB347AFCDEDA5C992760F7A60041B7E835FD300
```

Jira의 최종 완료 조건인 **서로 다른 PC의 WebGL 6인 경기·퇴장·재경기**는 같은 PC의 다중 네이티브 실행만으로 충족되지 않는다. 로컬 실행 결과와 외부 환경 검증 결과를 구분해 기록한다. 서버 임대·공개 배포·Jenkins 활성화는 이 로컬 검증에 포함되지 않는다.

사용자 결정: 로컬 검증 뒤 서로 다른 PC의 6인 확인은 실행 절차를 전달받아 사용자가 직접 진행한다.

[6인 수동 실행·기록 절차](../../Tools/network/server-flow/manual-six-pc.md)에는 실제 조작과 충돌·물건 상호작용, 비밀번호·비공개·정원, 비정상 종료까지 포함한다. 자동 흐름 검증은 입력 없이 경기 규칙의 실제 타이머를 사용했으며, 이 조작 확인이나 120 FPS·운영 수용량 측정을 대신하지 않는다.


## 기존 EC2 후속 검증 (2026-09-14)

Linux Dedicated Server 빌드의 UI 초기화 문제를 수정하고 기존 EC2에서 6인 경기→참가자 퇴장→5인 결과·재경기→방장 퇴장·서버 종료를 검증했다. 실제 WebGL도 EC2에 Client로 접속·퇴장했다. [EC2 검증 기록](server-ec2-trial-988.md)에 증거와 자원 관측을 정리했다. 별도 PC WebGL 6인 실플레이, Chromium 설정 진입 오류와 presence 401은 남아 있다. 이전 로컬 검증 결과와 구분하며 MR은 생성하지 않았다.
