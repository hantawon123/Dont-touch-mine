# AI 봇 이틀 실행 계획 — 2026-09-22

상태: 코드 확인을 반영한 재계획. 아래 신규 기능·평가 수치는 아직 구현 결과가 아니다.

## 0. 역할 정정 — 봇은 플레이어 대체 참가자가 아니다

2026-09-22 목표를 다음과 같이 정정한다.

- AI 봇은 로비 대기열, 플레이어 좌석, 물건 배정, 숨기기 순서, 사람 승패 인원에 포함되지 않는다.
- 사람들의 숨기기 단계가 끝나고 수색 단계의 실제 맵이 준비된 뒤, 경기 권한을 가진 서버가 NPC 봇을 유효한 무작위 위치에 생성한다.
- NPC 봇은 맵을 탐색하며 공개된 물건을 선택하고, 이동·집기·운반·놓기·파쇄를 수행한다. 사람을 발견하면 조건에 따라 공격하거나 물건을 들고 도망갈 수 있다.
- 기존 `BotProfile`, 봇 좌석, `MatchParticipant.IsBot` 작업은 네트워크 KCC 동기화 실험 자산으로 보존하지만, 이 NPC의 경기 참가 모델로 사용하지 않는다.
- NPC는 가짜 `PlayerRef`나 가짜 `playerIndex`를 만들지 않는다. 사람용 규칙에서 공통으로 쓸 수 있는 거리·물건 점유·놓기 자세 검사는 공유하고, 사람 전용 규칙과 NPC 생명주기는 분리한다.

비유하면 이 봇은 빈 선수 자리를 채우는 선수가 아니라, 숨기기 시간이 끝난 뒤 경기장에 투입되는 경비 로봇이다.

이번 이틀의 작업 순서는 이 문서를 우선한다. 이전 장기 계획과 Jira 초안은 장기 참고 자료로 남긴다. Jira 순서에 맞추려고 불필요한 게임 통합을 먼저 하지 않는다.

## 1. 목표와 정직한 약속

목표는 **학습한 물건 선택 판단을 사용하는, 한 맵에서 수색 단계에 투입되는 하이브리드 NPC 봇**이다. 하이브리드는 “두뇌는 연습으로 배우고, 다리는 이미 만든 걷기 기능을 쓰는 것”이다.

- 최소 완료: 봇이 공정한 시야로 물건을 보고, 학습 모델로 탐색/물건 선택을 결정하고, 실제 KCC 이동과 실제 집기 판정을 통해 확보한다. 학습하지 않은 비교 봇과 성능을 비교한다.
- 시연 목표: 위 기능에 코드 기반 운반·내려놓기·파쇄기 투입·간단한 공격·지정 지점 숨기기를 연결한다. 이 행동들까지 모두 학습했다고 설명하지 않는다.
- 장기 목표: 상황에 맞는 운반/파쇄/공격/도주/숨기기 전략까지 학습한다. 이틀 범위 밖이다.

이틀은 약 16~20시간의 집중 개발과 그 사이 실행하는 학습을 가정한 추정이다. 장비 속도와 게임 상호작용 연결 난이도에 따라 달라진다. 모든 기능과 학습 수렴을 보장할 수 없다. 먼저 하나의 의미 있는 학습 결과를 확보하고 확장한다.

## 2. 지금까지의 자산과 실제 확인 수준

| 작업 | 확인된 수준 | 이번 사용 방식 |
| --- | --- | --- |
| Reach 학습 | 기존 기록과 사용자 결과: 목표 도달 100회 평가 성공. CharacterController 기반 단순 이동 | Python→학습→ONNX→추론 경로의 참고. 게임 전략 모델로 재사용하지 않음 |
| NetworkedBot / BotMoveToTarget | 사용자가 캐릭터 이동·정적 벽 우회 확인 | KCC와 NavMesh 실행부 재사용 |
| BotProfile / 참가자 관리 | 코드와 테스트 작업 존재 | KCC 네트워크 시험 기록으로만 보존. NPC를 경기 참가자로 넣는 데 사용하지 않음 |
| Host + Windows 클라이언트 | 사용자 동일 화면 확인 | 최소 복제 검증 자산. 완전한 경기/전용 서버 검증은 아님 |
| BotPerception | 전방/후방/벽 가림 테스트 사용자 통과. 추가 최근접 물건 테스트 2개 존재 | 추가 테스트 실행 및 정보 누출 수정 필요 |
| 집기·운반·파쇄·공격·숨기기 | 게임 기능은 존재하지만 봇의 전체 연결과 성공 증거 미확보 | 완료로 취급하지 않음 |
| 게임 판단 학습 | 새 관찰/행동/보상과 학습 결과 없음 | 이번 핵심 작업 |

Reach의 높은 성공률은 해당 작은 환경의 결과다. 새 맵, KCC, 물건 집기나 전투까지 잘한다는 뜻이 아니다. 기존 평가 배치를 반복 사용한 기록은 새로운 배치에 대한 일반화 증거와 구분한다.

MPPM에서는 Read Only Asset Database 및 NetworkProjectConfigAsset 로드 실패가 반복됐다. 정확한 원인은 확정하지 않는다. 이번에는 이를 재조사하는 데 시간을 쓰지 않고, 필요한 네트워크 최종 확인에 이미 성공한 Editor Host + Windows 클라이언트를 사용한다.

## 3. 이번 기능별 구현 경계

| 원하는 행동 | 이틀 구현 방향 | 학습 여부 / 우선순위 |
| --- | --- | --- |
| 돌아다니기 | 도달 가능한 탐색 지점을 고르고 KCC로 이동 | 탐색할지 물건을 고를지는 모델, 경로는 코드 / 필수 |
| 물건 선택·집기 | 눈에 보이는 복수 후보에서 목적에 맞는 물건 선택 | 모델의 핵심 학습 / 필수 |
| 무작위 물건 옮기기 | 유효한 소품 선택 모드→집기→안전 지점 운반→내려놓기 | 코드 시연 모드 / 우선 확장 |
| 파쇄기 투입 | 허용된 물건을 운반하고 기존 게임 규칙으로 투입 | 코드 / 확장 |
| 사람 발견 후 공격 | 시야·거리·공격 가능 상태·쿨다운 확인 후 공격 | 코드 / 확장 |
| 숨기기 | 사전 검증된 은폐 지점 중 선택→운반→배치→차례 종료 | 코드 / 마지막 확장 |

**실전 물건 목표(2026-09-23 확정):** 기본은 목표 1 "일반 소품을 골라 옮겨 놓아 수색자 교란", 확장은 목표 2 "파쇄 가능한 소품을 파쇄기에 투입". 플레이어가 숨긴 물건 추정은 범위 밖. 모델은 물건 이름이 아니라 성질(거리·크기·파쇄 가능·점유·목표 일치)로 후보를 보므로 모든 CarryableItem에 재학습 없이 적용된다. 상세는 [파이프라인 v1 2·3절](ai-bot-pipeline-v1.md).

“무작위로 아무 물건이나 고르기” 자체는 학습할 이유가 작다. 그래서 학습 실험에는 **주어진 목적에 맞는 물건을 여러 후보 중 고르는 문제**를 둔다. 데모용 무작위 행동과 학습 성능 평가는 별도 모드로 유지한다.

숨기기는 임의 장소의 은폐 효과를 이해하는 능력이 아니라, 미리 확인한 장소에 배치하는 기능이다. 전투도 사람처럼 심리를 읽는 기능이 아니다. 발표와 문서에 이 차이를 명시한다.

## 4. 순서와 중간 통과 조건

### Day 1 — 학습을 실제로 시작하는 날

| 시간 예산 | 작업 | 통과 증거 / 실패 시 조치 |
| --- | --- | --- |
| 0~1시간 | 복구 상태 확인, 기존 테스트 재실행, 작은 시험 씬과 물건 종류 고정 | 기본 이동·시야 회귀 통과. 패키지 업그레이드 금지 |
| 1~4시간 | 시야 스냅샷, 목적지 좌표 이동, 봇 권한의 실제 집기·놓기 실행 | 20회 접근/집기/초기화 반복. 실패하면 학습보다 연결 문제부터 수정 |
| 4~6시간 | 단일 봇 학습 환경, 에피소드 초기화, 관찰·행동·보상 연결 | 모델 없이 무작위/규칙 입력으로 에피소드 완주·성공 판정 검증 |
| 6~8시간 | 최초 PPO 학습 시작, 기록·평가 경로 확보 | 학습 지표와 체크포인트 생성. 첫날 안에 반드시 학습 시도 |
| 남은 시간/야간 | 학습 진행, 독립적인 운반·놓기 확장 | 환경/보상 변경 시 새 실행 ID. 학습 중인 환경 파일을 덮어 바꾸지 않음 |

### Day 2 — 결과 검증과 작은 완성품 연결

| 시간 예산 | 작업 | 통과 증거 / 실패 시 조치 |
| --- | --- | --- |
| 0~2시간 | 미사용 배치에서 평가, 무작위/규칙 기준선 비교 | 보상 그래프가 아닌 실제 올바른 집기 성공률 확인 |
| 2~4시간 | 가장 큰 실패 원인 한 가지 수정·재학습, ONNX 연결 | 늦어도 이 구간 끝에 모델/입력 형식 고정 |
| 4~6시간 | 확보된 실행부로 운반·파쇄 투입·공격 순차 연결 | 각 기능 기존 서버 판정 확인. 시간 부족 시 뒤 기능 보류 |
| 6~8시간 | Host+Windows, 안정성·데모·실험 보고서 | 모델 판단이 실제로 사용됐는지 로그와 비교 실행으로 증명 |
| 여유분 | 지정 지점 숨기기, 실제 맵 추가 배치 | 필수 항목 통과 후에만 진행 |

이 표는 순차 작업 예산이다. 학습 시간을 무조건 2시간으로 제한하거나 성공을 보장하는 표가 아니다. 한 작업이 지연되면 공격·숨기기부터 줄이고, 학습 결과 검증 시간은 남긴다.

### 중단·축소 기준

- 4시간째 실제 집기 연결이 안 되면 다중 봇/경기 전체 통합을 중단하고 단일 봇 실행부만 해결한다. 가짜 집기 보상으로 성공을 꾸미지 않는다.
- 첫날 끝에도 학습 환경이 돌지 않으면 둘째 날 범위는 “선택·집기 학습 + 평가”로 축소한다.
- 2회의 짧은 진단 실험에서 올바른 집기가 전혀 나오지 않으면 초기 배치부터 쉽게 만들고 관찰/보상/마스크를 점검한다. 무작정 학습 시간만 늘리지 않는다.
- 마감 때 모델이 기준을 못 넘으면 기능 데모는 규칙 봇으로 제공할 수 있지만, **학습 기능 실험 중 / 목표 미달**이라고 명시한다.
- 모든 행동 학습, 자기대전, 사용자 대규모 로그 수집, 새 맵 확장, Web 재빌드를 동시에 시작하지 않는다.

## 5. 게임 연결에서 지킬 규칙

1. 봇 생성·판단·행동 요청은 수색 단계의 경기 권한을 가진 실행 측에서만 만든다. Host 테스트 통과와 실제 Dedicated Server 배포 통과를 구분한다.
2. 봇은 가짜 사람 `PlayerRef`, 플레이어 좌석, `playerIndex`를 만들지 않는다. 별도 NPC ID와 NPC 상태를 사용한다. 거리·물건 점유·놓기 자세 같은 공통 검사는 사람과 공유하지만, 숨기기 차례·개인 물건·사람 승패 같은 플레이어 전용 규칙에는 들어가지 않는다.
3. `MatchStarter.TryUseShredder`와 `MatchSessionCoordinator`에서 플레이어 물건 파괴와 일반 소품 재배출 경로가 다르다. 투입/사용 횟수 소비/파괴/재배출을 따로 기록한다.
4. 게임 승리는 종료 시 자기 물건을 보유하는 조건이다. 공격 횟수나 무작위 파괴 수만 높이는 봇을 게임을 잘하는 봇으로 평가하지 않는다.
5. Core는 공유 약속, BotRuntime은 관찰과 판단 지원, Network는 Fusion 연결, Bootstrap은 조립 역할을 유지한다. Client의 CarryableItem 때문에 Network→Client 순환 참조를 만들지 않는다.
6. 학습의 보상/초기화는 실제 서비스의 게임 판정을 바꾸지 않는다. 트레이너와 실험용 초기화는 서비스 실행에서 꺼진다.

## 6. 최종 통과 기준 — 제안값, 아직 결과 아님

- 데이터 공정성: 벽 뒤/범위 밖의 새 정보가 입력에 없고, 사라진 대상 위치가 실시간 갱신되지 않는다.
- 실행부: 집기/놓기 20회 반복에서 상태 누락·중복 보상·에피소드 간 잔여 상태가 없다.
- 학습: 학습에 쓰지 않은 고정 100개 배치에서 올바른 집기 80% 이상을 1차 목표로 둔다. 성공률·평균 및 상위 10% 소요 시간·실패 사유를 기록한다.
- 비교: 같은 배치와 제한 시간에서 무작위 정책보다 성공률 20%p 이상 개선을 목표로 한다. 목적을 아는 단순 규칙 정책과도 비교한다. 규칙 정책보다 못하면 그대로 보고하며 우월성을 주장하지 않는다.
- 학습 증거: 학습 전/후 모델, 설정, 결과, 모델 선택 로그를 남긴다. 선택 결과를 코드가 항상 덮어쓰는 구조는 통과가 아니다.
- 실사용 시험: 사람 참가자들이 수색 맵에 들어온 뒤 NPC 봇이 별도로 생성되고, 그 행동이 Host/클라이언트에서 동일하게 보이며 20분 동안 중단 예외가 없다. 5봇은 별도 부하 측정 후 확대한다.
- 성능: 목표 장비에서 봇 없는 상태 대비 프레임 시간·추론 시간·할당을 측정한다. 임의의 FPS 보장을 하지 않는다.

100회는 실용적인 1차 점검이지 모든 맵에 대한 증명이 아니다. 최종 검증 배치는 튜닝에 사용하지 않는다. 추가 시간에는 여러 학습 시드의 재현성을 확인한다.
