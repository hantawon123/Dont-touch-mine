# AI 봇 파이프라인 v1 — 물건 선택부터 실사용까지

작성일: 설계 제안이며 구현 완료 명세가 아니다.

## 0. 실행 주체 — 수색 단계 NPC

이 문서의 봇은 사람 플레이어를 대신하지 않는다.

- 로비와 숨기기 단계에는 존재하지 않는다.
- 모든 사람 참가자가 수색 맵에 들어오고 수색 단계가 시작되면 서버가 생성한다.
- 플레이어 배열과 별도의 안정된 NPC ID, 생존/기절/소지 상태, 네트워크 복제 상태를 가진다.
- 사람의 배정 물건, 숨기기 차례, 승리 판정 인원에는 포함되지 않는다.
- 기존 `BotProfile`과 봇 좌석 코드는 KCC 동기화 실험과 구분한다. NPC가 사람인 것처럼 `PlayerRef.None`을 사람 요청에 넣거나 가짜 `playerIndex`를 할당하지 않는다.

사람과 NPC가 공유할 것은 신분이 아니라 **규칙의 작은 부품**이다. 예를 들어 “2m 안인가?”, “이미 다른 손에 들렸나?”, “놓을 위치가 정상인가?”는 같은 자를 사용한다. 반면 “지금 내 숨기기 차례인가?”와 “내 배정 물건인가?”는 사람에게만 묻는다.

## 1. 하나의 학습 경로

작은 Unity 연습장 → 봇이 볼 수 있는 정보 → 모델의 선택 → NPC용 이동·행동 실행부와 공통 물건 검사 → 실제 성공/실패 → Python 학습 → ONNX 모델 → 같은 실행부로 수색 단계 게임에서 평가.

연습 때와 시험 때 다른 자전거를 타지 않게 하는 것이 핵심이다. 기존 Reach의 CharacterController를 새 게임 봇의 KCC 대신 사용해 성능을 그대로 주장하지 않는다.

- 연습장: 기존 `Training_KCC`를 기준으로 별도 학습용 씬/프리팹을 구성. 로컬 Fusion `GameMode.Single`과 실제 KCC 실행 경로를 먼저 검증한다. Photon Cloud, 음성, 계정 로그인, 방 목록은 학습의 선행 조건으로 두지 않는다.
- 실행부: 실제 들기·놓기의 거리·점유·자세 판정을 공유한다. 플레이어 상태를 요구하는 규칙과 NPC 상태를 분리하고, 순수 판정과 네트워크 전달을 나눠 단일 실행에서도 같은 판정을 부를 수 있게 한다. 필요하면 분리 비용 때문에 범위를 줄이지, 가짜 성공 판정으로 대체하지 않는다.
- 초기에는 한 환경, 한 봇. 초기화가 검증되면 서로 상태가 섞이지 않는 소수 환경을 추가한다. 장비 처리량을 측정한 뒤 병렬 수를 정한다.
- 학습 알고리즘은 기존 경험이 있는 PPO부터 사용한다. PPO는 “여러 번 시도하고 점수가 나아지는 쪽으로 선택 습관을 조금씩 고치는 방법”이다. 시범 기록을 이용한 BC는 선택 사항이다. [ML-Agents 학습 설정](https://unity-technologies.github.io/ml-agents/Training-Configuration-File/)

## 2. 첫 학습 문제와 실전 목표

### 실전에서 봇이 물건으로 하려는 것 (2026-09-23 확정)

- **목표 1 (기본):** 수색 맵의 일반 소품을 골라 집고 다른 곳에 옮겨 놓아 수색자를 교란한다. 소유자 정보는 쓰지 않는다.
- **목표 2 (확장):** 파쇄기에 넣을 수 있는 소품을 골라 운반해 기존 파쇄 규칙으로 투입한다.
- **범위 밖:** 플레이어가 숨긴 물건을 추정해 노리기. 소유자 ID는 비공개라 쓸 수 없고, 사람이 볼 수 없는 단서를 쓰면 치트다. 별도 설계가 필요하다.

### 모델은 물건의 이름을 배우지 않는다

봇은 게임의 모든 CarryableItem을 다뤄야 한다. 손(집기 심판)은 이미 모든 물건에 같은 규칙을 적용한다. 그래서 두뇌도 **물건의 이름이 아니라 판단에 쓰이는 성질**로 후보를 본다. 성질은 물건 종류가 몇 개든 전부 계산할 수 있으므로, 새 물건이 추가되어도 재학습이 필요 없다.

- 후보의 성질: 거리, 방향, 크기 등급, 파쇄 가능 여부, 다른 행위자가 들고 있는지, **현재 목표에 맞는지(0/1)**, 마지막 관측 나이.
- "목표에 맞는지"는 실행부 코드가 계산한다. 어떤 규칙으로 켜는지는 게임 모드가 정한다.

| 모드 | 목표 일치 칸을 켜는 규칙 |
| --- | --- |
| 연습(학습 씬) | 에피소드마다 무작위로 뽑은 요청 종류와 같은 종류 스티커(`BotSightKind`)를 가진 물건 |
| 실전 목표 1 | 들 수 있는 모든 일반 소품 |
| 실전 목표 2 | 파쇄기에 투입 가능한 소품 |

모델은 스티커 값 자체를 보지 않는다. 종류 스티커는 연습 규칙을 만드는 재료일 뿐이다.

### 첫 학습 문제

한 에피소드는 "목표에 맞는 물건을 제한 시간 안에 실제로 집기"다. 후보가 2~3개 있고 그중 일부만 목표에 맞게 배치해 선택이 필요하게 한다. 맞는 물건이 더 멀고 틀린 물건이 더 가까운 배치를 반드시 섞는다. 같은 종류만 놓고 가장 가까운 물건에 자동 이동하는 문제로 끝내지 않는다.

초기 과제는 인간 행동이나 승리 전략 학습이 아니라 **성질을 보고 목표에 맞는 물건을 고르고, 안 보이면 탐색을 고르는 능력**이다. 이후 운반·파쇄·위험 판단 학습의 출발점으로 삼는다.

솔직한 범위: 후보 3개와 성질 몇 개로 v1 모델이 배우는 판단은 크지 않다. 이 실험은 "AI가 대단하다"가 아니라 **학습한 판단이 실제 게임 실행부와 연결되어 무작위·최근접 규칙 기준선을 재현 가능하게 이긴다**를 증명하는 것이다.

## 3. 정보 약속 — 봤을 때의 메모만 전달

시야 결과는 Transform 참조가 아닌 스냅샷("사진") 두 장이다(2026-09-23 구현 완료).

- 정책용 관측 `BotSightObservation`: 눈 기준 방향, 정규화 거리, 종류 키, 관측 시각.
- 실행부용 손잡이 `BotSightTargetHandle`: 대상 ID(`IBotSightTarget` 답변, 게임의 ObjectId), 관측 당시 월드 위치, 관측 시각. 정책에는 절대 전달하지 않는다. 실행부는 그 위치로 이동한 뒤 **다시 관측**해서 확인한다.

관측 벡터 v1 제안(성질 기반):

| 묶음 | 칸 | 내용 |
| --- | ---: | --- |
| 자기 상태 | 6 | 손 점유(0/1), 남은 시간 비율(0~1), 실행 중(0/1), 직전 결과 원핫 3칸(없음/성공/실패) |
| 후보 슬롯 1 | 11 | 존재(0/1), 방향 X, 방향 Z, 거리(0~1), 크기 등급 원핫 3칸(작/중/대), 파쇄 가능(0/1), 타인 점유(0/1), 목표 일치(0/1), 관측 나이(0~1) |
| 후보 슬롯 2 | 11 | 같은 형식 |
| 후보 슬롯 3 | 11 | 같은 형식 |
| 실행 피드백 | 5 | 직전 실패 종류 원핫(없음/길 없음/막힘/대상 소실/거절) |
| **합계** | **44** | |

- 후보는 보이는 물건에서만, **가까운 순**으로 채운다. 빈 슬롯은 전부 0. 후보 순서 변경으로 다른 물건을 집지 않도록 실행 중 대상 ID는 손잡이로 따로 고정한다.
- 크기 등급은 콜라이더 경계 상자의 최대 변 길이로 나눈다. 경계값은 구현 시 확정해 테스트로 잠근다.
- 파쇄 가능과 타인 점유는 v1 학습 씬에서 각각 항상 1, 항상 0이다. 나중에 칸 수를 바꾸지 않기 위해 지금 넣는다.
- 모든 값은 -1~1 또는 0~1 범위. 필드 순서·정규화·기본값을 테스트로 잠근다. 칸을 추가하면 새 버전이며 옛 ONNX를 그대로 쓰지 않는다.
- 사라진 물건은 마지막 목격 좌표만 최대 2초 기억하는 것으로 시작한다. 새로 관측하기 전에는 현재 위치를 조회해 쫓지 않는다.
- 시야 판정의 부모/자식 누출(선반 자식, 들고 있는 사람)은 2026-09-23 수정·테스트 완료. Raycast 버퍼 32/근처 후보 64 포화 시 낙관 문제는 테스트만 추가하고 수정은 보류.
- 정적 길 지도는 사전 지식으로 허용할 수 있지만, 숨겨진 물건 위치와 방문하지 않은 곳의 실시간 상태를 관찰에 넣지 않는다.

## 4. 행동 약속 — 모델은 선택, 실행부는 수행

첫 모델은 이산 행동 5개로 시작한다: `Continue`, `Explore`, `CollectSlot0`, `CollectSlot1`, `CollectSlot2`.

- 모델은 0.5초 간격의 일정한 시뮬레이션 시간으로 판단한다. 매 프레임 판단하지 않는다.
- 집기 동작 중에는 Continue를 기본으로 하고, 성공/실패/시간 초과 때 다음 선택을 받는다. 동작 잠금은 모든 정책에 동일하다.
- Explore는 유효한 방문 지점으로 이동한다. 물건이 없는 곳에서 회전 관찰도 가능하게 한다. 탐색 지점은 비밀 물건 좌표로 고르지 않는다.
- Collect는 선택 당시 후보 ID와 관측 위치를 고정하고 이동→재관측→거리 확인→실제 집기 요청을 수행한다.
- 경로 없음, 2초간 이동 진전 없음, 대상 소실, 집기 거절을 실패로 반환한다. 전체 동작 시간 초과는 초기 8초로 두고 작은 맵 크기에 맞춰 검증한다.
- 없는 후보·손 점유 등의 불가능한 선택은 마스크로 차단한다. “정답 아닌 물건”까지 전부 차단하면 모델이 배울 선택 문제가 사라지므로 그러지 않는다.
- Continue/Explore 등 적어도 하나는 항상 유효하다. 상태 바뀜으로 거절된 요청은 정해진 실패 경로로 돌린다.

게임 내 안전 규칙은 모델 위에 존재하지만, 정상적인 선택을 항상 규칙으로 바꿔치기하지 않는다. 추론 실패/잘못된 모델 버전일 때만 명시적인 fallback 모드로 전환하고 횟수를 기록한다.

### NPC 권한과 소지 상태

- NPC는 서버에서만 행동하고 클라이언트 RPC를 보내지 않는다.
- 물건의 소유 표현은 사람의 `HolderPlayerIndex`만으로는 부족하다. NPC 소유자를 구분할 수 있는 별도 상태를 두거나, 사람/NPC를 함께 표현하는 명시적 actor 참조로 확장한다.
- 첫 구현은 이 표현을 먼저 고정한 뒤 실제 `CarryableItem`을 연결한다. 화면에서만 손에 붙이거나 `CarryableItem.OnPickedUp`을 직접 호출해 성공으로 만들지 않는다.
- 수색 단계가 아니거나 NPC가 아직 생성되지 않았거나 손이 차 있으면 요청을 거절한다.
- NPC가 제거되거나 경기가 끝나면 들고 있던 물건을 권위 상태에서 먼저 내려놓고 NPC 상태를 지운다.

## 5. 보상과 초기화

초기 보상 제안값:

- 목표 일치 물건 실제 집기 확정: +1, 에피소드 성공 종료.
- 목표 불일치 물건 실제 집기: -0.2, 실패 종료.
- 시간 비용: 시뮬레이션 1초당 -0.005. 에피소드 제한 초기 30초.
- 시간 초과: -0.2, 실패 종료.
- 거리 접근 보상은 첫 버전에서 생략. 필요하면 왕복하며 점수를 버는 문제가 없는지 검증한 후 추가한다.

명령 호출, 목표 설정, 애니메이션 시작에 성공 보상을 주지 않는다. 보상은 확정 이벤트에 한 번만 지급한다. 지연 도착한 이전 에피소드 이벤트는 에피소드 ID로 무시한다.

초기화는 손 상태/소유 상태/물건 활성화·물리 속도/봇 위치와 속도/쿨다운/경로/기억/현재 행동/보상 플래그를 모두 되돌린다. 같은 seed 초기 상태가 재현되는지 확인한다.

학습 난이도는 가까운 복수 후보 → 거리·방향 무작위 → 벽과 탐색 필요 배치 순서로 높인다. 도달 불가능하거나 목적 물건이 없는 배치를 정상 성공 과제에 섞지 않는다. 그런 상황의 안전 포기는 별도 시험한다.

## 6. 데이터·학습·평가 운영

실제 사용자 행동 기록은 필수가 아니다. 이 버전은 연습장에서 스스로 만든 시도와 결과로 학습한다. 사용자 기록이 있어야만 AI라는 뜻은 아니다.

시범을 추가한다면 개발자가 **같은 5개 선택 명령**으로 시범을 보이거나 Heuristic 정책으로 만들고 DemonstrationRecorder로 기록한다. 키보드 이동 녹화가 곧바로 이 모델의 선택 정답이 되지는 않는다. 수집 연결이 길어지면 BC는 보류한다. [ML-Agents 개요](https://unity-technologies.github.io/ml-agents/ML-Agents-Overview/)

1. **기준선:** 유효 행동 중 무작위 선택 정책과 목표 일치 최근접 후보 규칙 정책을 구현한다. 목표를 무시하는 단순 최근접 규칙(2026-09-23 실행기)도 비교 대상으로 남긴다. 같은 시야·기억·실행부를 쓴다.
2. **연결 시험:** 기존 Reach PPO 설정을 출발점으로 작은 실행. 새 Behavior Name, 관찰/행동 크기, 성공 이벤트를 점검한다. Reach 모델을 새 모델처럼 쓰지 않는다.
3. **훈련:** 학습 seed와 배치를 바꾸며 실행. steps 예산은 첫 처리량 측정 후 정한다. 이전 max_steps=100000이 새 과제에도 충분하다고 가정하지 않는다.
4. **개발 평가:** 별도의 고정 배치로 실패 이유를 보고 한 번에 한 원인만 수정한다.
5. **최종 평가:** 튜닝에 쓰지 않은 100개 배치를 모든 정책에 동일 적용. 성공률/시간/정답 아닌 물건/막힘/거절/fallback을 기록한다.
6. **게임 추론:** ONNX를 같은 관찰·행동 계약의 Agent에 연결한다. 학습 모드를 끄고 모델이 실제 선택한 행동 ID를 기록한다. 모델 연결 방식은 기존 ML-Agents 경로를 우선하며 별도 추론 프레임워크를 새로 만들지 않는다. [공식 시작 안내](https://unity-technologies.github.io/ml-agents/Getting-Started/)

**초기화 속도 저하 감시:** 5절의 부분 초기화는 학습이 길어질수록 정리되지 않은 상태나 가비지가 누적되어 에피소드당 시간이 늘어날 수 있다. 참고 매뉴얼의 스퀴드워 팀은 같은 방식으로 시작해 수만 에피소드 뒤 느려져 전부 초기화로 바꿨다. 학습 실행마다 처음 1000 에피소드와 이후 구간의 에피소드당 실제 시간, 초당 스텝 수, 메모리 사용량을 함께 기록한다. 에피소드당 시간이 초기 대비 뚜렷하게 늘면 남은 상태부터 찾고, 원인을 못 찾으면 시험 씬 재로드 방식과 비교한다. 느려짐을 학습 시간 연장으로 덮지 않는다.

첫 모델은 작은 벡터 입력의 PPO, 기존 2층 64유닛을 출발점으로 한다. 영상 학습/거대 모델/LLM 실시간 호출/자기대전은 이번에 추가하지 않는다. 목표는 화려한 이름보다 재현 가능한 성능이다.

에디터에서 빠르게 반복하고, 처리량이 부족할 때만 전용 Windows 학습 빌드를 만든다. Web은 Python 학습 환경으로 쓰지 않으며 최종 Web 추론 검증이 필요할 때만 빌드한다. 기존 Web TensorProxy 수정은 호환성 위험 목록에 남기고 패키지 버전을 함부로 바꾸지 않는다.

## 7.1 개발자와 AI 조력자의 학습 반복 방식

이 작업은 지환의 취업 포트폴리오이기도 하다. 그래서 결과물만이 아니라 **어떻게 고민하고 기획하고 구현했는지**가 기록으로 남아야 한다. 역할은 다음과 같이 나눈다.

- 지환: 파이프라인 설계, 관찰·행동·보상 결정, 학습 실행, 결과 확인, 최종 선택. 학습 명령과 Unity 조작은 직접 수행한다.
- AI 조력자: 설계 검토, 개념 설명, 대안과 위험 제시, 결과 해석 보조, 문서 정리 보조. 지환이 결정하기 전에 대신 결정하거나, 지환이 실행할 단계를 대신 실행하지 않는다.

각 주요 결정마다 아래 형식으로 결정 기록을 남긴다. 실험 기록 문서에 실행 ID와 함께 적는다.

| 항목 | 내용 |
| --- | --- |
| 결정 | 무엇을 정했나 |
| 근거 | 어떤 실패 증거나 측정값, 참고 자료 때문인가 |
| 검토한 대안 | 함께 고려했던 다른 선택 |
| 기각 이유 | 대안을 택하지 않은 이유 |
| 확인 방법 | 이 결정이 옳았는지 무엇으로 판단할 것인가 |

아래 반복을 함께 수행한다.

1. 관찰·행동·보상·종료 조건을 먼저 문서와 테스트로 고정한다.
2. 학습 전에 무작위 정책과 간단한 규칙 정책이 같은 환경을 완주하는지 확인한다.
3. 짧은 진단 학습으로 실제 성공, 잘못된 물건 선택, 막힘, 시간 초과, 권한 거절을 각각 기록한다.
4. 결과를 보고 가장 큰 실패 원인 하나만 고친다. 여러 값을 동시에 바꿔 무엇이 효과였는지 모르게 만들지 않는다.
5. 새 실행 ID로 다시 학습하고, 학습에 사용하지 않은 같은 평가 배치에서 이전 결과와 비교한다.
6. 통과한 ONNX만 게임에 연결하고, 모델이 고른 행동이 규칙 코드에 의해 몰래 바뀌지 않았는지 로그와 화면으로 함께 확인한다.

신경망 내부의 가중치는 PPO가 학습 중 자동으로 바꾼다. 사람이 직접 조절하는 주요 손잡이는 보상 계수, 학습률, 배치 크기, 탐색 정도, 관찰값, 행동 간격과 과제 난이도다. 사용자가 말하는 “가중치 조정”이 보상 점수를 뜻하는지 학습 설정을 뜻하는지 결과표에서 구분해 기록한다.

각 조정 제안에는 다음을 함께 남긴다.

- 어떤 실패 증거 때문에 바꾸는가
- 정확히 한 번에 무엇을 바꾸는가
- 좋아졌다고 판단할 측정값은 무엇인가
- 나빠졌을 때 어떤 설정으로 되돌아가는가

## 8. 첫 모델 다음의 확장 순서

1. 운반·놓기·파쇄·공격·숨기기 실행부 각각을 코드 입력으로 검증.

## 9. v2 과제 — 들고 있는 물건을 어디에 놓을까 (2026-09-25 확정)

### 왜 이 과제인가

v1(집기 선택)은 목표 일치 정보가 관측에 그대로 있어 학습 모델이 규칙과 같은 답에 수렴했다(행동 합계까지 동일). 강화학습의 가치를 보이려면 **정답이 관측에 직접 없고, 관측 가능한 단서로부터 추론해야 하는** 판단이 필요하다. "수색자 눈에 덜 띄는 자리"는 실전 목표 1(옮겨서 교란)의 핵심이면서 이 조건을 만족한다.

### 확정 결정

| # | 결정 | 근거 |
| --- | --- | --- |
| D1 | 집기 모델(PickSelect v1.1)은 고정, **놓기 모델(PlaceSelect)을 별도 Behavior로** 학습 | 역할 분리(매뉴얼 63쪽 파일럿-터렛 분리). 기존 모델 재학습 불필요, 각자 평가 가능 |
| D2 | 학습 장소는 **저택 지형** | 숨기 좋은 자리는 실제 같은 지형에서만 배울 수 있다. 빈 학습장에는 구석이 없다 |
| D3 | 학습 중에는 **걷지 않고 자리 선택 즉시 평가**(순간이동 평가) | 걷기는 3a에서 검증한 코드. 걸으면 결정당 5~10 s로 학습 불가. 대신 학습 후 3a 샌드박스에서 실제로 걸어가 놓는 검증을 따로 한다 |
| D4 | 보상 = 숨김 + 원래 자리에서 거리(작게) − 걷는 경로 길이(작게) | 숨김만 보면 먼 곳만, 거리만 보면 가까운 곳만 고른다. 계수는 한 번에 하나씩 조정 |

범위 밖: "얼마나 자주 옮길지"는 학습하지 않고 게임 설정값으로 둔다. 선반·식탁 위 놓기는 v2.0에서 제외(바닥만).

### 한 에피소드

한 번의 결정으로 끝난다(단일 단계). 봇이 저택 NavMesh 위 무작위 위치에서 물건을 든 채 서 있고, 주변 1.5~8 m 안에서 경로 12 m 이하로 갈 수 있는 **후보 자리 4곳**이 주어진다. 모델이 하나를 고르면 보상을 받고 끝난다. 물리 봇이 없으므로 Fusion 없이 돌고, 한 씬에 Agent 여러 개를 두어 병렬로 학습한다.

### 관측(place-obs-v2-63)

| 묶음 | 칸 | 내용 |
| --- | ---: | --- |
| 자기 상태 | 3 | 들고 있는 물건 크기 원핫(작/중/대) |
| 후보 슬롯 ×4 | 15 | 존재, 방향 X/Z(봇 기준), 경로 길이/12, 직선 거리/8, 후보 지점 0.4 m 높이에서 8방향 광선 거리(가까운 순 정렬, /5), 머리 위 가림 여부, 가림 높이/2.5 |
| 합계 | 63 | |

**숨김 점수 자체는 관측에 넣지 않는다.** 모델은 "사방 광선이 짧다 = 좁은 구석", "머리 위가 막혔다 = 탁자 아래" 같은 지형 단서에서 숨김을 추론해야 한다. 8방향 광선을 정렬하는 이유는 방향과 무관한 "둘러싸인 정도"만 남기기 위해서다.

### 보상

- 숨김 = exp(−보이는 수색 지점 수 / 20). (2026-09-25 기준값 8→20: 흔한 노출 10~30곳에서 점수가 압축되어 가점·감점과 비슷해지던 문제) 수색 지점은 저택 NavMesh 전체에 면적 비례로 뿌린 400곳(눈높이 1.5 m). 15 m 안의 지점에서 물건 중심까지 광선이 고정 지형(Default 레이어)에 막히지 않으면 "보인다".
- 총 보상 = 1.0 × 숨김 + 0.1 × (직선 거리/8) − 0.1 × (경로 길이/12).
- 들 수 있는 물건(Carryable)은 가림으로 치지 않는다. 움직이기 때문이다.

### 기준선

같은 관측으로 돌리는 규칙 정책 3개와 상한 1개.
- 무작위, 가장 가까운 자리, **가장 둘러싸인 자리**(광선 평균이 가장 짧고 머리 위가 막힌 곳 우대) — 사람이 짤 법한 규칙
- 오라클: 숨겨진 참 보상을 직접 계산해 고르는 부정행위 정책. 도달 가능한 최대치로만 쓴다

통과 기준 제안: 미사용 고정 배치 1,000회에서 평균 보상이 "가장 둘러싸인 자리" 규칙보다 높고, 오라클과 같은 자리를 고른 비율이 무작위(25%)보다 뚜렷이 높을 것. 규칙보다 못하면 그대로 보고한다.

### 검증 순서

1. 관측 인코더·보상 함수 EditMode 테스트
2. 기준선 4종 평가(학습 없이) — 규칙과 오라클의 차이가 작으면 과제가 너무 쉬운 것이니 후보 수·범위부터 조정
3. PPO 학습 → 같은 배치로 비교
4. 3a 샌드박스에서 집기(v1.1) → 놓기(v2) 연결, 실제로 걸어가 놓는지 확인

### v2.1 관측 (2026-09-25)

v2 모델이 사람 규칙과 동급(0.470 대 0.469)에 머물렀고, 원인을 관측 정보 부족으로 본다. v2.1은 v2 관측을 **그대로 두고 시선 광선만 추가**한 상위 집합이다. 성능 차이를 추가 정보 덕분이라고 분리해 말하기 위해서다.

- 후보 한 칸: v2의 15칸 + 시선 광선 32칸 = 47칸. 전체 191칸(`place-obs-v21-191`).
- 시선 광선: 물건 중심에서 16방향으로, 수평 4 m(가까움)·12 m(멂) 떨어진 **눈높이 1.5 m 지점**을 향해 쏜다. 값 = 고정 지형에 막힌 거리 / 광선 길이(1 = 끝까지 트임). 층마다 오름차순 정렬해 "몇 방향에서 트였나"만 남긴다.
- 숨김 점수는 여전히 비공개. 사람 규칙("가장 둘러싸인 곳")은 v2와 같은 낮은 광선만 쓰므로 바뀌지 않는다.
- v2 씬·모델은 그대로 재현 가능. v2.1은 별도 씬(`Mansion_PlaceTraining_v21`, 메뉴 "Build Mansion Place Training (v2.1 sightlines)"). Agent의 `observationVersion`으로 구분.
- 학습 설정 파일은 v2와 동일(한 번에 하나만 바꿈). 실행 ID `place-v21-seed101`.
