## 1. 최종 목표와 출시 범위

### 1.1 우리가 만들 봇

봇은 빈자리를 채우는 참가자다. 사람과 같은 이동 속도, 상호작용 거리, 들기 규칙, 파쇄 횟수, 공격 간격, 기절, 스태미나 제한을 적용받는다. 판단과 입력은 경기 권한을 가진 호스트가 만들고, 다른 참가자는 확정된 동작을 본다.

| 상황 | 최종적으로 필요한 행동 | 완료했다고 판단할 증거 |
| --- | --- | --- |
| 참가 | 좌석 배정, 외형 생성, 물건 배정, 재경기 | 1명 사람+5명 봇이 경기 종료 후 로비로 복귀 |
| 인식 | 눈앞의 물건·플레이어·가림 여부 파악 | 벽 뒤 물건이 관찰값에 새어 들어가지 않음 |
| 이동 | 목적지 접근, 장애물 우회, 끼임 회복 | 다른 배치에서도 상호작용 거리까지 도착 |
| 일반 소품 조작 | 상자 등을 들고 옮겨 공간을 만들거나 물건을 가림 | 목표 소품을 옮기고 원래 목표를 수행 |
| 숨기기 | 내 물건을 접근 가능한 장소에 숨기고 차례 종료 | 시간 안에 배치되고 실제로 회수 가능 |
| 탐색 | 방문하지 않은 구역 탐색, 본 물건 기억 | 숨긴 위치를 미리 알지 않고 발견 |
| 탈취·파괴 | 상대 물건 확보, 파쇄기로 운반, 파쇄 | 서버가 유효한 파괴를 확정 |
| 전투 | 접근·조준·공격·거리 조절·도주 | 피격과 기절 규칙을 지키며 목적에 맞게 싸움 |
| 회수·보호 | 내 물건 마지막 목격지 확인, 회수, 위협 회피 | 제한 시간 종료 때 직접 보유 |
| 마무리 | 결과·하이라이트·재경기 | 봇 때문에 페이즈나 화면이 멈추지 않음 |

승리 조건의 원본은 `MatchOutcomeSystem.GetWinnerPlayerIndices()`다. **종료 순간 자기 물건을 직접 들고 있는 플레이어가 승자**이며 여러 명이 동시에 승리할 수 있다. 따라서 6인 게임의 정상 승률을 무조건 1/6로 잡지 않는다. 상대를 많이 때리거나 물건을 많이 부숴도 자기 물건을 회수하지 못하면 최종 목표를 달성하지 못한 것이다.

### 1.2 출시를 두 번으로 나누기

- **첫 공개 가능한 버전:** 한 개의 검증된 맵에서 참가→숨기기→탐색→집기→운반·파쇄→기본 공격·도주→내 물건 회수→결과까지 수행. 일반 소품 조작은 지정된 크기·개수·배치 범위에서 지원한다.
- **전체 확장 버전:** 다양한 소품 배치, 복잡한 은폐 전략, 동적 장애물, 추가 맵, 던지기·점프·앉기·엎드리기 등을 조합한다. 기능별 학습과 회귀 검증을 통과하며 범위를 늘린다.

첫 버전에 모든 임의의 물리 퍼즐을 해결할 능력을 요구하지 않는다. 하지만 일반 소품 이동을 영구히 제외하지도 않는다. 사용자가 원하는 기능이므로 독립된 필수 단계로 다룬다. 해결하지 못하는 구조에서는 포기·다른 경로·다른 목표 선택이 가능해야 한다.

### 2.2 이전 안내에서 보완할 부분

1. 공식 예제를 실행한다고 Python 패키지를 반드시 Git 로컬 설치로 바꿀 필요는 없다. 호환 조합이면 기존 설치를 사용할 수 있으며 실제 3DBall 연결도 성공했다. 별도 환경은 필요할 때 선택한다.
2. `release_23` 예제와 현재 게임의 Unity ML-Agents 4.1.0을 같은 버전이라고 보지 않는다. 게임 프로젝트에서도 Python 연결, ONNX 출력, Unity 단독 실행을 따로 통과해야 한다.
3. 같은 캐릭터 외형을 쓴다고 같은 물리 환경이 되는 것은 아니다. 연습용 이동체와 실제 KCC의 차이를 측정해야 한다.
4. 움직임 학습 모델과 전략 선택 모델은 입력·출력이 다르다. 여러 모델 파일을 붙이면 자동으로 전체 게임을 배우는 것이 아니다. 학습 실습과 제품용 모델을 구분한다.
5. 6인 개인전에서 YAML에 `self_play`만 추가하면 모든 경쟁 문제가 해결되는 것은 아니다. 상대를 고정한 실험부터 단계적으로 확장한다.
6. 평균 보상이 두 번 올랐다는 것만으로 안정적인 학습 성공을 선언하지 않는다. 새 배치와 여러 시드에서 실제 과제 성공률을 측정한다.
7. `Server`는 Fusion과 분리되어 있지만 완전히 Unity와 무관하지 않다. 현재 asmdef와 규칙 코드에는 UnityEngine·SOAP·VContainer 의존이 있다. 별도 Python 프로세스에서 그대로 실행되는 코드는 아니다.
8. 예제 버전 6000.0.40f1에 보안 경고가 있었는데 이전에 이를 가장 안전한 버전이라고 안내한 것은 부정확했다. 향후 학습 빌드와 공개 배포는 팀이 검증한 보안 수정 에디터로 만든다. 해당 Unity 공지는 6000.0 계열 수정 버전을 6000.0.58f2로 명시한다. [Unity 보안 공지](https://unity.com/security/sept-2025-01)

## 3. 개발하며 공부하는 방식

한 회차는 60~120분 정도의 작은 작업으로 나눈다. 실제 가능한 시간에 맞춰 조정한다.

1. **개념:** 일상 비유와 게임 상황으로 새 개념 하나를 이해한다.
2. **예측:** 실행하기 전에 어떤 행동·로그가 나올지 적는다.
3. **구현:** 개발자가 직접 작은 기능을 작성한다. 한 번에 완성 코드 전체를 붙이지 않는다.
4. **확인:** 수동 조작 또는 짧은 실험으로 가설을 검사한다.
5. **설명:** 어떤 정보가 들어가고 어떤 행동과 보상이 나왔는지 자신의 말로 설명한다.
6. **기록:** 바꾼 것, 결과, 다음 한 가지 질문을 남긴다.

가이드는 설계·코드 읽기·오류 해석·리뷰·실험 비교를 돕는다. 구현을 대신 요청받기 전까지 사용자의 실습을 중심으로 진행한다. 학습이 실패하면 먼저 환경·관찰·행동·보상을 확인하고 마지막에 알고리즘 설정을 바꾼다.

| 용어 | 쉬운 뜻 | 우리 봇 예시 |
| --- | --- | --- |
| Agent | 결정을 내리는 참가자 | 경기 속 봇 한 명 |
| 관찰 Observation | 지금 전달받은 상황 메모 | 눈앞의 상자, 남은 시간 |
| 행동 Action | 선택할 수 있는 조작 | 상자로 이동, 집기 요청 |
| 보상 Reward | 연습 중 받는 채점 | 물건 집기 성공 +점수 |
| 정책 Policy | 상황별 행동을 고르는 습관 | 위험할 때 물건을 들고 도망 |
| 에피소드 Episode | 한 번의 연습 판 | 시작 위치 초기화부터 집기 성공까지 |
| 추론 Inference | 배운 습관을 사용 | 배포 게임에서 행동 선택 |
| 시드 Seed | 무작위 배치를 재현하는 번호 | 같은 장애물 배치로 두 모델 비교 |
| 커리큘럼 | 쉬운 문제부터 난도를 올림 | 물건 1개→여러 물건→가림 |
| 기준 봇 Baseline | 비교할 단순한 상대 | 가까운 물건부터 줍는 규칙 봇 |
| 일반화 | 처음 보는 문제에서도 성공 | 학습에 없던 선반 배치에서 회수 |
| 마스크 Mask | 지금 불가능한 선택을 막음 | 손이 차 있으면 추가 집기 금지 |

PPO는 경험을 모아 행동 습관을 조금씩 고치는 학습법으로 시작한다. PPO 논문 수식 전체를 외우는 것을 첫 구현의 전제조건으로 두지 않는다. 다만 정책·누적 보상·할인·학습용/평가용 데이터 구분은 설명할 수 있어야 한다.

## 4. 전체 흐름과 기술 구조

### 4.1 전체 흐름

```text
환경 설치·3DBall 연결 확인 [완료]
  → 우리 캐릭터로 수동 테스트 씬
  → 단순 도달 과제 학습 + ONNX 단독 실행
  → 실제 KCC·상호작용 연결을 조기에 검증
  → 시야·집기·일반 소품 이동·숨기기
  → 탐색·운반·파쇄·전투·회수
  → 전체 경기 전략 학습
  → 실제 맵·상대·규칙을 바꾼 평가
  → 호스트 봇 연결·성능·WebGL 검증
  → 내부 테스트 → 제한 공개 → 정식 배포
  → 로그·피드백 → 재학습 → 검증된 모델 업데이트
```

각 단계의 통과 기준을 만족해야 다음 큰 단계로 넘어간다. 소요 시간이 늘면 평가를 생략하는 대신 출시 범위를 줄인다.

### 4.2 권장 제품 구조: 판단과 실행 분리

상위 판단은 “어느 물건을 회수할까?”를 정한다. 실행기는 “어떤 길로 이동하고 어느 거리에서 집기 요청을 보낼까?”를 처리한다. 택시 승객이 목적지를 말하면 운전사가 도로 규칙을 지키며 가는 구조다.

```text
시야·자기 상태·공개 정보·기억
  → 공통 관찰 생성기
  → 규칙 정책 또는 학습 정책
  → 목표와 행동 선택
  → 실행기: 길찾기 / 운반 / 배치 / 전투
  → 사람과 같은 입력·판정
  → 결과·네트워크 동기화
```

처음에는 개발자가 이해하기 쉬운 연속 이동 학습을 짧게 해본다. 제품용 기본 구조는 길찾기와 규칙 검증을 재사용하는 상위 판단 모델이다. 꼭 필요한 경우에만 배치 조절·전투 간격 같은 하위 기술을 별도 모델로 추가한다. 하나의 거대한 모델에 모든 물리 조작을 맡기는 방안은 비교 실험 이후의 선택지다.

### 4.3 파일과 어셈블리 배치 제안

아래는 **앞으로 만들 설계**이며 현재 존재하는 폴더 목록이 아니다. 실제 추가 시 `.meta`와 asmdef 의존 규칙을 함께 확인한다.

```text
Assets/_Game/
  Core/Bots/                 관찰·행동·실행 결과 타입, 인터페이스
  Server/Bots/               규칙 정책, 목표 유지·전환, 공통 결정 규칙
  BotRuntime/                새 Game.BotRuntime 어셈블리 후보
    Perception/              Unity 물리로 시야 검사
    Navigation/              경로와 다음 이동 방향
    Policies/                ML-Agents 추론 어댑터
  Network/Players/           호스트 봇 입력·스폰 연결
  Bootstrap/                실제 게임에서 필요한 구현 조립
  Training/                 새 Game.Training 어셈블리 후보
    Agents/                 실험용 Agent
    Environments/           초기화·보상·에피소드 종료
    Evaluation/             학습하지 않는 반복 평가
  Content/Training/          테스트 씬·훈련 전용 프리팹
  Content/Config/Bots/       난이도·승인된 모델·모델 정보
  Tests/                    규칙·관찰·통합 회귀 테스트
Tools/training/             YAML·실행/평가/빌드 스크립트
docs/planning/              이 계획서·실험 기록
```

- Core는 UnityEngine·Fusion·ML-Agents를 참조하지 않는다. 위치 같은 값은 엔진 독립 타입으로 주고받는다.
- BotRuntime은 Core와 필요한 Unity 패키지에 의존한다. Client↔Server 직접 의존을 만들지 않는다.
- 학습 Agent와 런타임 추론이 동일한 관찰 생성·행동 해석을 사용하도록 공통 부분을 BotRuntime/Core에 둔다.
- Training은 Core·Server·SOAP·BotRuntime·ML-Agents 등 실제로 필요한 참조를 명시한다. “Server와 Core만 참조”로 센서와 Agent까지 구현할 수 있다고 가정하지 않는다.
- Fusion 연결은 Network/Bootstrap에 둔다. BotRuntime은 `PlayerRef`를 받지 않는다.
- Training을 `Editor` 전용 asmdef로 만들지 않는다. 클라우드용 실행 파일에도 들어가야 한다. `GAME_TRAINING` 같은 별도 빌드 조건과 Training Build Profile을 설계한다.
- Game Release Profile에서는 학습 씬·보상·초기화 도구가 빠져야 한다. 런타임 추론에 필요한 ML-Agents 코드는 남을 수 있다.
- ProjectLifetimeScope의 사전 로드 때문에 학습 씬에서 로그인·Photon·홈 화면이 자동 시작되는지 먼저 확인한다. 학습 전용 조립 경로가 필요하다.

## 5. 관찰·행동·기억의 약속

### 5.1 “물건 인식”의 의미부터 정하기

첫 제품 모델은 카메라 이미지에서 사과를 알아보는 별도 영상 인식 모델을 만들지 않는다. Unity의 물체 정보를 **시야 검사를 통과한 경우에만** 제한적으로 전달한다. 눈앞의 물건을 보고 “가까운 상자 하나”라고 메모해 주는 방식이다.

이를 위해 후보 물건 선택→거리 검사→시야각 검사→벽·다른 소품에 가려졌는지 검사 순서가 필요하다. Layer와 Tag는 후보를 찾는 내부 도구이지, 벽 뒤 물건 정답을 알려주는 허가증이 아니다.

누구의 배정 물건인지도 게임에서 사람이 알 수 있는 범위까지만 제공한다. 소유자가 보이지 않는 규칙이라면 봇 관찰에도 `ownerIndex`를 제공하지 않는다. 가까이서 확인해야 아는 정보라면 같은 확인 행동을 거친다.

물체 정보 기반 방식의 한계는 크기·색·복잡한 가림이 사람의 시각과 정확히 같지 않다는 점이다. 초기에는 크기·거리·부분 가림을 반영해 보완하고, 시각적 오인이 게임의 핵심이라고 확인될 때 영상 관찰을 비교한다. 영상 관찰은 연산·학습·클라우드 렌더링 비용을 별도 측정한다.

### 5.2 관찰 계약 초안

| 묶음 | 포함 후보 | 주의점 |
| --- | --- | --- |
| 자기 상태 | 속도, 방향, 자세, 스태미나, 피격 누적, 기절 여부 | 현재 규칙 기준으로 정규화 |
| 경기 | 페이즈, 내 숨기기 차례, 남은 시간 비율, 파쇄 잔여 | 게임이 공개하는 정보만 |
| 보유 물건 | 없음/일반 소품/배정 물건, 내 물건 여부 | 서버가 확정한 소유 상태 |
| 보이는 물건 | 상대 위치, 크기 등급, 확인된 종류, 접근 가능 여부 | K개 후보만, 안 보이면 새 위치 갱신 금지 |
| 보이는 상대 | 상대 위치·속도, 관찰 가능한 자세·보유 상태 | 다른 사람의 비공개 상태는 제외 |
| 지형 | 주변 충돌 탐지, 경로 가능 여부, 알려진 목적지 | 전역 길찾기로 비공개 물건을 역추적하지 않음 |
| 기억 | 마지막 목격 위치, 경과 시간, 방문 구역, 내 숨김 위치 | 오래된 기억과 현재 목격을 구별 |
| 실행 상태 | 진행 중 행동, 경과 시간, 직전 성공/실패 사유 | 같은 실패 명령 반복 방지 |

관찰 순서·단위·정규화 범위·빈 슬롯·마스크를 `ObservationSchemaVersion`으로 고정한다. 예를 들어 위치는 내 캐릭터 기준의 상대 방향으로 바꾸고 관찰 반경으로 나눈다. 범위를 넘으면 일정 범위로 제한한다.

후보 수가 바뀌어도 입력 길이를 유지하려면 첫 구현에서는 고정 K개 슬롯과 `valid` 표시를 사용한다. K는 작은 맵 실측으로 정하며, 처음부터 수천 개 소품을 모두 입력하지 않는다. 일반 소품도 사용자 목표에 필요하므로 후보에서 전부 제외하면 안 된다. 근처의 이동 가능한 소품·가림 소품·현재 목표 관련 소품을 우선한다.

거리 순서가 바뀌면서 모델의 목표 번호가 다른 물건으로 바뀔 수 있다. 관찰을 만들 때 슬롯→objectId 대응을 저장하고 그 결정에 해당하는 대응표로 행동을 해석한다. 목표가 제거되었으면 실패 결과를 돌려주며 다른 물건에 명령을 보내지 않는다.

### 5.3 행동 계약 초안

| 행동 | 실행기 책임 | 완료·실패 조건 예 |
| --- | --- | --- |
| 탐색 구역 선택 | 알려진 구역으로 이동하고 시야 확보 | 구역 도착 / 경로 없음 |
| 물건 접근·집기 | 적정 거리 접근 후 한 번 요청 | 집기 확정 / 다른 사람이 먼저 집음 |
| 소품 재배치 | 집기→검증된 배치 후보 이동→놓기 | 배치 확정 / 부피 충돌 |
| 숨기기 | 내 물건을 은폐 후보에 배치 | 유효 배치 / 시간 초과 |
| 운반·파쇄 | 물건 유지, 파쇄기 접근, 파쇄 요청 | 파괴 확정 / 사용 횟수 없음 |
| 전투 | 상대 접근·시선·공격 간격 처리 | 목표 이탈 / 기절 / 상황 변화 |
| 회수·도주·보호 | 기억 위치 확인, 위험에서 이탈 | 내 물건 확보 / 기억 위치에서 못 찾음 |
| 대기·종료 | 입력 정지, 숨기기 완료 요청 | 페이즈 전환 / 요청 거절 |

처음 상위 정책은 `행동+대상`의 유효한 조합을 한 목록으로 만들고 목록 인덱스 하나를 고르는 방식으로 실험한다. 여러 독립 분기로 나누면 “파쇄+일반 소품” 같은 잘못된 조합의 마스크가 복잡해진다. 후보 목록의 크기와 정렬 방식도 버전에 포함한다.

ML-Agents는 연속·이산 행동과 수동 입력용 Heuristic을 지원한다. 초기 관찰·행동 설계의 기능적 근거는 [Agent 설계 문서](https://docs.unity3d.com/Packages/com.unity.ml-agents@4.1/manual/Learning-Environment-Design-Agents.html)와 설치된 패키지 소스를 함께 확인한다.

### 5.4 판단 속도와 실행 속도

- 초기 상위 판단은 5Hz, 즉 0.2초마다 한 번을 실험값으로 잡는다. 성능·반응을 보고 2~10Hz 범위에서 비교한다.
- 이동은 매 시뮬레이션 틱에 같은 목표를 추종한다. 물리 틱과 모델 판단 주기는 별개다.
- 집기·파쇄·공격 요청은 버튼을 계속 누르는 것처럼 매 틱 반복하지 않는다. 요청 ID와 대기/성공/실패 상태를 둔다.
- 목표에는 최소 유지 시간과 최대 실행 시간을 둔다. 기절·물건 파괴·페이즈 전환 같은 사건은 즉시 중단 가능하다.
- `Decision Period`는 실제 시뮬레이션 스텝 기준이다. 렌더 FPS나 현실의 경과 시간과 혼동하지 않는다.
- 마지막에 내 물건을 들고 가만히 있는 것은 올바른 행동일 수 있다. 모든 정지 상태에 벌점을 주지 않는다.

## 6. 단계별 구현·학습 계획

각 P단계는 작은 과제로 더 쪼갠다. 아래 게이트는 통과 증거를 남기는 체크포인트다. 한 단계가 실패하면 문제를 좁히고 재시도한다.

### P0. 환경 동결과 재현 기준 만들기

**배울 것:** Python 환경과 Git 저장소의 차이, 학습과 추론의 차이, 버전 잠금.

**직접 할 일:** `python --version`, `python -m pip show mlagents mlagents-envs torch setuptools`, `python -m pip check`, CUDA 인식 결과를 기록한다. Unity 패키지 잠금 파일과 게임 Git 커밋을 기록한다. 공식 예제의 실제 경로와 브랜치를 확인한다. 앞서 해결한 setuptools 문제는 재설치 문서에 실제 성공 버전으로 남긴다.

**산출물:** 로컬 환경 명세와 설치 로그. Windows의 pywin32 같은 패키지를 Linux 클라우드에 그대로 복사하지 않고 OS별 명세를 관리한다.

**G0:** 동일 환경에서 trainer 도움말과 3DBall 연결 재현. GPU 학습 여부는 별도 확인. 이후 우리 프로젝트 검증은 별도로 수행.

### P1. 우리 캐릭터로 작은 수동 테스트 씬

**배울 것:** Transform·충돌체·이동체·모델 외형, Heuristic, 에피소드 초기화.

**직접 할 일:** `Training_Reach` 씬에 평평한 바닥, 우리 캐릭터 외형, 목표 표식 하나, 경계만 배치한다. 첫 캐릭터는 학습용 프리팹으로 만들고 네트워크 프리팹을 그대로 분해하지 않는다. 가장 단순한 입력 2개로 평면 이동을 구현한다. 키보드가 이 입력 경로를 거쳐 캐릭터를 움직이게 한다.

키보드로도 성공할 수 없는 씬을 AI에 학습시키지 않는다. 한 번 시작할 때 속도·회전·보유 상태가 모두 초기화되는지 확인한다. 임시 이동체를 쓴 경우 최종 KCC와 다르다는 표시를 프리팹과 실험 기록에 남긴다.

**산출물:** 씬, 학습용 캐릭터, 수동 이동, Reset 버튼 또는 리셋 함수.

**G1:** 20회 수동 초기화·도착 성공. 초기 겹침·바닥 이탈·이전 속도 잔류 0건. 자동 로그인/Photon 연결 없이 실행.

### P2. 목표 도달을 처음 학습하고 모델을 게임 빌드에서 실행

**배울 것:** 관찰→정책→행동→보상의 반복, 누적 보상, 종료, TensorBoard.

**직접 할 일:** 고정 높이 평면 과제로 제한한다. 초기 관찰 예시는 상대 목표 위치 x/z와 자기 속도 x/z의 4개다. 행동은 평면 이동 2개다. 이 정의를 Inspector와 C#에서 정확히 일치시킨다. 첫 보상은 도착 +1, 실패 -1, 작은 시간 비용부터 시작한다. 시작점과 목표를 유효 영역에서 무작위 배치한다.

학습 후 모델을 ONNX로 내보내고 **Python을 종료한 상태**에서 Unity 추론을 실행한다. 여기서 배포하려는 플랫폼의 작은 빌드도 만든다. WebGL은 빈 씬+한 봇부터 확인한다. 첫 모델은 개념 학습·통합 시험용이며 최종 전략 모델로 재사용을 보장하지 않는다.

**산출물:** Agent, YAML, 로그, 첫 ONNX, Unity 단독 추론 결과.

**G2:** 학습과 다른 평가 배치 100회에서 도달률 95% 이상을 초기 목표로 사용. 다른 학습 시드 3개를 비교. 모델을 실제 타깃 빌드에서 읽고 실행 가능해야 통과.

### P3. 실제 이동·권한 판정 연결을 먼저 검증

**배울 것:** 학습 환경과 실제 환경의 차이, 공통 입력, 길찾기와 전략의 차이.

**직접 할 일:** 규칙이 정해준 목표 하나를 향해 실제 KCC 캐릭터가 움직이는 최소 호스트 봇을 만든다. 봇 좌석·스폰·입력 전달부터 작은 범위로 연결한다. 모델 없이도 진행 가능하다. 기존 사람 입력과 봇 입력이 동시에 위치를 쓰지 않게 한다.

NavMesh는 걸을 수 있는 바닥 지도다. 경로만 계산하고 실제 위치는 KCC가 변경한다. 정적 구조물 중심으로 베이크하고 움직이는 소품은 충돌·막힘 검사 대상으로 둔다. 모든 소품에 동적 NavMesh 갱신을 켜는 것은 성능 측정 전에는 하지 않는다.

집기 거리·배치·던지기 등의 검증이 지금 Network에 존재한다. 훈련에서도 재사용하려면 Fusion 비의존 규칙을 공통 위치로 옮기거나 공통 어댑터를 만든다. 좌표 검증을 훈련 코드에 별도로 복제하는 방식은 피한다.

**산출물:** 실제 게임 입력 어댑터, 최소 봇 참가자, 경로 추종, 규칙 기반 목표 이동.

**G3:** 호스트+원격 사람 클라이언트에서 봇 1개의 이동 동기화 확인. 직선·모서리·좁은 통로·정지·기절·텔레포트 시나리오에서 사람 규칙 유지. 임시 이동체와의 차이를 표로 작성.

### P4. 눈앞의 물건을 인식하고 집기

**배울 것:** 제한된 관찰, 상대 좌표, 마스크, 서버 확정 결과.

**직접 할 일:** 물건 하나→종류가 다른 물건 3개→벽 뒤 물건 순으로 추가한다. 시야·가림을 Gizmo로 그린다. 처음엔 눈앞의 목표가 주어지는 쉬운 과제로 시작하고, 이후 목격 후 접근으로 바꾼다. 집기 보상은 모델이 요청한 시점이 아니라 게임 규칙이 성공을 확정한 시점에 준다.

**산출물:** Perception, 후보 슬롯, 집기 실행기, 집기 과제.

**G4:** 평가 100회 집기 성공률 90% 이상. 보이지 않는 대상·거리 밖·이미 보유된 대상에 대한 실제 집기 성공 0건. 같은 물건을 놓고 반복 집어 보상만 얻지 못함.

### P5. 일반 소품을 옮겨 공간 만들기

**배울 것:** 여러 행동을 이어야 받는 보상, 소품과 배정 물건의 구분.

**직접 할 일:** 작은 상자 1개가 목표 접근을 막는 과제를 만든다. 상자를 집어 정해진 유효 구역에 놓은 뒤 목표 물건을 집게 한다. 상자 크기와 배치 후보를 제한한 뒤 단계적으로 늘린다. 옮긴 소품이 플레이어의 통로를 막거나 물건을 맵 밖으로 밀어내는지 검증한다.

물건을 운반 중이라 손이 찬 상황에서는 “현재 물건 놓기→소품 이동→다시 회수”가 필요할 수 있다. 이 순서를 별도 시나리오로 검사한다. 모든 장애물을 이동 가능하다고 가정하지 않는다.

**산출물:** 소품 선택·들기·배치 실행기, 작은 재배치 과제, 유효 배치 후보 생성.

**G5:** 제한된 배치 평가 100회에서 목표 달성 80% 이상. 비정상 좌표·충돌 배치·물건 유실 0건. 불가능한 문제에서는 제한 시간 내 포기 또는 다른 목표로 전환.

### P6. 숨기기와 소품으로 가리기

**배울 것:** 좋은 보상과 편법, 결과가 늦게 드러나는 목표.

**직접 할 일:** 검증된 숨김 후보 중 하나를 고르게 한다. 내 물건 배치→필요한 소품 이동→스스로 회수할 수 있는지 검사→숨기기 완료로 연결한다. 후보마다 실제 도달 경로와 배치 충돌을 검사한다.

처음에는 고정된 탐색 봇이 제한 시간 내 찾는지로 숨김 품질을 평가한다. 학습 정책에는 탐색 봇의 비공개 상태를 주지 않는다. 단순히 벽 뒤에 두었다는 이유로 높은 보상을 주면 맵 밖이나 회수 불가능한 곳을 고를 수 있다. 숨김 품질과 회수 가능성을 함께 평가한다.

**산출물:** 숨김 후보, 은폐 실행 루틴, 탐색 기준 봇, 숨김 품질 기록.

**G6:** 시간 안에 유효 배치 95% 이상. 회수 불가능 위치 0건. 새 후보 배치에서 무작위 유효 숨기기보다 탐색에 걸리는 시간이 개선되고 회수율이 악화되지 않음.

### P7. 탐색·기억·상대 물건 운반·파쇄

**배울 것:** 보이지 않는 정보를 기억하기, 구역 탐색, 희소 보상.

**직접 할 일:** 플레이어 물건과 일반 소품이 섞인 작은 맵을 만든다. 방문 기록, 마지막 목격 위치, 목격 후 시간, 이미 확인한 빈 위치를 기억한다. 다른 봇이 물건을 옮기면 기억은 낡은 정보로 남아야 한다. 본 적 없는 물건의 실제 위치를 자동 조회하지 않는다.

탐색→확인→집기→파쇄기로 운반→파쇄를 연결한다. 파쇄 횟수 소진, 운반 중 기절, 파쇄기 접근 실패를 넣는다. 자기 물건을 파쇄하는 정책은 제품 의도에 따라 금지 마스크와 규칙으로 막는 것을 기본 제안으로 둔다. 실제 게임 규칙 변경과 봇 정책 제약은 구별한다.

**산출물:** 기억 저장소, 탐색 정책, 파쇄 실행기, 2~3개 구역 과제.

**G7:** 눈앞 목표 운반·파쇄 성공률 90% 이상. 탐색 포함 과제는 100개 평가 배치에서 80% 이상을 초기 목표로 사용. 이전 위치에 물건이 없으면 재탐색. 동일 파괴 이벤트 보상 중복 0건.

### P8. 전투·회피·물건 탈취

**배울 것:** 상대 행동에 따라 바뀌는 환경, 시간과 위험의 비용.

**직접 할 일:** 정지 상대→규칙대로 접근하는 상대→추격하는 상대 순서로 진행한다. 공격 입력 애니메이션과 서버의 실제 명중 판정이 별도 경로인지 확인한다. 모델이 공격 버튼만 눌러도 명중이 되는 것으로 처리하지 않는다.

손이 찬 상태, 기절 직후, 상대의 물건 보유, 파쇄기 주변처럼 다른 목표가 있는 전투를 만든다. 원래 게임에 없는 체력 개념을 임의로 추가하지 않고 현재 피격 누적·기절·무적 규칙을 사용한다.

**산출물:** 공격·도주 실행기, 정해진 상대 모음, 목적별 전투 평가.

**G8:** 범위 밖 명중·쿨다운 우회·기절 중 행동 0건. 물건 운반 중에는 항상 싸우는 기준 봇보다 목표 완료율이 좋아야 한다. 공격 횟수만으로 성공 판정하지 않는다.

### P9. 종료 전 회수와 보유 유지

**배울 것:** 당장 얻는 점수보다 마지막 목표가 중요할 때의 선택.

**직접 할 일:** 남은 시간과 자기 물건 상태를 다양하게 시작한다. 내 물건이 숨긴 곳에 있음/다른 사람이 옮김/상대가 들고 있음/파괴됨을 각각 구성한다. 위험한 파쇄 시도 대신 돌아가야 하는 상황을 포함한다.

내 물건이 파괴된 뒤의 제품 행동도 정한다. 계속 다른 사람을 괴롭히는 봇이 재미를 해칠 수 있으므로, 단순 괴롭힘 보상을 주지 않고 참여 방식은 플레이테스트로 결정한다. 원래 게임이 계속 참여를 허용한다면 즉시 에피소드를 종료해 규칙을 바꾸지 않는다.

**산출물:** 마지막 구간 시나리오, 회수·보호 정책, 결과 조건 검사.

**G9:** 학습에 없던 마지막 구간 100회에서 무작위·탐욕적 기준 봇보다 자기 물건 최종 보유율 개선. 충분히 안전할 때 서 있는 행동도 성공으로 인정.

### P10. 전체 경기 전략을 학습

**배울 것:** 전략 선택, 장기 보상, 상대가 변할 때 학습이 불안정해지는 이유.

**직접 할 일:** P4~P9 실행기를 유지하고 상위 전략 정책을 학습한다. 하위 과제 모델을 썼다면 누가 언제 어느 모델을 호출하는지 명시한다. 전략 모델은 새로운 행동 계약이므로 P2 모델에서 자동 이어 학습하지 않는다.

첫 상대 구성은 학습 봇 1명+고정 규칙 봇이다. 2인 단축 경기→3인→6인으로 확장하고 좌석·배정 물건을 교체한다. 그다음 고정한 과거 모델을 상대 풀에 추가한다. 한 학습 구간 동안 상대 모델은 변경하지 않고 구간 사이에 갱신한다.

ML-Agents의 경쟁 Team ID와 협력 Group은 용도가 다르다. 현재 게임은 개인별 목표와 복수 승자를 가지므로 팀 보상을 그대로 쓰지 않는다. 내장 self-play를 채택하기 전에 작은 별도 실험으로 갱신 대상·상대 교체·보상 해석을 확인한다. 6개의 같은 모델이 동시에 배우는 것과 과거 상대를 관리하는 self-play는 동일하지 않다. [공식 다중 에이전트 설계](https://docs.unity3d.com/Packages/com.unity.ml-agents@4.1/manual/Learning-Environment-Design-Agents.html)

**산출물:** 전략 정책, 상대 풀 구성, 전체 경기 평가기, 난이도 초안.

**G10:** 학습 시드 3개 이상, 시드별 평가 경기 100판 이상. 동결 상대 풀에서 기준 봇 대비 최종 자기 물건 보유율이 개선되고 규칙 위반·경기 정지 없음. 평균 보상만 좋아진 모델은 탈락.

### P11. 실제 마트 맵과 게임 전체 연결

**배울 것:** 처음 보는 환경에 적응하는 능력과 성능 측정.

**직접 할 일:** 작은 맵→마트 일부 구역→전체 맵으로 늘린다. 소품 수·크기·배치·스폰·아이템 카테고리·경기 규칙을 확장한다. 앞서 만든 최소 호스트 봇 연결을 참가/설정/결과/재경기까지 완성한다. 실제 클라이언트 빌드에서 수행한다.

**산출물:** 후보 출시 모델, 실제 씬 배치, 멀티플레이 테스트 기록.

**G11:** 지원하는 맵·인원 조합에서 전체 경기 완주. 처음 보는 배치와 사람 플레이에서도 필수 행동 실행. 성능·공정성 게이트는 12절 적용.

### P12. 제한 공개와 정식 운영

**배울 것:** 실험 성능과 사용자 경험의 차이, 버전 관리, 롤백.

**직접 할 일:** 모델·게임·관찰 스키마 버전을 묶어 배포 후보를 만든다. 내부→테스터→일부 방→전체 순서로 확대한다. 새 모델은 경기 도중 교체하지 않는다. 실패 시 이전 모델이나 규칙 정책으로 전환할 경로를 실제 시험한다.

**산출물:** 릴리스 기록, QA 결과, 모델 정보 카드, 운영 지표, 되돌리기 절차.

**G12:** 코드·모델·규칙 조합 추적 가능, Python 없는 사용자 환경에서 실행, 이전 버전 복귀 검증, 팀의 출시 판정 완료.

## 7. 보상과 학습 설정

### 7.1 과제마다 다른 채점표 사용

“집기 연습”에서는 집기가 목표다. “전체 경기”에서는 집기는 마지막 보유를 위한 중간 행동이다. 따라서 두 과제의 보상표를 그대로 합치지 않는다.

| 보상 후보 | 단위 과제 | 전체 경기의 기본 제안 |
| --- | --- | --- |
| 자기 물건을 최종 보유 | 해당 없음 | +1, 미보유 -1을 출발점으로 비교 |
| 목표 물건 집기 성공 | +1로 종료 가능 | 첫 유효 확보에만 작게, 반복 지급 금지 |
| 상대 물건 파괴 | 운반·파쇄 과제의 성공 | 작은 보조 보상, 최종 보유 보상보다 우선하지 않게 |
| 공격 명중 | 전투 동작 검증용 | 기본적으로 횟수 보상 없음. 목적 달성에 연결 |
| 숨김 배치 완료 | 배치 성공 보상 | 유효성·회수 가능성·탐색 결과를 함께 평가 |
| 시간 경과 | 도달 과제에 작은 비용 | 페이즈·목표별 적용. 보호 중 정지에 무조건 벌점 금지 |
| 잘못된 요청 | 원인 로그가 우선 | 반복 실패를 측정하고 필요 시 제한된 비용 |

숫자는 실험 출발점이다. 전체 경기의 보조 양의 보상 총량을 예를 들어 0.3 이하로 제한한 비교 실험을 해보고, 결과를 바탕으로 조정한다. 큰 최종 보상만으로 장기 목표를 배운다는 보장은 없으므로 단축 경기·성공 직전 시작·단위 과제를 병행한다.

거리에 따른 보조 보상을 쓸 경우 단순히 “가까운 상태인 매 순간 +점수”를 주지 않는다. 왔다 갔다 점수를 버는지 검사한다. 잠재 함수 방식 `gamma × Phi(다음 상태) - Phi(현재 상태)`를 후보로 쓸 수 있지만, 종료 상태와 목표 교체 시 기준을 일관되게 처리해야 한다. 가림 뒤 실제 물건 위치를 거리 보상으로 계속 알려주는 설계도 피한다.

### 7.2 보상 편법 검사

- 같은 물건 집기/놓기 반복으로 누적 보상이 증가하는가?
- 움직이기만 하거나 파쇄기 앞에서 요청만 반복해 이득을 얻는가?
- 숨기기 완료를 늦추거나 에피소드 종료를 회피하면 더 유리한가?
- 공격만 하고 자기 물건 회수를 포기하는가?
- 맵 밖·벽 안·접근 불가능한 곳에 숨겨 점수를 얻는가?
- 장애물을 통과하거나 상대의 숨김 위치를 알아야만 성공하는가?

각 사건의 보상 합계를 따로 기록한다. 총 보상이 올라도 최종 성공률이 내려가면 보상 설계를 재검토한다.

### 7.3 처음 공부할 학습 설정

| 설정 | 비유 | 변경 기준 |
| --- | --- | --- |
| learning_rate | 습관을 한 번에 바꾸는 크기 | 변화가 불안정하면 줄이는 실험 |
| buffer_size | 복습하기 전 모을 경험 노트 양 | 환경 처리량과 경험 다양성 측정 |
| batch_size | 한 번에 읽는 노트 묶음 | 메모리·갱신 안정성 확인 |
| num_epoch | 같은 노트를 반복해 읽는 횟수 | 과도한 반복 여부 비교 |
| gamma | 미래 점수를 얼마나 중요하게 보는지 | 실제 판단 주기와 목표 지연을 함께 고려 |
| time_horizon | 경험을 잘라 평가하는 구간 길이 | 에피소드 최대 길이와 다른 값임을 이해 |
| max_steps | 실험 예산 | 성공 보장이 아니라 계산 종료 기준 |
| summary_freq | 성적표를 기록하는 간격 | 너무 잦은 기록으로 느려지지 않게 |

설정 이름과 지원 범위는 [공식 설정 문서](https://docs.unity3d.com/Packages/com.unity.ml-agents@4.1/manual/Training-Configuration-File.html)를 확인한다. 첫 YAML은 작은 검증된 과제로 시작하고 한 실험에서 한 원인만 바꾼다. 현재 계획서에 완성 YAML을 고정하지 않는 이유는 관찰·행동·판단 주기가 아직 정해지지 않았기 때문이다.

PPO가 계속 실패하면 곧바로 더 큰 모델이나 다른 알고리즘으로 바꾸지 않는다. 수동 성공→규칙 봇 성공→관찰/행동 로그→초기화→보상 순서로 검사한다. 성공 경험이 지나치게 희귀하면 개발자가 직접 플레이한 시범을 기록해 모방학습을 검토한다. 시범과 런타임의 관찰·행동 계약은 동일해야 한다.

## 8. 학습 환경과 실제 게임의 차이 줄이기

### 8.1 같은 외형보다 같은 규칙이 중요하다

훈련용 캐릭터는 눈에 보이는 모델을 재사용한다. 실제 제품 검증에서는 다음을 비교한다.

| 비교 항목 | 검증 방법 |
| --- | --- |
| 속도·가속·회전 | 동일 명령열을 두 이동체에 넣고 도착 시간·최종 위치 비교 |
| 충돌체 크기 | 같은 좁은 통로·선반 모서리에서 통과 결과 비교 |
| 스태미나·자세 | 같은 달리기 시간과 자세 전환으로 제한 비교 |
| 들기·배치 | 같은 거리와 물건 크기에서 성공/실패 비교 |
| 전투 | 같은 간격·방향·기절 시간에서 명중/거절 비교 |
| 시간 | 타임스케일 변경 전후 시뮬레이션 시간당 결과 비교 |
| 소품 물리 | 운반·놓기 뒤 안정화 시간과 충돌 결과 비교 |

초기 임시 이동체는 학습 원리를 익히는 동안만 쓴다. 고급 숨기기·전투 모델에 긴 학습비를 쓰기 전에 실제 KCC 경로를 검증한다. 오프라인 KCC 재사용이 어려우면 무그래픽 로컬 호스트 학습이나 공통 이동 구현 분리를 검토한다. 어느 쪽이든 검증 없이 “나중에 붙이면 된다”고 넘기지 않는다.

### 8.2 에피소드 초기화와 병렬 실행

매 판 시작할 때 캐릭터 위치·속도·자세·스태미나·피격·기절, 아이템 위치·회전·속도·소유·파괴 상태, 파쇄 횟수, 시계, 기억, 대기 중 요청, 모델의 순환 기억을 초기화한다. 경기 제한 시간 종료는 게임의 정상 결과이며, 장비 중단이나 실험 강제 절단과 구별한다.

여러 연습장을 한 씬에 복제하면 충돌·Raycast·정적 레지스트리·R3 구독이 다른 연습장에 영향을 주지 않아야 한다. 숨기기 후보·objectId·플레이어 인덱스도 연습장별로 분리한다. 누수가 해결되지 않으면 프로세스별 연습장 한 개로 먼저 돌린다.

### 9.1 매 실험에 남길 정보

```text
실험 ID: pickup-v01-seed101
가설: 가림 여부를 넣으면 벽 뒤 물건으로 직진하는 실패가 줄어든다.
변경: 관찰에 가시 여부 추가. 그 외 조건 동일.
게임 Git SHA / Unity / ML-Agents / Python / torch:
관찰·행동·보상 스키마 버전:
학습 씬·맵·NavMesh 버전:
실제 경기 규칙 / 판단 Hz / 물리 틱:
```

무작위 숫자를 고정해도 서로 다른 OS·GPU·물리 실행이 비트 단위로 같아진다고 보장하지 않는다. 같은 조건을 최대한 재현하고 결과의 범위를 비교하는 것이 목적이다.

### 9.2 학습·조정·최종 시험을 분리

1. 학습 배치: 모델이 반복 연습한다.
2. 검증 배치: 보상·설정을 조정하며 비교한다.
3. 최종 시험 배치: 후보를 고른 뒤 한 번 평가한다. 이를 보고 다시 튜닝했으면 다음 출시 시험에는 새 배치를 준비한다.

같은 평가 시드·같은 상대·좌석 교환으로 규칙 봇과 학습 봇을 비교한다. 최소 3개 학습 시드의 결과를 평균·범위로 보고하고, 한 번 가장 잘 나온 모델만 근거로 주장하지 않는다. 100판에서 1~2판의 차이는 큰 개선이라고 단정하지 않고 경기 수를 늘리거나 불확실성을 함께 표시한다.

최종 기준은 자기 물건 보유율, 경기 완주율, 규칙 위반, 목표 완료 시간, 멈춤·반복 행동, 사람 평가다. 승률만 높고 불쾌하거나 너무 정확한 봇은 출시 품질이 좋다고 판단하지 않는다.

### 9.3 학습 명령 템플릿

아래 YAML·빌드 경로는 **앞으로 만들 파일의 예시**다. 지금 바로 실행하는 명령이 아니다. 모든 예시는 `C:\Users\SSAFY\Desktop\S15P21D205`에서 실행하는 것으로 통일한다.

```cmd
conda activate ml-agents
cd /d C:\Users\SSAFY\Desktop\S15P21D205
mlagents-learn Tools\training\config\reach.yaml --run-id=reach-v01-seed101 --seed=101
```

같은 실험을 이어 실행할 때만 `--resume`을 쓴다. 새 설계는 새 run-id로 기록한다. 모델 구조·관찰 길이를 바꾼 뒤 무조건 이전 실험을 이어 실행하지 않는다. 정상 중단은 Ctrl+C 한 번 후 저장 완료를 기다린다. 결과를 덮어쓰는 `--force`를 일상적인 해결책으로 사용하지 않는다. [공식 실행·저장·재개 안내](https://docs.unity3d.com/Packages/com.unity.ml-agents@4.1/manual/Training-ML-Agents.html)

```cmd
mlagents-learn Tools\training\config\reach.yaml --run-id=reach-v01-seed101 --resume
tensorboard --logdir results
```

전체 체크포인트와 로그는 별도 결과 저장소에 보관한다. Git에는 재현용 설정·메타데이터·승인 모델만 넣고 모델 파일의 LFS 정책을 적용한다. ONNX만으로 optimizer 상태를 포함한 학습을 그대로 재개할 수 있다고 보지 않는다.

## 10. 로컬과 클라우드 운영

### 10.1 로컬 RTX 4050의 역할

씬·센서·행동 구현, 수동 확인, 짧은 학습, 오류 수정, Windows/WebGL 빌드 평가를 담당한다. 작은 숫자 관찰 모델은 GPU가 커져도 Unity 시뮬레이션 CPU가 느리면 전체 학습이 빨라지지 않는다. GPU 사용률만 보지 말고 환경 steps/s와 CPU·GPU 처리 시간을 함께 측정한다.

### 10.2 Jupyter 클라우드의 사전 점검

Jupyter는 코드를 실행하는 창이다. Unity 게임 세계도 같은 서버에서 실행할 수 있어야 본격 학습이 가능하다. Python 학습기만 클라우드에 있고 Unity는 집 PC에 있는 방식은 초기 기본 경로로 사용하지 않는다.

| 확인 | 통과 조건 |
| --- | --- |
| 운영체제 | 대체로 Linux. 그 OS용 Unity 학습 빌드 준비 |
| 실행 권한 | 업로드한 Unity 실행 파일을 프로세스로 시작할 수 있음 |
| 통신 | 학습기와 환경 사이 로컬 포트·여러 프로세스 사용 가능 |
| 렌더링 | 숫자/Ray 관찰은 무그래픽 시험. 이미지 관찰은 렌더링 구성 별도 |
| GPU | GPU 종류·드라이버·torch 조합의 실제 CUDA 인식 확인 |
| 저장소 | 세션이 종료되어도 체크포인트·로그가 남음 |
| 자원 | 충분한 CPU/RAM·디스크. 여러 환경 실행 시 처리량 개선 확인 |
| 시간·비용 | 세션 최대 시간·중단 정책·예산·지출 알림 확인 |

최신 클라우드 GPU가 로컬 torch 2.2 계열과 맞지 않을 수 있다. 더 강한 GPU라는 이유로 환경 명세를 그대로 복제하지 않는다. 후보 GPU에서 torch와 ML-Agents 조합을 별도 검증하고 호환되지 않으면 검증된 장비로 변경하거나 독립된 버전 검증 실험을 한다.

Unity는 Editor 대신 실행 파일을 원격 머신에서 학습 환경으로 사용할 수 있다고 안내한다. 무그래픽 실행은 렌더링이 필요 없는 관찰에 적합하다. [공식 학습 실행 파일 안내](https://docs.unity3d.com/Packages/com.unity.ml-agents@4.1/manual/Learning-Environment-Executable.html)

### 10.3 클라우드 이동 순서와 예산

1. 로컬에서 같은 학습 빌드로 10~20분 학습·저장·재개를 검증한다.
2. Linux 학습 빌드와 Linux용 Python 환경을 준비한다. 학습 빌드는 훈련 전용 씬으로 시작한다.
3. 클라우드에 빌드·YAML·모델 메타데이터만 올리고 10분 연결 시험을 한다.
4. 환경 1개→2개→4개 순서로 늘려 steps/s와 메모리를 비교한다. 느려지면 줄인다.
5. 1시간 시험 후 로그와 체크포인트를 영속 저장소에서 실제로 다시 내려받아 재개한다.
6. 효과가 확인된 뒤 장시간 학습을 예약한다. 학습 완료/정체/예산 초과 시 종료 기준을 둔다.

비용 추정은 `실험 수 × 실험당 시간 × 시간당 장비 비용 + 저장 비용`으로 계산한다. 학습 시간은 로컬/클라우드 10분 처리량 측정 이후 추정한다. 에피소드가 길어지면 처리량과 필요한 경험이 달라지므로 초기 도달 과제 수치를 전체 경기까지 그대로 확장하지 않는다.

## 11. 모델의 게임 적용과 멀티플레이

### 11.1 모델 가져오기

초기 런타임은 ML-Agents Agent + Behavior Parameters의 `Inference Only` 경로를 우선 검증한다. 직접 Inference Engine Worker를 작성하는 방식은 성능·특수 출력 처리가 필요할 때 비교한다. ML-Agents ONNX의 입력 이름·마스크·메모리·출력 구조를 추측해서 수동 연결하지 않는다.

학습은 Python에서, 배포 후 판단은 Unity에서 수행한다. 이용자에게 Conda·Python·CUDA 설치를 요구하지 않는다. 공식 안내는 작은 ML-Agents 모델에서 CPU/Burst 추론이 GPU보다 빠를 수 있다고 설명한다. RTX 4050으로 훈련했다는 사실이 배포 봇도 GPU를 써야 한다는 뜻은 아니다. [Unity 추론 안내](https://docs.unity3d.com/Packages/com.unity.ml-agents@4.1/manual/Inference-Engine.html)

### 11.2 훈련과 실행 계약 검증

- 입력 길이뿐 아니라 항목 순서·좌표 기준·정규화·후보 슬롯이 동일한지 검사한다.
- 같은 기록된 관찰을 학습용/제품용 어댑터에 넣고 같은 형태의 행동을 얻는지 비교한다.
- 확률적 출력을 쓰는 경우 비트 단위 일치를 요구하지 않고 유효 범위·분포·성능을 비교한다. 재현용 시험은 가능한 결정적 모드로 따로 한다.
- 모델 교체·봇 재스폰·재경기 때 순환 기억과 보류 중 행동을 초기화한다.
- 출력이 NaN·범위 밖·비어 있음·호환되지 않으면 즉시 무효 처리한다.
- 제품 빌드에서 trainer 연결 대기나 reward/reset 코드가 실행되지 않는지 확인한다.

### 11.3 사람과 봇의 네트워크 경로

```text
사람: 입력/RPC → 송신자 확인 → 공통 행동 검증 → 경기 결과 확정
봇:   호스트 정책 → 고정된 봇 인덱스 → 공통 행동 검증 → 경기 결과 확정
확정 결과 → Photon 복제 → 모든 참가자의 화면
```

`PlayerRef.None`으로 스폰하는 것만으로 봇 참가가 완성되지 않는다. 좌석 조회·아바타 조회·인트로 준비·물건 배정·재경기·정리 경로에서 실제 사람 연결이 없는 참가자를 지원해야 한다. 봇은 친구·보이스·초대·신고의 사람 계정 대상으로 취급하지 않는다.

사람 RPC의 신원 검증을 제거하거나 playerIndex를 외부에서 임의 지정할 수 있게 만들지 않는다. 봇 내부 경로는 호스트가 생성한 해당 봇 인덱스에 고정한다. 중복 집기·동시 파쇄·피격과 던지기가 겹치는 경우도 공통 판정이 최종 결정한다.

호스트 이탈은 기존 서비스의 방 종료 정책을 우선 따른다. 저장소에 Migration 코드가 있다고 봇 복원이 완성되었다고 가정하지 않는다. 서비스가 호스트 승계를 실제 지원하기로 하면 좌석·보유 상태·모델 버전·기억 복원 정책을 별도 게이트로 추가한다.

### 11.4 실패 시 행동과 난이도

규칙 정책은 비교 상대이자 비상 동작으로 유지한다. 모델 로드 실패·추론 오류 시 유효한 대기/자기 물건 회수 같은 단순 행동으로 전환한다. 끼임은 재경로→목표 포기 순서로 처리하며, 사람에게 없는 순간이동을 봇만 사용하지 않는다.

쉬움/보통/어려움은 모델 선택·반응 시간·탐색 성향·실수 확률 등을 조절한다. 어려움에서도 벽 뒤 정보·추가 이동 속도·무한 스태미나를 몰래 주지 않는다. 난이도를 낮추기 위해 손에 든 자기 물건을 이유 없이 놓는 식의 부자연스러운 실수도 피한다.

## 12. 출시 검증·배포·운영

### 12.1 먼저 확정할 플랫폼

저장소에 WebGL 배포 경로가 있으므로 **WebGL을 주요 검증 대상으로 포함**한다. 최종 판매/배포 채널은 아직 미정이다. Windows 다운로드나 Steam 등은 팀의 결정 후 추가하며, 이 문서가 특정 스토어 출시를 승인하거나 확정하지는 않는다.

WebGL에서는 브라우저·실제 추론 백엔드·호스트 CPU·메모리·탭 백그라운드 제약을 측정한다. Editor에서 GPU 추론이 됐다는 이유로 브라우저에서도 같은 백엔드가 된다고 가정하지 않는다. 첫 ONNX 단계에서 작은 WebGL 실행을 검증한 뒤 전체 봇 수로 확대한다.

### 12.2 출시 후보 통과 기준

| 영역 | 초기 제안 기준 | 증거 |
| --- | --- | --- |
| 규칙·권한 | 치명적 규칙 우회·상태 손상 0건 | 자동 시나리오와 재현 로그 |
| 경기 진행 | 최소 100판에서 봇 때문에 멈춘 경기 0 | 완주율, 페이즈 대기 시간 |
| 인원 | 1사람+1봇부터 1+5, 2+4, 5+1, 봇 없음 | 실제 원격 클라이언트 시험 |
| 기능 | 지원 범위 내 숨기기·집기·소품 이동·파쇄·전투·회수 | 행동별 성공/실패 기록 |
| 공정성 | 벽 뒤 정보 누출·비공개 소유자 식별 0 | 센서 로그와 가림 테스트 |
| 모델 | 동결 평가에서 기준 봇 대비 목표 개선 | 3개 학습 시드, 좌석 교환 |
| CPU | 5봇의 관찰+판단+길찾기 추가 비용 p95 ≤ 3ms/frame를 초기 목표 | 대상 호스트 실측, 추론만 측정하지 않음 |
| 프레임 | 목표 60fps 장비는 전체 프레임 p95 16.7ms 예산에 맞춤 | 기존 게임 기준선과 전후 비교 |
| 지속 실행 | 재경기 20회 및 2시간 시험에서 지속적인 메모리 증가 없음 | GC·메모리·에셋/Worker 해제 기록 |
| 사용자 경험 | 내부 테스터 최소 5명의 공정성·재미·멈춤 평가 | 점수와 구체 사례 |
| 복구 | 이전 모델 복귀와 규칙 정책 전환 재현 | 리허설 결과 |

성능값은 장비 확정 후 조정한다. p95는 100번 중 대략 95번이 그 시간 안에 끝났다는 뜻이다. 평균 FPS만으로 간헐적인 멈춤을 숨기지 않는다. 기준에 못 미치면 모델 크기·판단 빈도·시야 후보 수·경로 재계산을 조정한다. 봇 수를 줄이는 변경은 제품 범위 변경으로 명시한다.

### 12.3 배포 전에 만드는 모델 정보 카드

```text
모델 ID / 파일 해시 / 크기:
학습 실행 ID / Git SHA / Unity·Python·패키지 버전:
ObservationSchema / ActionSchema / RuleVersion:
지원 맵 / NavMeshVersion / 지원 아이템 범위:
지원 플랫폼 / 확인된 추론 백엔드 / 최대 봇 수:
평가 경기 수 / 시드 / 상대 풀 / 기능·성능 결과:
알려진 약점 / fallback 정책 / 이전 승인 모델:
검토자 / 승인일:
```

첫 출시는 검증된 모델을 게임 빌드에 포함한다. 런타임 원격 모델 다운로드는 후속 기능이다. 원격 갱신을 추가한다면 호환 스키마·해시 검증·다운로드 실패·이전 모델 보관을 먼저 구현한다.

### 12.4 배포 순서

1. 후보 코드·모델·규칙을 고정하고 의미 있는 규칙/통합 테스트를 실행한다.
2. Training Profile과 Game Release Profile을 각각 빌드하여 학습 리소스 혼입 여부를 확인한다.
3. CI 또는 새 체크아웃에서 모델 파일이 실제 바이너리로 받아졌는지 확인한다. Git LFS 포인터만 빌드에 들어가면 안 된다.
4. 스테이징 환경에서 로그인·방 생성·사람 참가·봇 설정·전체 경기·재경기를 시험한다.
5. 내부 테스트 후 참여를 선택한 테스터와 제한 공개한다. 모델 버전별 실패율을 비교한다.
6. 일부 방으로 확대한다. 예를 들어 10%→50%→전체를 제안하되 실제 트래픽과 관측 기간을 팀이 정한다.
7. 시작 시 방의 모델/규칙 버전을 고정하고 진행 중인 경기에 새 모델을 주입하지 않는다.
8. 문제 발생 시 신규 방의 봇 기능을 끄거나 이전 승인 빌드로 복귀한다. 진행 중인 방은 안전한 규칙 정책으로 처리할 수 있어야 한다.

현재 WebGL 도구는 버전별 산출물과 `current.json` 포인터를 사용하는 배포 방식을 문서화한다. 실제 적용 시 `Tools/webgl/README.md`의 현재 절차를 따르고, 코드와 모델을 같은 릴리스로 묶는다. 브라우저 캐시가 새 코드와 이전 모델을 혼합하지 않게 버전 URL을 사용한다.

추가 스토어 출시가 정해지면 계정·앱 등록, 플랫폼 SDK, 입력·해상도·최소 사양, 스토어 제출 요구사항, 심사 기간을 해당 플랫폼 공식 문서로 확인하고 출시 일정에 넣는다. 학습 완료 날짜와 판매 가능 날짜를 동일하게 잡지 않는다.

### 12.5 운영과 재학습

봇 로그에는 모델 버전, 난이도, 맵/규칙, 경기 완주, 최종 자기 물건 보유, 실패 행동 사유, 막힘, fallback 발생, 추론 비용을 남긴다. 봇을 가짜 사람 계정으로 만들지 말고 `participantKind` 같은 구분을 설계한다. 기존 백엔드 이벤트 스키마에 필드를 추가해야 하면 담당자와 함께 버전을 관리한다.

기존 리플레이·분석 로그가 곧바로 학습 데이터는 아니다. 모방학습에는 당시 봇이 볼 수 있었던 관찰과 실제 행동의 대응이 필요하다. 사람 데이터 수집이 필요해지면 수집 범위·안내·보관/삭제를 정한 뒤 적용한다. 초기 학습은 자체 시뮬레이션과 개발자 시범만으로 진행 가능하다.

출시 후에는 정기적으로 버전별 지표와 실패 사례를 검토한다. 맵 가구·아이템 크기·이동 속도·공격 규칙·관찰 구조 변경은 회귀 평가를 촉발한다. 운영 중 모델을 자동 온라인 학습시키지 않고, 실패 사례→재현 과제→오프라인 재학습→동결 평가→새 버전 배포 순서를 유지한다.

| 실제 캐릭터에서 실패 | KCC 속도·충돌·틱·거리 판정 차이 | 실제 실행기 기준 재학습·미세 조정 |
| 물건이 순간이동/중복 소유 | 요청 반복·원격 권한·슬롯 변경 | 공통 판정·요청 수명·ID 검사 |
| GPU가 놀고 학습 느림 | Unity CPU·물리·센서·렌더링 | 간소화·빌드 실행·환경 수 실측 |
| 개인전 성능이 오락가락 | 상대가 너무 자주 변함 | 상대 풀 동결·비교 경기 |
| WebGL에서 멈춤 | 추론 백엔드·할당·경로 재계산 | 작은 모델·판단 분산·CPU 경로 시험 |
| 모델은 좋은데 재미없음 | 과도한 정확도·추격·반복 전략 | 난이도·행동 다양성·사람 테스트 |

## 14. 다음 첫 실습

다음 회차는 **P1: 우리 캐릭터로 바닥 위를 수동 이동하고 초기화하는 씬**까지다. 먼저 모델을 학습시키기보다 학습할 문제가 제대로 만들어졌는지 확인한다.

1. 우리 게임 프로젝트의 Unity 버전과 현재 변경 파일을 확인한다.
2. 캐릭터 외형 프리팹과 NetworkedPlayer에 붙은 컴포넌트를 읽고, 학습용 외형 재사용 범위를 정한다.
3. `Training_Reach` 씬과 학습용 캐릭터를 만든다.
4. 바닥·목표·경계만 두고 수동 이동 입력 2개를 연결한다.
5. 초기화 20회와 수동 도달을 확인한다.
6. 아래 질문에 답하고 나서 관찰과 보상 코드를 작성한다.

스스로 설명할 질문:

- 이 캐릭터의 실제 위치를 바꾸는 컴포넌트는 무엇인가?
- 봇에게 목표 위치를 알려주는 쉬운 연습과, 스스로 발견해야 하는 제품 과제는 어떻게 다른가?
- 집기 버튼을 눌렀다는 사실과 물건을 실제로 들었다는 사실은 왜 다른가?
- 보상은 사용자가 플레이할 때도 반드시 필요한가?
- 에피소드가 새로 시작할 때 이전 속도와 기억을 남기면 어떤 문제가 생기는가?

이번 회차의 완료물은 스스로 설명할 수 있는 작은 씬과 짧은 실험 기록이다. 이 기반 위에 관찰·행동·보상을 하나씩 추가한다.
