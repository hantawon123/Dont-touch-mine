# 채팅 필터 성능 — 판정 방식과 기록 저장 (1048, 1070, 1077)

금칙어 목록을 41개에서 3860개로 늘리면서(같은 이슈) 판정 시간이 함께 늘었다. 기존 구현은 금칙어 하나마다 메시지를 한 번씩 훑으므로 목록 크기에 비례한다. 세 가지 방식을 같은 조건에서 재고 아호-코라식을 채택했다. 판정 규칙은 바꾸지 않았고, 두 구현이 같은 답을 내는지 확인하는 시험을 함께 넣었다.

## 왜 문제인가

판정이 도는 곳은 두 군데다.

| | 게임 서버 (C#) | 백엔드 (Java) |
|---|---|---|
| 언제 | 메시지 한 줄마다, 실시간 중계 경로 | 200줄 묶음을 저장할 때 |
| 무엇을 | 가릴지 판정하고 실제로 가림 | `masked` 칼럼 값만 판정 |
| 지연이 보이나 | 사람에게 바로 보임 | 게임 서버가 응답을 기다리지 않음 |

절대값으로는 목록을 늘린 뒤에도 메시지당 1ms 미만이라 당장 문제가 되는 수준은 아니다. 다만 목록은 앞으로도 늘어나는 쪽이고, 늘어난 만큼 그대로 느려지는 구조라는 점이 걸렸다.

## 측정 방법

Windows 11 26200, OpenJDK 21.0.12, 논리 프로세서 22개. 판정 로직만 뽑아 낸 마이크로벤치마크이며 Spring이나 네트워크는 끼지 않는다. 예열 2만 회 뒤 5만 회를 돌려 평균을 냈고, 3860개는 5회·41개는 3회 반복한 범위를 적었다. 측정 중 다른 작업은 돌리지 않았다.

입력은 실제 채팅에 가까운 한국어 문장 5종이며 **모두 깨끗한 문장이다.** 금칙어가 들어 있으면 순회 방식은 찾는 즉시 멈추므로, 아래 순회 값은 그 방식의 최악값에 해당한다. 반대로 깨끗한 메시지가 대다수인 실제 채팅에서는 이 값이 평상시 값이기도 하다.

허용 목록 제거(`String.replace` 7회)는 세 방식 모두 똑같이 거치므로 차이에 영향을 주지 않는다.

## 결과

목록 3860개 (메시지당, 5회 범위)

| 방식 | 시간 | 순회 대비 | 판정 동치 |
|---|---:|---:|---|
| 전체 목록 순회 (기존) | 0.70 ~ 0.91 ms | 1× | 기준 |
| 길이별 해시 집합 | 0.062 ~ 0.083 ms | 약 12× | **불일치 10건** |
| 아호-코라식 | 0.0036 ~ 0.0048 ms | 약 200× | 일치 |

목록 41개 (변경 전, 3회 범위)

| 방식 | 시간 |
|---|---:|
| 전체 목록 순회 | 0.0031 ~ 0.0041 ms |
| 길이별 해시 집합 | 0.0089 ~ 0.0116 ms |
| 아호-코라식 | 0.0013 ~ 0.0015 ms |

목록이 94배(41 → 3860)가 되는 동안 순회는 약 240배 느려졌다. 아호-코라식은 0.0014ms에서 0.0042ms로 3배 늘었는데, 이는 목록 크기 때문이 아니라 트라이가 커지면서 캐시 적중률이 떨어진 영향으로 보인다. 목록 41개에서도 자동자가 순회보다 빨랐다.

## 세 방식

### 전체 목록 순회 — 기존

금칙어마다 `indexOf`로 메시지를 훑는다. 영문은 앞뒤 글자를 보고 낱말 경계를 확인하고, 그 밖은 포함되기만 하면 걸린다. 목록 크기 × 메시지 길이에 비례한다. 규칙이 코드에 그대로 드러나는 것이 장점이라, 자동자를 넣은 뒤에도 지우지 않고 동치 시험의 기준으로 남겼다.

### 길이별 해시 집합 — 기각

한국어 금칙어를 길이별로 `HashSet`에 넣고, 메시지의 각 위치에서 그 길이만큼 잘라 조회한다. 길이 종류가 12개뿐이라 12번만 훑으면 되고, 구현이 20줄이면 끝난다.

**기호가 섞인 영문 항목을 놓친다.** `@sshole`, `b!tch`, `a$shole`, `carpet muncher`, `.com` 같은 것들인데, 영숫자로 토큰을 나누면 이 말들이 쪼개지기 때문이다. 동치 검사에서 3953개 입력 중 10건이 어긋났다. 별도 처리를 붙이면 고칠 수는 있지만 그러면 이 방식의 유일한 장점인 간결함이 사라진다.

### 아호-코라식 — 채택

금칙어 전부를 트라이 하나로 만들고 실패 링크를 걸어 메시지를 한 번만 훑는다. 목록이 몇 개든 판정 시간은 메시지 길이에만 달린다.

실패 링크로 닿는 말까지 마디마다 미리 합쳐 두어, 판정할 때 링크를 거슬러 올라가지 않는다. 마디마다 두 가지를 들고 있다 — 경계를 보지 않아도 되는 말이 여기서 끝나는가(한국어 등), 경계를 봐야 하는 말들의 길이(영문). 영문 경계 검사는 매치 지점의 앞뒤 글자만 보면 되므로 기존 규칙이 그대로 유지된다.

3860개 기준 트라이 마디 8537개, 메모리 약 6MB. 방 서버 메모리 상한이 3GB이므로 부담되지 않는다.

## 동치 확인 — 이 작업에서 제일 중요한 부분

성능보다 **판정이 갈라지는 것**이 위험하다. 같은 메시지를 게임 서버는 가리고 백엔드는 기록하는데, 둘의 판정이 어긋나면 사람들이 그대로 본 말이 "가려졌다"고 기록되거나 그 반대가 된다. 채팅 기록은 정지의 근거가 되므로 어긋난 기록은 없는 것보다 나쁘다.

그래서 두 언어 모두 기존 구현을 지우지 않고 남겨 시험의 기준으로 삼는다.

| | 기준 구현 | 시험 |
|---|---|---|
| 백엔드 | `WordMatcher.containsWord` | `WordAutomatonTest` |
| 게임 서버 | `ChatBlocklist.HitsByScan` | `ChatModerationTests` |

- 백엔드: 실제 목록 3860개 전부를 그대로·앞뒤에 말을 붙여·어미를 붙여 넣고, 금칙어 조각과 평범한 글자를 섞은 무작위 문자열 2000개를 추가로 넣어 비교했다. 불일치 0건.
- 게임 서버: 표본 30개와 무작위 조합 3000개를 비교했다. EditMode 시험 15개 전부 통과.
- 무작위 시험은 씨앗을 고정했다. 실패하면 같은 입력으로 다시 돌려 볼 수 있어야 한다.

규칙을 고칠 일이 생기면 두 구현을 같이 고치고 이 시험으로 확인한다.

## 적용 범위

- 판정(`IsForbidden` / `isForbidden`)만 자동자로 바꿨다.
- **가리는 코드(`Mask`)는 그대로 두었다.** 자리를 세는 방식이 달라 같은 결과를 보장하기 어렵고(같은 말이 겹쳐 나올 때 현재 구현은 겹치지 않는 자리만 가린다), 가리는 일은 이미 걸린 메시지에만 일어나므로 실시간 경로의 비용이 아니다.
- 닉네임 목록(56개)은 손대지 않았다. 목록이 작고 입력도 한 줄짜리다.

## 함께 고친 것 — 트랜잭션 경계

백엔드의 금칙어 판정이 `@Transactional` 안에서 돌고 있었다. 목록이 41개일 때는 200줄 묶음에 2ms였지만 3860개면 같은 묶음에 150ms가 되고, 그동안 DB 커넥션을 쥐고 있게 된다. 방마다 몇 초 간격으로 묶음이 오므로 커넥션이 그만큼 묶인다.

판정은 DB를 쓰지 않으므로 트랜잭션 밖으로 옮겼다. 같은 빈 안에서 메서드를 부르면 프록시를 타지 않아 `@Transactional`이 걸리지 않으므로, 저장만 하는 `ChatLogWriter`로 클래스를 나눴다. 판정 로직과 저장 로직 자체는 바뀌지 않았다.

```
전: [트랜잭션 시작] 판정 + 조회 + 저장 [커밋]
후: 판정 → [트랜잭션 시작] 조회 + 저장 [커밋]
```

## 이어서 — 채팅 기록 저장 (S15P21D205-1077)

판정을 고치고 나니 같은 경로의 다음 구간이 드러났다. 게임 서버가 2.5초마다 보내는 묶음을 저장하는 부분이다.

`chat_logs_seq` 가 AUTO_INCREMENT 이고 엔티티가 `GenerationType.IDENTITY` 라, Hibernate 는 생성된 키를 행마다 받아야 해서 **insert 배치를 아예 끈다.** `hibernate.jdbc.batch_size` 를 넣어도 달라지지 않는다. Hibernate 통계로 세어 보니 200줄 묶음 하나가 PreparedStatement 200개였다.

### 측정

Testcontainers MySQL 8.4, 200행 묶음. 같은 실행 안에서 둘을 **번갈아** 6회 돌렸다. 한쪽을 다 돌리고 다른 쪽을 돌리면 그 사이의 기계 상태 변화가 차이로 읽힌다 — 실제로 따로 잰 첫 측정은 바꾼 쪽이 더 느리게 나왔고, 번갈아 재고 나서야 맞는 값이 나왔다.

| 방식 | rewrite 켬 | rewrite 끔 |
|---|---:|---:|
| 행마다 한 문장 (JPA saveAll 이 내던 것) | 157.3 ms | 138.0 ms |
| JDBC 배치 | **16.1 ms** | 131.7 ms |

`rewriteBatchedStatements=true` 가 없으면 배치를 써도 5% 차이에 그친다. 이 옵션이 있어야 여러 행이 INSERT 한 문장으로 합쳐진다. **옵션은 운영과 로컬 JDBC URL 에 이미 켜져 있었고**, JPA 쪽이 그것을 쓰지 못하고 있었다.

`@ServiceConnection` 이 시험 DB URL 을 쥐고 있어 `spring.datasource.url` 로는 덮이지 않는다. 드라이버로 그대로 넘어가는 Hikari 의 `data-source-properties` 로 넣어야 운영과 같은 조건이 된다.

### 바꾼 것

`ChatLogBatchWriter` 를 두고 `jdbcTemplate.batchUpdate` 로 넣는다. 분석 모듈의 `GameEventWriter` 와 같은 방식이고, 그쪽은 이벤트 양이 많아 처음부터 그렇게 짰다. 채팅만 JPA 로 남아 있었다.

줄과 값(발신자, 판정)을 자리로 맞추는 코드이므로 행 객체에 값을 함께 담아 넘긴다. 어긋나면 남의 말이 남의 이름으로 남고 그 기록이 정지의 근거가 된다. 같은 말이 반복돼도 줄마다 제 값이 붙는지 보는 회귀 시험을 넣었다.

## 백엔드 전체를 훑고 찾지 못한 것

같은 김에 백엔드 전체를 봤고, 위의 것 말고는 손댈 곳을 찾지 못했다.

- **N+1 없음.** JPA 연관관계를 일부러 걸지 않고 seq 와 네이티브 쿼리로 짰다. `@ManyToOne` 이 하나뿐이고 그것도 LAZY 이며 `open-in-view: false` 다.
- **프레즌스 하트비트** 는 접속자가 몇 명이든 `IN` 한 문장이다. 주석을 보면 이미 한 번 고친 자리다.
- **분석 수집** 은 버퍼와 배치 flush 로 짜여 있다. 가장 양이 많은 경로가 가장 잘 정리돼 있다.
- **인덱스** 는 실제 쿼리 모양과 맞는다. `chat_logs(room_code, sent_at)`, `(sender_seq, sent_at)`, `(sent_at)` / `friendships` 유니크와 `user_high_seq` / `user_presence(status, heartbeat_at)`.
- **트랜잭션 안에서 외부 HTTP 를 부르는 곳이 없다.**
- **조회 범위** 는 대화 조회 ±180분 상한이 있고 나머지는 사용자당, 기간당으로 묶인다.

봐 둘 값이 둘 남는다. 보관 청소 쿼리(`deleteExpired`)는 `NOT EXISTS` 안에서 칼럼에 함수를 씌워 `user_reports` 인덱스를 쓰지 못한다. 3일치라 지금은 표가 작아 견딘다. 커넥션 풀이 10이고 Tomcat 스레드가 200인 것도 100~200명 부하 측정 때 함께 볼 값이다.

## 측정하지 않은 것

- 실제 6인 경기에서의 tick 지연이나 GC 영향. 이 문서의 숫자는 판정 로직만 뽑아 낸 값이다.
- C# 쪽 실측. 구현은 자바와 같은 구조지만 시간은 재지 않았고, 동치만 확인했다.
- 목록을 더 키웠을 때(1만, 10만)의 곡선. 아호-코라식이 목록 크기와 무관하다는 것은 알고리즘의 성질이지 이 측정으로 확인한 사실은 아니다.
- 운영 DB 에서의 저장 시간. 위의 숫자는 Testcontainers 로 띄운 MySQL 에 대고 잰 값이다. 왕복 비용의 모양은 같지만 절대값은 다르다.
