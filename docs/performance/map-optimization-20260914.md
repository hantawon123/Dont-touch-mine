## 1. 정지한 물건의 불필요한 갱신 제거
커밋 470fea97. CarryableItem은 참가자의 물건 위치를 보간할 때만 FixedUpdate를 실행한다. 스크립트만 비활성화하며 Rigidbody, Collider, GameObject와 공개 상호작용 메서드는 유지한다.
검증: 새 PlayMode/씬 전환3, 물건·배치 EditMode27, 착지·받침 제거·결과 상태 복구 PlayMode6 통과. 정상 정지 구간에서 CarryableItem.FixedUpdate 호출 제거 확인.

## 2. 렌더 방식 대조: 기존 설정 유지
정적 배칭 범위 조정은 개선을 확정하지 못해 제외했다. 고정 배경은 이미 상당 부분 배칭되고 있다.
CPU 오클루전 베이크와 GPU 인스턴싱(SRP 배처 비활성화)을 각각 동일한 3개 스폰 위치 × 4방향에서 비교했다. 640×360 오프스크린 Camera.Render, 각 모드 워밍업 후3회 평균, 실행 순서를 시야마다 교대했다. 모두 12개 시야에서 픽셀 차이가0이었지만, CPU 렌더 호출 시간은 대부분 증가했다. 그러므로 새 베이크 데이터, 재질/파이프라인 설정, 실험용 배칭 코드는 원본에 적용하지 않았다.
이 시간은 GPU 실행 시간이나 WebGL FPS가 아니다. Unity 에디터/프로파일러/Single 모드 측정이며, 실험에서 효과가 없었다는 뜻이지 모든 플랫폼에서 GPU 인스턴싱이 느리다는 뜻은 아니다.

| 실험 | 기존 방식 중앙값 | 후보 방식 중앙값 | 판단 |
|---|---:|---:|---|
| 가림 처리 | 10.425ms | 12.249ms | 미적용 |
| GPU 인스턴싱 | 9.488ms | 12.511ms | 미적용 |

검증 주의: 맵 진단 직후 같은 프로세스에서 기존 물리 단위 시험을 실행했을 때, 남아 있는 맵 충돌체가 시험에 간섭하여 한 건 실패했다. 물리 시험을 독립 실행한 결과는6/6 통과했다. 통합 진단과 독립 물리 시험을 구분한다.

## 3. 실행 전에 초기화 작업 선계산
빌드 씬 처리기에서 경기 맵의 물건 ID, 배치 범위, Carryable 레이어를 선계산한다. 원본 씬/프리팹은 저장하지 않는다. 로비 ID 규약에 영향을 주지 않도록 PlaygroundLifetimeScope가 있는 경기 씬에만 적용한다. 런타임 생성 프리팹은 기존 경로를 유지하고, 크기가 달라지면 배치 범위를 다시 계산한다.
에디터/미준비 프리팹에서는 같은 이름의 카탈로그 검색 결과를 재사용한다. 카탈로그가 바뀌면 캐시를 비우고, 개별 씬 계층 ID는 공유하지 않는다.
검증: Supermarket6423개 물건의 ID/배치 범위 일치, PlayMode6/6, 관련 EditMode95/95. 빌드 전처리를 모사한 진단 씬에서 Capture0.087초, 안내3.080초, 첫 조작 시 소모된 게임 시간0.031초. 최대 프레임 정지3.775초는 여전히 남았다.
이는 초기화 지연을 게임 플레이로 넘기는 방식이 아니다. 비동기 씬 활성화를 완전히 분할한 것도 아니며, 모든 로딩 정지가 해결됐다는 뜻은 아니다. 단회 프로파일 수치를 WebGL FPS로 환산하지 않는다.

## 4. 장식/충돌 구성 검사: 기능 보존을 위해 삭제하지 않음
실제 경기 씬을 에디터 API로 검사했다. Rigidbody6423개와 CarryableItem6423개가 대응하며, 영구 장식으로 지정된 물건 목록은 없다. 기존 집기 가능 물건을 임의로 장식으로 바꾸지 않았다.
같은 GameObject에 MeshCollider와 BoxCollider가 함께 있는639개는 모두 convex MeshCollider였지만, 박스 내부에 모든 정점이 있고8개 모서리를 모두 포함하는 정확한 동일 충돌체는0개였다. 바운딩 박스가 비슷하다는 이유만으로 MeshCollider를 지우면 이동/점프/배치/물건 쌓기 충돌이 바뀔 수 있어 제외했다.
검증: 진단 전용 MapComponentAudit.Run 정상 종료(exit0). 구성 요소 삭제나 씬 저장은 수행하지 않았다. 이 검사는 해당 안전한 삭제 후보를 제외한 결과이며, 모든 종류의 맵 최적화가 불가능하다는 뜻은 아니다.
